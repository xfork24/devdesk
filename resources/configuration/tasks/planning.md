# Task 规划与依赖拆分

## 目标与适用边界

把已采纳需求和设计分解为可独立交付、可汇合的 Task 集合。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- 同一基线上的需求、设计和验收编号，已有工作计划与已接受交付。
- 模块与接口依赖、允许并行的工作树边界、可用测试环境和交付约束。
- 已确定的外部依赖和未决问题；缺少接口或范围决定时标明阻塞，不自行替换架构方案。

## 必需交付内容

### 本次工作范围

- 逐项写清目标、范围、依赖、AC 责任和预期产物，避免任务间重叠拥有业务状态。
- 建立无环依赖图并为每项 Task 配置自身 TestRecipe，核对文件、接口与命令。
- 输出引用 requirement_id、design_id 的 task_plan 提案；不在规划中擅自改变已采纳架构。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

按当前 output_contract 提交对应 ProposalContent，正文与结构化 ID、验收或 Task 字段保持一致。提案是待采纳建议，不是正式交付接受事实；根据反馈修订后等待用户采纳。

## 内容与一致性检查

- 任务边界不重复拥有同一业务状态，验收有明确责任且不遗漏。
- 每项 Task 能在其依赖满足后独立完成测试及交付；不要求其他无关 Task 或 Feature 最终产物提前存在。
- TestRecipe、文件路径和导出接口真实可执行，环境准备与断言失败有区分。
- 任务、依赖、范围和汇合策略与已采纳设计一致，新增需求或架构改变有明确修订入口。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本节点所需材料或动作实际完成、返回结构合法且范围与证据明确后，才可提交下一门禁。 任务清单、无环依赖、验收映射及逐项测试配方完整且一致时才可提交规划交付。存在循环、任务无法独立验收或缺少关键接口时应拒绝并定位具体任务与依赖。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 保留需求/设计修订、任务 key、依赖图和覆盖矩阵；计划与配方只是未来执行约定，不把计划中的测试写成已执行事实。
