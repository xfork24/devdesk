# Feature 收尾公共任务

## 目标与适用边界

在固定的已接受 Task 集合上完成 Feature 的整体验证和交付说明。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- Feature 冻结需求、设计、固定 TaskGroup、已接受的 Task 交付和当前 Feature 代码版本。
- Feature TestPlan、完整测试配方、已有评审发现和要求保留的独立断言。
- 允许写入的测试或文档范围、实际测试环境、合入前仍需完成的候选验证要求。

## 必需交付内容

### 本次工作范围

- 核对源 Task 交付、当前 Feature SHA、完整验收和 prior_review_findings。
- 仅在授权测试和文档节点补全整体测试与使用说明，保留有效独立断言。
- 汇总完整 Feature 结果和限制，不把局部 Task 通过冒充整体验收，也不伪造新的 TDD Red。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

按当前 output_contract 返回本节点的执行摘要、实际产物与限制；不把执行摘要、结构化提案和内容评审报告混用。没有真实 Run 或回执时不得声称测试、交付或远端操作成功。

## 内容与一致性检查

- 完整 AC 覆盖和跨 Task 行为有实际内容与测试证据，不能仅检查各 Task 状态为通过。
- 测试与文档对应当前 Feature SHA，评审发现已定位和处理，已知限制明确。
- 收尾补测遵守写范围，不修改产品实现或把环境问题伪装成产品断言。
- 原始 TDD Red 属于各 Task 实现证据；Feature 收尾不应伪造一次新的 TDD Red。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本节点所需材料或动作实际完成、返回结构合法且范围与证据明确后，才可提交下一门禁。 完整 Feature 验收、实际测试和文档齐备且独立评审通过后，才进入精确候选交付流程。存在关键 AC 未覆盖、测试过期或评审问题未闭合时应拒绝并定位证据缺口。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 保留固定 Task 交付引用、Feature SHA、完整配方和真实 Run/Artifact；清楚说明虚构服务、平台差异及未验证范围，不能把局部测试结论扩大到全部环境。
