# 方案内容验证

## 目标与适用边界

检查已采纳设计和 TaskPlan 能否落实需求，且彼此一致、可执行。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- 冻结且已采纳的需求、设计、任务计划、测试计划和当前步骤 Spec。
- 固定 Task 清单及依赖、各 TestRecipe、验收映射与未决问题。
- 作者使用的 Role/Skill 精确修订和先前评审发现；按这些材料的真实要求进行内容检查。

## 必需交付内容

### 本次工作范围

- 沿 AC 核对设计接口、数据和不变量，再核对负责 Task、依赖与交付边界。
- 检查循环、悬空或不可满足的依赖、共享写入冲突，以及各 Task 能否独立测试交付。
- 定位具体材料、接口或任务问题；不能因为计划中的实现和真实运行尚不存在而拒绝方案。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

严格输出当前 output_contract 规定的单个 JSON 对象：approve、summary、checks。checks 为 traceability、scope、tests、failure_paths 四类，各项给出 key、passed、evidence；依据当前 Skill 和 Spec 的真实内容填写，不固定为测试版标题或关键词。发现实质内容缺口时 approve=false，并指出具体位置、影响和改进内容。格式正确、外部调用成功或章节齐全均不足以 Approve。模型结论随后仍等待人类 Approve；人类覆盖 Reject 时保留原结论和理由。

## 内容与一致性检查

- 需求与方案范围一致，所有验收都有落实位置，非目标没有被计划重新加入。
- 接口、数据、不变量、任务依赖和测试预期不存在相互冲突。
- 可执行配方和故障策略有具体内容，不能只凭文件名或关键词判断通过。
- 本阶段不要求未来代码和实际测试结果已经存在，缺少未来产物不能充当方案拒绝理由。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本次内容判断已逐项给出证据，才可提交模型建议。存在缺口时明确 Reject，保留返工定位并等待人类决定。 所有阻碍实现或独立验证的方案缺口都有处置结论后，才可提交方案交付。模型 approve 只表示内容建议；独立评审和人类确认仍按工作流执行，存在实质缺口时 approve=false。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 引用各材料精确修订、AC/Task/用例编号与对应正文位置。区分已读到的设计事实、必要的方案推演及仍待真实执行证明的事项。
