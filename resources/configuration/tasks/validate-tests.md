# 测试计划内容验证

## 目标与适用边界

独立核对 TestPlan 与每项 TestRecipe 的质量、覆盖和可执行性。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- 冻结需求、设计、TaskPlan、稳定 AC-* 及接口和状态不变量。
- 当前 Task 或 Feature 的测试范围、允许写入的测试目录、执行镜像/命令和依赖限制。
- 已知缺陷、已有独立测试和评审发现；标明可复用证据的版本与范围。

## 必需交付内容

### 本次工作范围

- 检查正常、错误、边界和恢复用例是否有明确预期，AC 覆盖是否完整且责任清楚。
- 核对文件、导出、命令、环境和失败分类，区分 Task 自身测试与 Feature 完整验证。
- 计划阶段不编造运行结果；缺口应指向具体用例、配方或遗漏的验收。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

严格输出当前 output_contract 规定的单个 JSON 对象：approve、summary、checks。checks 为 traceability、scope、tests、failure_paths 四类，各项给出 key、passed、evidence；依据当前 Skill 和 Spec 的真实内容填写，不固定为测试版标题或关键词。发现实质内容缺口时 approve=false，并指出具体位置、影响和改进内容。格式正确、外部调用成功或章节齐全均不足以 Approve。模型结论随后仍等待人类 Approve；人类覆盖 Reject 时保留原结论和理由。

## 内容与一致性检查

- 预期结果能区分正确与错误实现，断言不只是调用成功或对象存在。
- 每个关键验收有对应测试，错误与恢复行为覆盖完整，范围与当前阶段一致。
- 环境准备错误不会被计为产品 Red；已通过的局部测试不会被扩大解释为完整 Feature 验证。
- 测试、设计和配方中的文件、命令、导出与依赖一致，不依靠隐藏安装或修改产品代码来运行。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本次内容判断已逐项给出证据，才可提交模型建议。存在缺口时明确 Reject，保留返工定位并等待人类决定。 用例、预期、覆盖和配方可供独立执行时，测试计划才可提交采纳。缺少断言、使用空壳测试、无法复现环境或混淆失败分类时应要求修订。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 计划阶段保留 AC 与用例/配方映射；执行阶段提供真实 Run、测试 Artifact、代码 SHA 和失败分类。未运行、受夹具限制和结果未知的范围必须明确。
