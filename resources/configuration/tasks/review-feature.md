# 独立评审 Feature 交付

## 目标与适用边界

独立审查完整 Feature 的固定源交付、验收、测试和文档。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- Feature 冻结需求、设计、固定 TaskGroup、已接受的 Task 交付和当前 Feature 代码版本。
- Feature TestPlan、完整测试配方、已有评审发现和要求保留的独立断言。
- 允许写入的测试或文档范围、实际测试环境、合入前仍需完成的候选验证要求。

## 必需交付内容

### 本次工作范围

- 核对固定 Task 集合、完整 AC、跨任务行为及当前 Feature SHA 上的实际测试。
- 检查 prior_review_findings 是否真实关闭，使用说明、错误恢复和剩余局限是否准确。
- Task 局部通过不能代替 Feature 完整验证；原始 TDD Red 归属各 Task，不要求收尾新造 Red。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

严格输出当前 output_contract 规定的单个 JSON 对象：approve、summary、checks。checks 为 traceability、scope、tests、failure_paths 四类，各项给出 key、passed、evidence；依据当前 Skill 和 Spec 的真实内容填写，不固定为测试版标题或关键词。发现实质内容缺口时 approve=false，并指出具体位置、影响和改进内容。格式正确、外部调用成功或章节齐全均不足以 Approve。模型结论随后仍等待人类 Approve；人类覆盖 Reject 时保留原结论和理由。

## 内容与一致性检查

- 完整 AC 覆盖和跨 Task 行为有实际内容与测试证据，不能仅检查各 Task 状态为通过。
- 测试与文档对应当前 Feature SHA，评审发现已定位和处理，已知限制明确。
- 收尾补测遵守写范围，不修改产品实现或把环境问题伪装成产品断言。
- 原始 TDD Red 属于各 Task 实现证据；Feature 收尾不应伪造一次新的 TDD Red。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本次内容判断已逐项给出证据，才可提交模型建议。存在缺口时明确 Reject，保留返工定位并等待人类决定。 完整 Feature 验收、实际测试和文档齐备且独立评审通过后，才进入精确候选交付流程。存在关键 AC 未覆盖、测试过期或评审问题未闭合时应拒绝并定位证据缺口。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 保留固定 Task 交付引用、Feature SHA、完整配方和真实 Run/Artifact；清楚说明虚构服务、平台差异及未验证范围，不能把局部测试结论扩大到全部环境。
