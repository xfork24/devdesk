# 需求澄清与 PRD

## 目标与适用边界

从本次用户问题澄清目标、用户与范围，形成可以人工采纳的需求提案。

## 输入与前置条件

- 本次 Step 或配方节点冻结的任务、Role/Skill/Spec 与输出合同；先确认对象、阶段、输入修订和职责。
- 用户原始描述、现状流程与约束，注明提供者、材料位置和修订；区分已证实事实、暂定假设与待决策事项。
- 已有需求和相关 Feature 的边界；核对历史经验的适用条件，不把历史结论当作当前事实。
- 目标用户、业务优先级、受影响数据和外部依赖；缺失信息须列出影响及最小澄清问题。

## 必需交付内容

### 本次工作范围

- 先核实事实、约束和主要场景，提出阻碍验收定义的最小问题。
- 为正常、失败、边界和恢复行为编写稳定 AC-*，正文与结构化 acceptance 保持一致。
- 输出 requirement 提案及可阅读正文，标注假设、未决事项和来源；不提前替用户选定实现。

### 内容与定位要求

围绕当前阶段交付具体事实、判断和缺口；引用 AC、Task、材料章节、实际文件或代码版本，说明范围与剩余限制。不能只重复章节标题或声称已检查。

### 返回内容与决策边界

按当前 output_contract 提交对应 ProposalContent，正文与结构化 ID、验收或 Task 字段保持一致。提案是待采纳建议，不是正式交付接受事实；根据反馈修订后等待用户采纳。

## 内容与一致性检查

- 目标、范围、流程和验收指向同一产品行为，非目标没有以隐藏前置条件重新进入范围。
- 每个 AC-* 都可由输入与可观察结果判定，编号唯一、引用有效，新增或删除验收的影响有说明。
- 错误、边界、恢复和未决事项具有实际内容，不以标题、关键词出现或笼统“已考虑”替代判断。
- 需求质量检查不要求设计、Task、实现或真实测试已经存在；“未来尚未实现”不能作为此阶段的拒绝理由。
- 核对返回内容是否属于当前角色及节点范围，是否如实区分已执行、未运行、失败与未知结果。

## 完成与拒绝标准

本节点所需材料或动作实际完成、返回结构合法且范围与证据明确后，才可提交下一门禁。 正文和结构化验收一致、关键歧义有明确处理、需求可供人工采纳时，讨论交付才完整。正式验证与独立评审仍须遵守对应工作流门禁；内容有缺口时指出具体章节、AC 和修改建议，不宣布需求已被接受。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 引用用户输入、材料修订和确认结论；说明哪些事实已核实、哪些仅是假设。需求阶段可提交场景走查与内容证据，不编造尚未发生的实现、测试或业务效果。
