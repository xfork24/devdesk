# 默认工程 Standard

## 目标与适用边界

规定项目从需求到主线交付的通用质量与协作边界。工作流组织步骤，Role、Skill 和 Spec 细化职责及方法；它们均不能豁免内核的冻结、权限、独立测试、评审和合入不变量。

## 输入与前置条件

- 项目目标、需求与验收基线、所选 Workflow/Role/Skill/Spec 的精确修订。
- 工作树和代码基线、固定 Task 集合、测试配方、真实执行及权限合同。
- 外部服务和远端副作用边界、人工确认规则、历史问题与兼容要求。

## 必需交付内容

### 需求与规划

需求先讨论并采纳，再正式验证及独立评审。设计、TaskPlan 和 TestPlan 必须引用同一 AC 基线，包含接口、范围、依赖、失败恢复与逐项配方。

### 独立测试与实现

测试和实现职责分离。真实断言 Red、实现后的 Green、回归和 verify 需指向实际代码，保护只读测试和用户修改。

### Task 与 Feature

Task 对自身范围、验收和配方负责；Feature 收尾还需固定源交付、完整 AC 与跨任务测试，不能互相替代证据。

### 评审与决定

Reviewer 独立评价内容和证据，保留问题定位与原始模型结论。业务接受及必要人类确认由有权角色或协调器记录。

### 精确候选与交付

候选来源、父关系、源与目标 SHA、候选测试和评审必须一致。主干推进核对 CAS 与远端 lease；快照和资源释放需有真实回执。

### 修订与恢复

定义、材料、流程与冻结输入不可原地改写。新修订显式采用；结果未知先核对，不把超时当作可以自动重发的证明。

## 内容与一致性检查

- 所有重要 AC 都有责任材料、Task 和测试来源，范围变更有对应修订和重新验证决定。
- 模型返回、命令启动、输入已消费、执行终态、交付接受与远端推进分别有独立事实依据。
- 自动检查、夹具结果、局部测试和历史经验的适用范围明确，不能扩大解释为完整真实验收。
- 权限、工作树、只读测试和职责分离得到实际执行，不能通过文本指令绕过合同。

## 完成与拒绝标准

按当前阶段的 planning、implementation 或 merge Spec 判断是否达到门禁；格式合法与自动检查通过不足以证明整体质量。出现缺口须给出位置、影响和改进办法，例外决策保留理由及原始结论。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 每个交付保存材料修订、代码与候选 SHA、测试 Run/Artifact、评审及确认记录；明确未运行、失败、未知和平台限制。
