# 工程工作方法与阶段协作

## 目标与适用边界

把需求、方案、独立测试、实现、评审和交付组织为可追溯的工程过程。每个角色只完成当前节点职责，任何推进都以真实材料、执行回执和有权决定为依据。

## 输入与前置条件

- 当前阶段、冻结需求和验收，当前角色、Task/Feature 范围、流程配方及绑定规范。
- 已采纳的上游材料、实际代码与测试结果、独立评审发现和必要人工决定。
- 可用工具、冻结 Permission、工作树与资源状态。

## 必需交付内容

### 阶段材料

需求形成可验收 PRD，方案形成明确设计、无环任务与可执行测试计划；正文和结构化编号相互一致。

### 执行交付

按测试职责编写、真实 Red、实现、Green、文档、verify 推进，Task 与 Feature 各自承担其完整范围。

### 评审与交付

独立评审指出有证据的缺口，精确候选验证对应同一 SHA，必要人类确认后由协调器推进并保存快照。

### 执行顺序

1. 确认本阶段应交付什么、由谁验证、哪些事实尚未成立。
2. 取得和核对输入，完成当前角色的方法步骤与交付。
3. 验证内容、范围及证据，将问题定位到具体材料、验收或代码。
4. 等待相应采纳、独立评审或人类确认，再按工作流进入后续阶段。

## 内容与一致性检查

- 材料在当前阶段是否充分具体，不能把标题存在或格式合法视为内容合格。
- 是否正确区分计划、实际执行、模型 Approve、人类确认和业务接受，不能越过职责直接设置终态。
- 失败是否区分产品、测试、环境与未知外部结果，恢复是否避免重复副作用。
- 新修订是否明确影响旧证据，已开始的执行是否继续使用其冻结输入。

## 完成与拒绝标准

当前节点交付和证据满足对应 Spec 后提交下一门禁；任何关键材料、真实结果或决策缺失都应明确指出。异常返工使用可追溯修订，保留原结论和历史。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 每项结论给出材料位置或执行来源，并说明未验证范围。自动规则只覆盖已实现检查，不能代替内容阅读和真实工程验证。
