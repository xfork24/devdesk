# 工程上下文与工作树核对方法

## 目标与适用边界

在讨论、执行、恢复和跨角色交接时建立可以核验的工程现场，防止混用项目、材料、工作树、代码修订与历史结果。

## 输入与前置条件

- 当前 Project、Feature、Task、阶段和职责，以及应用提供的冻结任务与材料索引。
- 当前工作目录、工作树、预期基线、允许写路径、只读测试路径和外部调用范围。
- 已有会话、快照、执行回执及恢复原因；历史经验只作为参考输入，不拥有当前执行权威。

## 必需交付内容

### 现场清单

列出当前对象和精确材料修订、工作树及代码 SHA、角色与权限边界、已满足和缺失的前置条件。

### 差异与冲突

指出当前状态与预期基线、用户已有修改或历史材料之间的差异，说明对下一步行为和证据的影响。

### 恢复与交接

记录未完成操作、输入是否已消费、外部结果是否确认、writer 是否停止及应由谁核对；给出可以安全继续的条件。

### 执行顺序

1. 从冻结任务识别目标及当前职责，读取所需需求、设计、测试、Skill 和 Spec 的确切修订。
2. 核对工作树、基线、当前 SHA 与用户修改，再确认写入、命令和网络范围。
3. 仅检索任务相关文件，记录关键事实及其来源；外部资料与历史经验不得替换当前输入。
4. 交接或恢复时重新核对现场与回执，列出已完成、未完成及禁止重复执行的操作。

## 内容与一致性检查

- 对象、工作树、材料和代码版本能相互对应；不能因为目录名称相似就当作同一任务现场。
- 保留用户修改，只在授权范围写入，不通过复制只读测试、跨工作树改写或读取私有运行状态绕过限制。
- 旧测试、旧评审与旧经验只能证明其原始版本和范围；与当前现场有差异时必须说明。
- 结果未知不等于未执行；恢复前先核对回执和 writer，不盲目重发副作用。

## 完成与拒绝标准

全部关键输入和现场已确认，缺口及冲突有明确处置方式后才进入依赖它们的动作。发现跨项目引用、基线不符或未知外部结果时应保留现场并请求核对，不能凭假设继续。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 保留对象 ID、材料修订、代码/候选 SHA、命令、环境、退出码和实际回执；对未运行、失败和未知结果分别标记。

## 当前执行合同

以本次 `task_instructions`、`inputs`、`input_sources`、`outputs` 和 `output_contract` 为执行依据。材料已经通过 Workflow 端口接纳时，不再要求额外的提案采纳或未声明的文档 ID。只在本次任务确实缺少必要事实时请求补充输入。若当前未授予代码视图，明确这一限制，不虚构读取结果；能够基于当前明确事实完成的设计或检查应继续完成。
