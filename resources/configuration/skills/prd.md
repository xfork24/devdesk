# 需求分析与 PRD 成文

## 目标与适用边界

用事实澄清、场景走查和验收建模，将问题形成可讨论、可采纳的需求文档。

## 输入与前置条件

- 用户原始描述、现状流程与约束，注明提供者、材料位置和修订；区分已证实事实、暂定假设与待决策事项。
- 已有需求和相关 Feature 的边界；核对历史经验的适用条件，不把历史结论当作当前事实。
- 目标用户、业务优先级、受影响数据和外部依赖；缺失信息须列出影响及最小澄清问题。

## 必需交付内容

### 问题与目标

写清现状、用户损失、期望变化和成功指标。指标应包含观察对象、触发条件或度量口径；无法量化时给出可重复的判定办法。

### 用户与流程

描述主要用户、权限、前置状态和主流程；列出关键决策点、用户看到的反馈及流程结束后的可观察状态。

### 范围与非目标

把本次包含、不包含和依赖外部提供的能力分开。说明与已有行为的兼容要求，不能把未承诺的周边需求写进验收。

### 验收条目

为每项行为分配稳定 AC-* 编号，写明条件、操作、预期结果与验证方式。验收编号在当前文档与所引用的材料中保持一致，避免“体验良好”“全部正常”等不可判断表述。

### 异常与恢复

覆盖非法输入、空状态、重复操作、权限不足、网络或依赖失败、中断与重试；对不适用的情况解释原因，说明错误提示和已有数据如何处理。

### 约束与未决问题

记录性能、兼容、权限、资源和数据约束；每个未决问题给出责任方、影响范围与决定前能否继续的条件。

### 执行顺序

1. 先复述问题和目标，定位影响最大的歧义，再询问阻碍验收定义的问题；将用户新补充的约束合并到同一份需求。
2. 按用户流程分解行为，为每个分支写出可观察结果，再建立 AC-* 与正文位置的双向索引。
3. 用至少一个正常场景和一个失败场景走查需求；发现相互矛盾的预期时明确冲突，提交待决定事项。
4. 按本次输出端口声明提交需求正文及其中的验收条目；若端口格式为 Markdown，输出值就是正文字符串。接纳、确认或后续检查由当前 Workflow 定义。

## 内容与一致性检查

- 目标、范围、流程和验收指向同一产品行为，非目标没有以隐藏前置条件重新进入范围。
- 每个 AC-* 都可由输入与可观察结果判定，编号唯一、引用有效，新增或删除验收的影响有说明。
- 错误、边界、恢复和未决事项具有实际内容，不以标题、关键词出现或笼统“已考虑”替代判断。
- 需求质量检查不要求设计、Task、实现或真实测试已经存在；“未来尚未实现”不能作为此阶段的拒绝理由。

## 完成与拒绝标准

正文和结构化验收一致、关键歧义有明确处理、需求可供人工采纳时，讨论交付才完整。正式验证与独立评审仍须遵守对应工作流门禁；内容有缺口时指出具体章节、AC 和修改建议，不宣布需求已被接受。

## 工具与证据

使用所选 Harness 的原生读取、搜索及获准命令工具，执行以冻结 Permission 和当前节点范围为准；工具出现在目录中不代表已获写入或网络授权。历史经验由应用检索、选择并恢复后提供，须标注来源和适用条件，不能替代当前现场核实。 引用用户输入、材料修订和确认结论；说明哪些事实已核实、哪些仅是假设。需求阶段可提交场景走查与内容证据，不编造尚未发生的实现、测试或业务效果。

## 当前执行合同

以本次 `task_instructions`、`inputs`、`input_sources`、`outputs` 和 `output_contract` 为执行依据。材料已经通过 Workflow 端口接纳时，不再要求额外的提案采纳或未声明的文档 ID。只在本次任务确实缺少必要事实时请求补充输入。若当前未授予代码视图，明确这一限制，不虚构读取结果；能够基于当前明确事实完成的设计或检查应继续完成。
