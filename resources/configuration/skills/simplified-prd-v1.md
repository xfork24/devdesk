# 精简版需求成文
以冻结原始请求和本步骤 Spec 为准，不增加需求，不替后续设计预选方案。先判断有无真正阻断成文的问题；无阻断直接交付。

明确的小型单 Task 修改采用下面的紧凑版式。保留全部六个必需标题，每节通常一句；把篇幅用于可验收规则，通常约 500–800 个字符（含代码和标点）足够。内容确有需要仍须补齐，不为字数删减规则。复杂需求按实际复杂度展开。

- 问题与目标：一行说明来源、问题及可观察的成功结果。
- 用户与流程：一行写调用者、接口和反馈，可复用 AC 中的正常/失败例子。
- 范围与非目标：合并写本次交付、保护边界及不做事项。
- 验收条目：按独立业务行为编号。每条一至两句，含条件、操作、确切结果及验证方式；原请求的全部指定例子集中写一次。类型/异常及空结果必须可判定。
- 异常与恢复：只补 AC 未覆盖的真实异常和状态影响；无状态/网络/权限场景可合为一句，不分别展开不适用项。
- 约束与未决问题：一行写真实约束及有无阻断问题，未现场核实的现状如实标注。

交付路径和流水线约束在范围或约束章节集中保留，不为每个既有评审、人工决定、回归、PR 或平台职责再建立单独功能 AC；也不要在各 AC 的验证方式中重复整个流水线。原请求中的这些要求仍必须完整满足，当前 Workflow 继续执行全部门禁。需求 AC 以本次业务行为和交付为主，任务计划可以直接引用它们。

不要复制完整 UUID、摘要及上游全文；使用冻结 source_ref 说明来源。不要反复声明每个后续阶段尚未发生；只在实际可能混淆来源时说明。本阶段提交可供独立评审和人工确认的需求正文，不宣布被接受。
