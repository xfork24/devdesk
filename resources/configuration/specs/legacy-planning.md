# 规划阶段综合规范

## 目标与适用边界

在实现前确认 PRD、Design Doc、TaskPlan 和 TestPlan 形成一致、可执行的整体方案。验证材料之间的实际内容，而非仅确认引用存在或章节标题齐全。

## 输入与前置条件

- 冻结且已采纳的需求、设计、任务计划、测试计划和当前步骤 Spec。
- 固定 Task 清单及依赖、各 TestRecipe、验收映射与未决问题。
- 作者使用的 Role/Skill 精确修订和先前评审发现；按这些材料的真实要求进行内容检查。

## 必需交付内容

### 追溯矩阵

逐项说明 AC-* 对应设计、责任 Task、测试用例和执行配方，指出遗漏、冲突或重复责任。

### 接口与依赖核对

验证任务间输入输出能够衔接，接口、数据和状态含义一致，依赖 DAG 无环且可以推进。

### 测试可执行性

检查每项 Task 自身测试与完整 Feature 测试的分工、环境、文件和断言，以及后续 Red/Green/verify 的取得方式。

### 问题与影响

每个缺口注明材料修订、章节/任务/AC、具体矛盾、影响及建议由哪类材料修订。

### 逐项内容结论

按当前 output_contract 返回检查结论；需要模型内容判断时，给出 approve、summary 和四类 checks 的具体依据。

### 执行顺序

1. 先建立完整材料索引，确认全部输入来自同一冻结基线，再沿验收逐条对照设计、任务与测试。
2. 推演关键业务、错误和恢复流程，检查跨材料的接口和责任是否闭合。
3. 验证 TestRecipe 与约定工程环境的一致性，把计划缺陷和将来实现结果分开。
4. 输出有定位依据的问题清单和结论，等待独立评审及人类决定，不修改已采纳材料来消除矛盾。

## 内容与一致性检查

- 需求与方案范围一致，所有验收都有落实位置，非目标没有被计划重新加入。
- 接口、数据、不变量、任务依赖和测试预期不存在相互冲突。
- 可执行配方和故障策略有具体内容，不能只凭文件名或关键词判断通过。
- 本阶段不要求未来代码和实际测试结果已经存在，缺少未来产物不能充当方案拒绝理由。

## 完成与拒绝标准

所有阻碍实现或独立验证的方案缺口都有处置结论后，才可提交方案交付。模型 approve 只表示内容建议；独立评审和人类确认仍按工作流执行，存在实质缺口时 approve=false。

## 工具与证据

引用各材料精确修订、AC/Task/用例编号与对应正文位置。区分已读到的设计事实、必要的方案推演及仍待真实执行证明的事项。 自动规则仅覆盖已实现的有限检查；traceability、failure_paths、sections 通过不能替代上述内容评审。
