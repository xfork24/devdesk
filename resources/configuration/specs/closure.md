# Feature 完整验收规范

## 目标与适用边界

在固定的已接受 Task 集合上验证完整 Feature，而不是把各 Task 的局部成功相加当作整体验收。确认用户流程、跨任务接口、完整测试与使用文档共同满足冻结需求。

## 输入与前置条件

- Feature 冻结需求、设计、固定 TaskGroup、已接受的 Task 交付和当前 Feature 代码版本。
- Feature TestPlan、完整测试配方、已有评审发现和要求保留的独立断言。
- 允许写入的测试或文档范围、实际测试环境、合入前仍需完成的候选验证要求。

## 必需交付内容

### 整体追溯

逐项映射 Feature AC-* 到源 Task、实现位置、完整测试及证据，暴露遗漏或跨 Task 的责任断点。

### 完整测试

测试职责仅在授权测试目录补全 Feature 用例，覆盖端到端流程、模块交互、共享状态、失败及恢复；保持原有有效断言。

### 实际验证

在明确的 Feature 代码 SHA 上运行完整配方，记录环境、退出码、失败分类和关键结果，不用旧 Task 报告替代。

### 使用与交付说明

说明整体入口、运行条件、接口协作、错误反馈、已知限制和恢复方法，清楚区分局部与完整验证范围。

### 评审问题处置

逐项回应 prior_review_findings，给出修复位置与重验证结果；未解决事项说明影响与处置决定。

### 执行顺序

1. 核对固定源交付和实际代码，确认没有遗漏、额外混入或使用过期 Task 结果。
2. 依据完整 Feature 验收组织独立测试，在授权范围内补测；不能通过修改产品代码或弱化断言隐藏失败。
3. 运行完整配方并更新文档，检查各 AC 的真实证据以及跨任务故障路径。
4. 提交 Feature 收尾交付并等待独立评审；候选验证与主干确认仍属于后续步骤。

## 内容与一致性检查

- 完整 AC 覆盖和跨 Task 行为有实际内容与测试证据，不能仅检查各 Task 状态为通过。
- 测试与文档对应当前 Feature SHA，评审发现已定位和处理，已知限制明确。
- 收尾补测遵守写范围，不修改产品实现或把环境问题伪装成产品断言。
- 原始 TDD Red 属于各 Task 实现证据；Feature 收尾不应伪造一次新的 TDD Red。

## 完成与拒绝标准

完整 Feature 验收、实际测试和文档齐备且独立评审通过后，才进入精确候选交付流程。存在关键 AC 未覆盖、测试过期或评审问题未闭合时应拒绝并定位证据缺口。

## 工具与证据

保留固定 Task 交付引用、Feature SHA、完整配方和真实 Run/Artifact；清楚说明虚构服务、平台差异及未验证范围，不能把局部测试结论扩大到全部环境。 自动规则仅覆盖已实现的有限检查；traceability、failure_paths、sections 通过不能替代上述内容评审。
