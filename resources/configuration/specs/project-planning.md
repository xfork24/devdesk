# Task Plan 拆分规范

## 目标与适用边界

把已采纳需求与设计拆成可独立验证和交付的 Task 集合。每项任务有明确边界、依赖和验收责任，汇合后能够覆盖完整 Feature，而非只罗列活动名称。

## 输入与前置条件

- 同一基线上的需求、设计和验收编号，已有工作计划与已接受交付。
- 模块与接口依赖、允许并行的工作树边界、可用测试环境和交付约束。
- 已确定的外部依赖和未决问题；缺少接口或范围决定时标明阻塞，不自行替换架构方案。

## 必需交付内容

### Task 清单

为每项任务写明目标、包含与排除内容、受影响接口或文件区域、预期交付及完成条件，避免一项任务承担互不相关的多个目标。

### 依赖 DAG

给出稳定任务 key、前置任务和依赖产物；解释依赖原因，确认无环、无悬空引用，不能通过互相等待掩盖边界不清。

### 验收责任

列出 AC-* 到负责 Task 的映射及所依赖的其他任务；所有验收必须有负责人，重复覆盖应说明协作关系。

### 独立测试配方

为每项 Task 提供自身 TestRecipe、测试文件、执行方式、环境与断言目标，说明真实 Red、Green、verify 在何处取得。

### 汇合与 Feature 验证

区分 Task 局部通过和 Feature 完整通过，列出跨任务接口、共享状态、用户流程及最终汇合验证要求。

### 风险与顺序

指出共享文件冲突、外部依赖、关键路径和需要先做的验证；给出失败返工的边界与对下游任务的影响。

### 执行顺序

1. 按交付结果划分任务，先确定接口与验收责任，再规划并行关系；不要按角色名称或文件数量机械拆分。
2. 逐项走查依赖输入能否由上游实际提供，独立工作树能否完成本任务，测试配方是否与设计接口一致。
3. 检查 AC 覆盖矩阵和依赖 DAG，处理遗漏、循环与共享写入冲突；必要时回到设计澄清。
4. 依据需求、设计的确切输入引用提交当前端口所声明的任务集合，字段以当前交付 Schema 为准；后续平台工具建立真实 Task。

## 内容与一致性检查

- 任务边界不重复拥有同一业务状态，验收有明确责任且不遗漏。
- 每项 Task 能在其依赖满足后独立完成测试及交付；不要求其他无关 Task 或 Feature 最终产物提前存在。
- TestRecipe、文件路径和导出接口真实可执行，环境准备与断言失败有区分。
- 任务、依赖、范围和汇合策略与已采纳设计一致，新增需求或架构改变有明确修订入口。

## 完成与拒绝标准

任务清单、无环依赖、验收映射及逐项测试配方完整且一致时才可提交规划交付。存在循环、任务无法独立验收或缺少关键接口时应拒绝并定位具体任务与依赖。

## 工具与证据

保留需求/设计修订、任务 key、依赖图和覆盖矩阵；计划与配方只是未来执行约定，不把计划中的测试写成已执行事实。 自动规则只能核对当前配置声明的有限事实，不能替代上述内容评审。
