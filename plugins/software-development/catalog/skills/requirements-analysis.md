# Requirements Analysis

## 从原始请求建立需求

读完冻结请求和已确认材料，整理现状、用户目标和可观察结果。先解决会改变范围或验收的歧义。方案和技术选型交给后续设计；用户已经指定的技术约束和例子纳入需求。没有阻断问题时直接成文。

## 使需求可验收

按照 PRD Specification 的六个标题组织正文。每个 AC 对应一项可判定行为，写明前置条件、触发动作、预期结果及验证方式。把用户的原始例子集中保留在相关验收条目中，明确错误、空状态和恢复后的结果。交付路径和现有流程条件集中放在范围或约束章节，后续任务沿 AC 引用。

## 提交前核对

走查主要场景及有效的异常场景，确认目标、范围与 AC 的一致性。将已核实事实、假设和待决定事项清楚区分。用 `source_ref` 引用冻结依据，并按当前端口提交可供独立评审的版本。
