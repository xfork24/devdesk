# 后台阶段与跨项目调度

Host 让持久化的待执行操作得到处理，同时避免一个项目长期占住全部运行容量。调度入口是 [workspace.rs](../../../crates/host/src/workspace.rs) 的 `Workspace::tick`。

## 一轮调度做什么

先收集已结束的后台任务，再按需要处理目录摘要、经验索引和配置同步等维护。随后读取各项目的 scheduling hints，计算运行数量和可用容量，安排工作流、会话、工具及控制器阶段。

这些阶段调用 core 提供的应用方法，不能直接替步骤写 completed。外部执行完成后仍要经过原操作结果的接纳。

## Background 的作用

[background.rs](../../../crates/host/src/background.rs) 管理唤醒、阶段执行、冲突处理和停止。重点符号是 `spawn`、`poll`、`stage_due`、`stage_finished` 和 `stop_and_drain`。

阶段记录和通知用于减少空转。它们不能替代数据库中的执行资格；准备好一个后台闭包后，真正执行时仍须核对原操作是否有效。

## 公平性与未知状态

项目遍历和分页游标帮助避免未解决的工作始终占据队首。如果某项目的运行数量读取失败，调度不能把未知数量当作零再多派任务；代码保留相应容量，同时尽量让其他可推进阶段继续。

显示读取与后台维护分开。打开页面不应该触发全目录同步，后台状态变化再通过事件使页面查询失效。

## 停机与验证

停止信号阻止新阶段进入，已经运行的阶段需要收集和核对。`stop_and_drain` 处理后台任务；worker 的实际停止由 core 和适配器继续验证。

workspace.rs 包含单项目异常不阻塞其他项目的回归；[workflow_live.rs](../../../crates/host/src/workflow_live.rs) 和性能相关模块覆盖阶段及读取行为。局部调度测试通过不等于 100 活跃前端容量目标已通过，范围见[质量说明](../../design/quality-and-limits.md)。
