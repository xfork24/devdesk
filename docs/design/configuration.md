# 配置如何成为一次执行

配置将“这个人负责什么”“使用什么程序”“本次要做什么”分开。Host 启动执行时把这些选择组合起来，并保存当时采用的版本，供后续读取和恢复。

## 各类配置的作用

| 配置 | 回答的问题 |
|---|---|
| Role | Agent 承担什么职责？ |
| Capability | 使用什么 Model、Harness、工具和技能？ |
| Agent | 哪个 Role 与哪个 Capability 组合？ |
| Model / ModelProvider | 使用哪个模型、服务端协议和连接信息？ |
| Harness | 容器内运行什么模型程序，怎样安装和启动？ |
| Sandbox | 使用什么容器基础环境和系统依赖？ |
| Skill | 做这类工作时采用什么方法和材料？ |
| Workflow / Step | 任务顺序、依赖、输入输出及执行方式是什么？ |
| Delivery / Spec | 输出结构、来源及内容需要满足什么条件？ |
| Standard | 本次工程采用哪一组固定规范及其依赖？ |
| Profile / Binding | 权限规则是什么，应用到哪个 Harness 或 Sandbox？ |

例如，“需求分析师”是 Role；“通过 Codex 使用某模型并能读取工作流输出”属于 Capability；“生成本项目的 PRD”由 Step 给出。更换角色名称不改变步骤执行器。

## 从编辑到运行

1. 用户编辑配置草稿。目录和模型候选查询只帮助填写草稿，不直接改变执行。
2. 保存时验证结构、类型允许的引用及依赖，形成新的不可变源修订。
3. 发布和采用决定项目或组合引用哪一版。新版本存在，不等于所有引用自动更新。
4. 启动工作项或会话时，core 解析引用，检查依赖，编译工作流和任务输入。
5. 执行记录保存所选配置、规范、权限和运行资源。后续恢复继续使用这些选择。

文档中把第 5 步称为“冻结”：保存这次执行的确定版本。它不意味着全局配置从此禁止编辑。

## 配置存放在哪里

[核心 manifest](../../kernel/core/manifest.json) 管理 Host 自带的配置，[软件开发 manifest](../../plugins/software-development/catalog/manifest.json) 管理领域 ZIP 的配置。两种目录分别发布。领域激活后，项目建立前即可在配置目录读取包内定义。项目绑定决定哪些项目配置可见。

基础组件页可查看模型、运行时和工具。领域项目提供与自身范围匹配的编辑器及查询。运行时从 SQLite 的 `source_definitions` 和已保存的绑定解析所需视图。需要恢复的工作项继续使用当时冻结的配置与包摘要。

停用 Model 等源定义、删除接入或预览模板重置时，Host 从各项目的只读配置目录核对引用或计算预览。项目仍通过 Capability、Agent 或其他配置间接使用该定义时，停用会被拒绝。停用保留原修订，供已冻结的执行读取。完整重置只重写依赖配置源的历史正文和受影响的活动工作流。已有会话引用的 Agent 修订及其依赖保留在历史目录中。

完整重置先提交全局目录，再更新项目与全局讨论目录。项目同步期间，查询仍可读取其上一次完整提交的目录；项目提交后，查询切换到新代次。

重置准备读取配置、重建历史正文所需的事实以及可能包含源引用的记录。同一 SQLite 快照内重复引用的正文可复用已核验的解码结果。页面在操作进行时显示状态，响应超时后可使用原命令核对结果。

原始配置格式、根引用与依赖检查见[格式参考](reference/contracts.md)。加载和编译见 [core 配置手册](../crates/devdesk-core/configuration-and-catalog.md)。

## 哪些变化需要新的执行

修改 Model、Capability、Agent 或默认选择，不会替换既有会话的模型连接。凭据更新也产生新的不透明引用；技术重试保留原引用，不能悄悄换用最新密钥。

权限切换需要按照运行边界建立后继绑定或会话；仍在运行的进程不能只修改数据库显示就被认为已经采用新权限。运行计划变化则走预览、停止相关执行、应用变化的专门流程，见[恢复与变更](data-and-recovery.md)。

## 为什么这样设计

如果执行总是追随“最新配置”，重试可能用另一套模型、权限或交付规则，难以解释前后差异。固定版本让一次执行可追溯，代价是更新后必须明确采用新组合。界面应展示引用关系，帮助用户找出仍使用旧版的对象。
