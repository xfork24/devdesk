# 15 分钟净流程的组件拆解与优化方向

基于[成功完整回归基准](workflow-benchmark-2026-11-20.md)的同一轮历史数据，继续拆解净耗时 **902.380 秒**。这次分析没有重跑流程或重采样原有 API 基准；原基准 JSON 保持不变，派生数据保存于[组件时间账本](workflow-cost-breakdown-2026-11-20.json)，其中记录原基准文件 SHA-256。

## 三类组件的互斥账本

| 组件 | 净墙钟分配 | 占比 | 包含内容 |
|---|---:|---:|---|
| Agent 非工具服务周期 | **720.481 秒（12:00.481）** | **79.84%** | 主机观察到的原生轮次服务周期，扣除工具及外部等待；含模型服务、生成、传输和主机接收延迟 |
| 业务工具 | **94.418 秒（01:34.418）** | **10.46%** | Git、测试、Shell、快照与其他平台业务处理 |
| workflow 侧编排与运行时 | **87.481 秒（01:27.481）** | **9.69%** | 运行时准备/回收、workflow 控制接口、工具请求回传及其余内部衔接 |
| 合计 | **902.380 秒** | **100%** | 同一秒只分配一次；百分比显示舍入 |

这不是纯模型推理、纯工具 CPU、纯调度器 CPU 的采样。Agent 服务周期取主机收到 admission 至 terminal 的记录，工具跨度取主机收到开始及完成的记录。主机轮询接收延迟可能落在这些服务周期内；后台数据库操作、锁等待与 CPU 消耗目前没有完整独立 span。

组件账本的分配优先级为外部排除 → 工具 → Agent 服务周期 → 原生 turn 生命周期 → 其他内部时间。再把工具中的 workflow 控制接口与请求回传归入 workflow 侧，得到上表。并发时间按此明确规则分配，不是经证明的因果关键路径，也不是删掉某类时间后必然能获得的加速量。

Agent 部分进一步分为生产者 Agent **525.728 秒**、项目经理 **194.753 秒**。并发时生产者优先于经理分配，同一秒仍只计一次。实际共 10 个生产者 turn、21 个经理 turn。

## 步骤间、审批准备和收尾具体耗在哪里

下表是按流程阶段观察同一份组件切片，不能再与上面的组件总量相加。审批请求创建后的外部响应、以及主机休眠仍按原基准排除。

| 阶段窗口 | 净跨度秒 | Agent 服务秒 | 业务工具秒 | workflow 侧秒 |
|---|---:|---:|---:|---:|
| 31 段常规步骤间隔 | 13.042 | 7.404 | 0.000 | 5.638 |
| 四次审批准备 | 76.831 | 65.815 | 0.000 | 11.016 |
| 初始创建至首次派发 | 17.594 | 11.178 | 0.000 | 6.416 |
| 创建 Task 至 Task 首步启动 | 34.327 | 27.132 | 0.000 | 7.195 |
| Task 最后生产者结束至显式完成 | 21.963 | 16.584 | 0.000 | 5.379 |
| Feature 最后生产者结束至显式完成 | 17.147 | 13.682 | 0.000 | 3.465 |
| 根完成至经理关闭及 worker 静止 | 5.598 | 4.196 | 0.000 | 1.402 |

常规步骤间隔取同一层“上一行接纳 → 下一行开始”，不把 Task 创建及最终关闭窗口混进去。最大的两段分别是 Task `source_publish → target` 1.401 秒、`workspace → tests` 1.378 秒；其余均小于 1 秒。常规间隔中 workflow 侧只有 5.638 秒，约占整个净流程 **0.62%**，因此提高轮询频率的端到端收益空间有限。

审批准备逐次拆解如下：

| 审批 | 净跨度秒 | Agent 服务秒 | workflow 侧秒 |
|---|---:|---:|---:|
| 需求 | 20.134 | 17.850 | 2.284 |
| 设计 | 15.744 | 12.989 | 2.755 |
| 任务规划 | 18.340 | 15.840 | 2.500 |
| 最终交付 | 22.613 | 19.136 | 3.477 |
| 合计 | **76.831** | **65.815** | **11.016** |

准备阶段的约 **85.7%** 是经理的非工具服务周期。最后三个收尾窗口合计 **44.708 秒**，其中 Agent 服务 **34.462 秒**、workflow 侧 **10.246 秒**。把这些阶段整段称为“调度器开销”会掩盖真正的优化位置。

## 可以优先优化的地方

### 1. 让确定性的审批材料准备由平台完成

当独立评审已通过、所需原始产物和候选版本齐备时，平台可按冻结配置生成结构化审批包及请求，直接绑定 execution、input digest、outputs、候选版本与当前控制版本。经理处理需要判断、驳回或补充材料的情况，用户继续作真实签核。

本轮四个准备窗口共 76.831 秒，其中经理服务 65.815 秒。这是值得优先替换的工作窗口，不是已验证可直接消除的收益。实现需要验证请求幂等、并发产物变化、失效请求和 Human 权限，随后用相同工作流实测。

### 2. 合并只剩登记工作的关闭回合

Task 和 Feature 的最后一步已接纳、全部规则通过、子流程及原生 worker 均达到终态后，配置可以明确允许平台生成完成记录。需要经理判断的关闭则提供一次结构化终态快照，使 inspect、complete 与通知在同一轮完成。

当前两个显式关闭与末尾经理结算共 44.708 秒，多数耗在经理服务。自动关闭必须由明确的冻结策略授权，核对全部子流程、实际合入/同步、Human 签核和 stop proof。完成事实与面向用户的自然语言总结可以独立计时，前者仍以真正满足交付条件的持久化记录为准。

### 3. 减少没有新决定的经理唤醒

本轮 21 个经理 turn 中，有 **7 轮仅调用 `workflow.controller.wait`**。这些轮次的原始服务跨度累计 101.044 秒，但不少发生在外部审批等待或与生产者、工具并行。扣除这些重叠后，它们独占的经理非工具时间为 **22.370 秒**，不能把 101 秒直接当作可节省的端到端时间。

可继续收敛由同一经理已处理动作产生的通知，以及没有改变当前可执行操作的状态通知。保留原始审计事件，按当前请求与控制版本合并投递；Human 回复、失败、需要输入、子流程终态与超时仍及时唤醒。本轮只有 wait 的清单、每轮方法和独占时间均在派生 JSON 中，后续可逐轮验证合并是否正确。

### 4. 缩短真实运行时准备和停止路径

31 个原生 turn 的准备时长累计 77.523 秒、terminal 后收尾累计 30.109 秒；它们与其他活动重叠，因此端到端净分配为 51.578 秒。`conversation_open_intent → open observation` 的累计跨度为 71.868 秒，但尚未把 Docker 调用、preflight、provider 建连分别独立计时。

可在每次实际 worker 启动屏障内执行 UID、空间及可执行性探测，以减少额外探测容器的创建/销毁，保留每次探测及失败时的明确结果。也可评估同一授权 epoch 下经理只读会话的复用，同时保持逐轮权限绑定、停止证明、writer 撤销和独立测试隔离。先增加 Host 侧启动/探测/派发/停止 span，再选择能保持这些约束的实现。

### 5. 常规步骤间延迟作为后续小项

31 段间隔中的纯 workflow 侧占比只有 0.62%。可以用同一事务批量提交就绪状态、事件到达后立即唤醒、避免重复恢复聚合对象来减少这部分，但应先处理上述经理回合和运行时路径。Git 净分配约 64.655 秒也值得细分远端发布、PR API、同步与本地处理；这轮无法据此判定远端服务或本地 Git 哪一项是主要原因。

## 时钟、并发与测量限制

休眠后的经理 turn `3a8c9b5a-734b-4f51-b011-885436fac4e3` 的原生 `turn/started.emittedAtMs` 为 `1795136993004`，却在主机 turn 开始 `1795137889113` 之前 **896.109 秒**。其后原生时间发生同步，部分工具时间也处在不同的偏移阶段。直接拼接这些时钟会把工具画进已经排除的休眠区间。

因此，本分析对全部 31 个服务周期及 88 个原生工具（65 个动态平台工具、23 条 Shell 命令）统一使用主机保存的 `provider_poll_observation.created_at`。48 个平台处理 span 则保留其本来就使用主机时钟的 started/finished。主机同一批次收到开始与结束时，该工具观测跨度可能为零；JSON 单独保存生产者上报的持续时间作诊断，不把它与主机绝对时间混拼。

这些是主机可观察到的时间归属，并非模型服务端纯推理时间；派生 JSON 保留每个切片、每个阶段窗口、全部原生服务边界和异常时钟证据。原有 902.380 秒净总量及外部排除口径完全不变。各项优化影响可能重叠，建议用同一输入、同一测试与审批策略分别实测，而不把建议中的窗口长度相加作为收益承诺。
