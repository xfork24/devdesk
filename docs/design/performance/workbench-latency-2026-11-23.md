# DevDesk 工作台延迟评估

## 结论

本轮最慢的操作来自三条代码路径。上下文查询在 SQLite 内反复关联步骤、会话和历史记录。模板重置在 Rust 适配器里扫描候选记录、读取外部正文并判断哪些历史事实需要封存。项目经理的驱动查询还经过配置同步入口，重置期间会等项目目录应用新一代定义。它们有各自的修复点。

现阶段建议保留 SQLite，优先把高频列表从通用 JSON 记录的临时关联迁到有索引的读投影，并让配置重置和页面查询保持独立。等写入争用在容量测试中成为主要瓶颈，或者产品需要多个 Host 同时访问同一数据集时，再评估 PostgreSQL。

## 测量口径

- 同一份本地真实数据集的隔离副本。Apple M1、16 GB、macOS 26.7.3，Release Host，经环回 HTTP 访问。基线版本为 `9116d588`。项目库约 229 MB，包含 53,926 条治理记录、371 个轮次及 10,534 个已归档正文索引项。
- HTTP 表每个场景先单独记录该请求形状的第一次读取，再顺序采集样本。通常为 30 次，上下文为 5 次。P95 使用最近秩计算。Host 和操作系统缓存保持启用，短间隔重复读取可能命中 Host 的 100 ms 显示缓存。
- 浏览器表用 Chromium 在同一个已启动的浏览器和 Host 中反复打开页面路由，从导航开始计到指定主要 RPC 正文可读，再等待两个动画帧。它包含页面引导和主要请求链。该口径没有等待页面所有后台请求或外部资源。样本数较少，使用 P50 和最慢值。
- 主要执行页使用有真实历史、已完成且缺失旧目录定义的 Feature。并发探针同时打开多个上下文读请求、运行重置、读取工作区与驱动摘要，并连接浏览器使用的 SSE 尾读接口。
- 报告覆盖本地页面与配置重置。GitHub、模型服务、Keychain、Docker、真实流程执行和网络部署的耗时取决于另外的边界，本轮没有计入。

## 瓶颈归因

### 上下文与执行列表

旧 SQL 先按项目枚举会话，再为每个候选组合判断是否属于某次执行。查询计划出现项目级扫描、相关子查询和临时去重。在同一数据库上只执行 SQL，旧版约 15.65 秒。新版先定位所选流程、步骤和历史轮次，再从执行 ID 找直接会话及配置会话，并按主键关联会话。新版约 87 毫秒，返回的 12 行逐项一致。这个数量级的差异在 Rust 反序列化或浏览器渲染之前已经出现。

材料与执行记录仍要从治理 JSON 找到工作流、执行轮次和产物。新路径缩小了查询范围。材料目录此前因内连接已被重置清除的 Delivery 定义而返回零条，现从本次执行的冻结计划恢复已保存的名称和格式。Workflow 状态也在确切定义缺失时读取该实例的冻结计划。材料详情仍按项目、实例、计划和执行归属验证，再读取原有正文。

### 项目经理

进度、管理摘要和驱动摘要的普通查询都很轻。真正较重的是完整协作读，它为决策、材料和当前资格补齐事实。一例基线 `query.orchestration` 的 HTTP P50 约 272 毫秒。重置期间，旧的 `query.workflow_driver` 读取还会进入配置同步路径，具备重复准备同一个项目的条件。直接读取项目的已提交状态后，页面可继续查询。前端已有工作流入口时直接使用它，驱动摘要和协作结果可以展示后，才补读需要确切内容的人审与接纳信息。

### 模板定义重置

运行时使用各数据库已经提交的配置及实例冻结计划。重置以 Host 内嵌的出厂配置为输入，源码位于 `configurations/`。完整重置要先替换全局默认目录，再使全局讨论库及各项目接受同一代目录。它还要保住被历史会话引用的 Agent 及依赖、仍可用的项目绑定和冻结证据。基线的一次成功重置是 26.58 秒，准备耗时 26.18 秒，三个库的 SQLite 写事务合计 0.086 秒。准备包含候选 SQL、外部正文读取和校验、JSON 解码以及证据封存，几个嵌套分段不能相加。

旧实现把许多仅作事实保存的外部正文解包，再检查它们能否依赖配置。现在先查实际由源编解码器遍历的字段，仅对相关记录完整解包和封存，并原地处理字面值。重置准备使用独立读连接，仍受 Host 总连接预算限制。同一项目的同步只准备一次。保留自定义定义的更新、完全重置、命令回放和历史会话仍经过原有版本校验。

工作区约 2 秒的 `storage_busy` 与连接池借用截止时间对应。旧版在并发上下文请求下，四条前台读连接都可被长期占用。此时事件尾读和工作区读也在等待连接。SQLite WAL 允许同一台机器上的读写重叠，但每个 WAL 同时只有一个写者。这里先解决了长读与重置准备耗尽前台连接，并保留真实忙碌错误的日志。 [SQLite WAL 文档](https://sqlite.org/wal.html#concurrency)

## 优化路线

| 优先级 | 建议 | 验收 |
| --- | --- | --- |
| P0 | 给页面首屏、主要 RPC、连接借用、SQL、正文读取和序列化建立分段指标。记录每个版本在同一数据集上的结果。 | 使用至少 30 次样本记录 P50、P95、最大值和错误数。分别采集冷启动、热读和并发重置。 |
| P1 | 为上下文、材料、执行记录维护有索引的读投影。行内保留 Project、Feature、实例、计划、执行、轮次、会话和产物 ID，以及展示所需的短字段。使用现有事务维护投影，并支持按事件游标校验和重建。 | 1 倍、10 倍、100 倍历史下按作用域翻页。对比原始记录、子流程、重试轮次、跨项目拒绝和历史材料。建议把单个热页面关键 RPC 的 P95 目标设为 150 毫秒。 |
| P1 | 把项目经理首屏固定在轻量状态与阻塞摘要。仅对当前待操作证据和用户展开的历史读取确切内容。批量取得一页历史决策所需的已签记录和输出摘要。 | 检查待审批、过期审批、接纳、子流程和原始材料定位。建议完整加载 P95 目标为 300 毫秒。 |
| P1 | 为新写入的历史记录或正文持久化可校验的源依赖索引。按将被替换的确切修订选候选，用可恢复的逐项目作业发布重置代次。保留旧数据的扫描和索引构建路径。 | 首次与后续重置都要覆盖断电恢复、重复命令、并发修改和正文一致性。建议把两项目样本的重置 P95 目标设为 3 秒，并把重置期间前台读 P95 控制在 150 毫秒。 |
| P2 | 按项目和查询设置读预算，监控连接池借用时间、短写事务和 WAL 检查点进度。用 1、4、16 并发页面加真实 Run 写入验证容量，再决定在哪一层限流。 | 记录前台读超时数、写事务等待、WAL 体积和回放恢复情况。用实测区分 CPU、I/O、连接借用与事务写锁。 |
| P2 | 按页面拆分 Web 入口代码。在项目管理、角色与代理等页面按需加载目录正文，复用目录索引请求。当前 Vite 主 JS 约 625.5 kB，gzip 后约 190.8 kB。 | 保持现有路由、返回、精确版本选择和无 Feature 的空态。实测冷导航、脚本解析和渲染，再决定拆分粒度。 |

## 存储选型

| 方案 | 适用条件 | 代价 |
| --- | --- | --- |
| SQLite 加读投影 | 单机 Host、按项目分库。本轮最慢的上下文查询和重置准备在此方案内已经获得明显改善。 | 每库只能同时有一个写者。需要管理长读、检查点、读投影重建和跨库发布恢复。 |
| 独立本地读侧数据库 | 读投影增长到影响主库或需要可丢弃的索引文件。可先使用第二个 SQLite 文件，主库事务保存事件，读侧按游标追赶。 | 要给 UI 标明游标和滞后状态。审批、重试与权限检查仍需回到主库验证确切版本。 |
| PostgreSQL | 多 Host 或远程服务共享状态，或经过索引与短事务改造后仍测到稳定的同库多写竞争。 | 增加服务运维、备份、迁移与连接开销。还要迁移项目隔离、版本见证、命令回放和正文目录协议。SQL 扫描与 Rust 正文重建仍需各自优化。 |

PostgreSQL 的 MVCC 提供语句快照及更细的写并发控制。迁移决策应以业务确实需要共享数据库，或在目标负载下有明确的事务争用证据为前提。 [PostgreSQL MVCC 文档](https://www.postgresql.org/docs/current/mvcc-intro.html)

## 修复验证

真实数据副本上确认两项历史 Feature 均有材料，选中的原正文可打开。浏览器回归覆盖 Feature 清空、迟到响应、材料深链接、经理审批及现有项目级工作流，共 37 项通过。另有 107 项适配器单测、7 项 Host 模板测试和独立 Release 二进制重置验收通过。
