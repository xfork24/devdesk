# 权限与凭据

DevDesk 同时管理用户、Agent 和外部进程。权限设计要回答两个问题：谁有资格请求某个动作，以及执行这个动作的进程实际上能访问什么。

## 信任边界

浏览器经 Host 的认证和来源检查进入应用。Agent 经绑定到会话和 Turn 的工具连接进入应用。模型输出和外部服务返回值都作为输入处理，不能直接授予权限或改变业务终态。

| 边界 | 限制方式 |
|---|---|
| 浏览器 → Host | 连接认证、Host/Origin 校验、明确项目作用域 |
| Agent → 平台工具 | 已发布工具、当前能力、会话/轮次身份、操作权限 |
| Harness 进程 → 文件和命令 | Harness 权限后端和原生工具规则 |
| 容器 → 宿主及网络 | Sandbox 挂载、网络、资源及平台安全策略 |
| Host → 系统凭据库 | 平台凭据接口；macOS 使用验证过的固定签名助手 |
| 自动流程 → 人工决定 | Human 来源校验，Agent 不可代签 |

## 权限配置怎样落地

Profile 是权限规则的来源，Binding 选择把哪份 Profile 应用到哪个 Harness 或 Sandbox。步骤显式选择可以替换同层默认绑定，实际操作仍需同时满足两层限制。

core 保存本次采用的权限选择，adapters 将其转换成实际执行参数和后端策略。不能实现的规则会阻止启动，不采用“尽量限制”的方式假装成功。

Docker 隔离不等于默认只读或默认禁网；实际权限由所选 Profile 决定。模型请求通常需要网络，测试容器也有自己独立的授权范围。Agent 不持有 Docker daemon socket。

当前默认全权限配置把整个 Harness 容器作为信任范围，同容器的工具可能访问该运行的模型凭据和状态。宿主凭据库、其他项目及未挂载目录仍在容器外。应用层权限选择不会授予 Keychain 或 Secret Service 的系统访问权。

权限变更要落实到后继运行或经过明确切换流程。数据库中显示新 Profile，不足以证明旧进程已经受到新限制。

## 凭据如何保存和使用

API key 和工具 token 存入系统凭据库，配置中只保存不透明引用。Host 为授权的运行读取相应凭据，按驱动要求注入受控的运行环境，不把它作为普通项目材料传给模型。

macOS 由证书签名的 `devdesk-host` 直接访问钥匙串。Host 验证自身签名并检查凭据的服务名和账户范围。后台读写关闭弹窗，显式授权期间暂停其他钥匙串调用。

源码开发签名、运行副本和旧版授权见[Host 签名与钥匙串](../crates/devdesk-adapters/signing-and-keychain.md)。

Linux 使用 Secret Service，要求可用且解锁的 D-Bus 会话。Codex OAuth 使用单独的数据集私有认证文件。不同认证方式的存储边界不能混为一谈。

更新密钥产生新引用，既有运行仍绑定原引用。如果原凭据不可读，运行应报告失败；不能用新密钥替换原执行而不留下身份变化。

## 远程连接与外部工具

非 loopback 监听要求配置连接密钥；反向代理的公开地址需与 Host/Origin 校验匹配。连接密钥不进入 URL。详细启动参数见[运行指南](run-binary.md)。

HTTP/MCP 工具还要检查目标地址、认证注入、重定向和项目绑定。发现一个工具并不等于任何项目都获准调用它。外部写入失败时也不能假定远端回滚，未知效果需要核对。

实现与测试见[凭据和权限后端](../crates/devdesk-adapters/credentials-and-permissions.md)和[权限资产](../../permissions/README.md)。
