# S6：规范校验与全链工程验收

状态：待实施。依赖：S1–S5；规范检查原语可在 S2 后先做。[总体路线图](../PLAN.md)

## 1. 目标

把可由机器判定的规范交给明确原语执行，保持模型/人类语义判断的真实边界；用完整工程场景证明配置独立演进、资源可选择、双驱动与项目经理管理实际成立。

不以“模型填齐 evidence”代表文档质量，也不以注册一个接口或单元测试通过代表真实运行支持。

## 2. Spec 检查模型

在现有 Spec 上增加有类型的可执行检查描述，优先复用 JSON content_schema、端口、来源和规则能力，不在 Delivery 与 Spec 中再造两套同义 DSL。Delivery 表达内容类型/结构约束及 Spec 引用；Spec 表达可复用检查项，执行时冻结完整引用和检查器身份。

检查按能力区分：

- 纯结构检查：必需字段/章节、长度范围、JSON Schema、指定结构引用的合法性。规则内容在配置中，不在 Rust 写死“PRD 必须有 AC-”或默认步骤数量。
- 可定位证据：目标产物引用 + 内容摘要 + JSON pointer/行或字符范围；核对范围及内容确实来自该版本，不能靠任意非空 evidence 字符串通过。跨产物证据必须在授权/冻结输入范围内。
- 工具事实检查：真实测试、Git、发布、隔离和独立性等由共同接纳原语判断，外部调用经 port 和意图/回执，不在 domain 纯校验里做 I/O。
- 模型/人类判断：明确保存判断者身份、输入/输出引用、理由；与机器事实分别记录，不互相替代。

纯算法在 domain 或无环境依赖的 core 模块，外部检查执行走 core 用例/adapter port。未知检查原语拒绝；长度、深度、正则/Schema 复杂度等有界。优先选择有界执行机制，不承诺无法实现的随意超时中断。

提供共用 validate/lint 用例和工具：草稿自检、UI 预览、提交及接纳使用同一检查器/数据依赖。预览不是最终接纳证明；接纳必须核对同一内容摘要及实际输入事实。

## 3. 测试层次与责任

| 层次 | 覆盖内容 | 不能替代的证明 |
|---|---|---|
| domain/core 纯测试 | 原语、图、变更集、选择、调度和接纳；自建最小流程/资源 | 不证明真实 Docker、SDK 或权限执行 |
| adapter 集成测试 | SQL/文件 round trip、原生协议、资源准备与能力验证 | fixture/模拟协议不代表供应商实测 |
| Host/HTTP 与浏览器 | 主体注入、跨项目/跨库、UI 历史选择、经理工作台 | 点击成功不代表业务/外部世界成功 |
| 真实工程 | Linux 容器、真实 Harness、Git/测试/发布回执、人工门禁 | 不自动代表 Ubuntu/macOS 宿主全平台通过 |
| 独立发布包 | 无源码目录运行，同一二进制导入/选择新配置和兼容资源 | 重新编译后成功不能证明数据独立演进 |

出厂配置专门做 manifest/正文归属/引用/组合自洽与产品流程验收；通用引擎测试用自建夹具，不依赖 builtin ID、特定修订号和整个默认流程结构。不要因解耦测试而删除真实业务回归。

## 4. 必须保留的验收矩阵

| 编号 | 情景 | 成功标准 |
|---|---|---|
| A01 分层 | 独立构建 core/domain，审查外层业务写入 | 无反向依赖/资产构建绑定；Host/Adapter 无第二套业务判定 |
| A02 配置演进 | 同一包并存三修订，改 Skill/Spec/Delivery/Workflow，选择中间修订 | 无 Rust 改动、无全模板重置；旧执行冻结值和历史产物不变 |
| A03 组合与原子性 | 多对象相互依赖创建、错误类型/Scope/循环、并发修改 | 统一诊断；非法整体拒绝；不出现半发布、失效引用或丢失更新 |
| A04 运行资源 | 两份真实兼容同协议资源，改标签、改真实内容、缺能力 | 相同二进制可选两份；标签无关；内容/权限/能力不符准确拒绝 |
| A05 Rust 全自动 | 自建图和默认 Feature/Task，含 Agent/Tool/Control/子流程 | 除配置要求的人工输入外无需经理模型调度；依赖/接纳/完成正确 |
| A06 Agent 调度 | 同一工程目标由配置好的经理 Harness 推进 | 真实工具调用/回执，遵守与 Rust 相同门禁和终态规则 |
| A07 控制切换与恢复 | Rust↔Agent、人工接管、暂停/取消、重启、迟到回包 | 唯一有效租约；不重复外部效果；未知结果进入核对 |
| A08 经理配置创作 | S5 五个对话场景，含未来采用和运行中采用 | 每项有事实查询、预演、合法应用和结果验证；非口头宣称 |
| A09 经理知情与范围 | 多 Feature/Task、大产物、分页历史、无当前根实例 | 能续读并引用全项目业务事实；无跨项目越界、无秘密材料泄漏 |
| A10 规范检查 | 违规文档/悬空证据/错误内容摘要，草稿与接纳检查 | 同一检查器给相同结构结论；模型不能自造检查事实 |
| A11 跨库故障 | 准备、复制、目标切换、回执各节点中断 | 重启按操作核对恢复；读者不采用未提交候选 |
| A12 独立包 | 无 resources 源目录、无开发工具链运行，再导入配置和资源 | 初始化、选择、调度、查询与经理管理都可用；记录包摘要/命令和结果 |

故障注入至少包括意图持久化后进程退出、外部效果完成但接纳前退出、资源内容改变、当前计划/配置 head 改变、旧 worker/工具回执到达。场景需要有实际断言，不是只列一张通过清单。

## 5. 证据与可重现性

记录程序包摘要、源/计划/策略/Spec/Agent 修订、实际资源/驱动/权限资产摘要、输入/产物/回执引用、命令与恢复路径；敏感内容不写入报告。把“重放命令返回同结果”“重建环境”“复核证据”“重新运行模型”分开，模型输出与外部世界变化不承诺确定性。

本阶段形成可核对的执行来源清单和报告；完整离线证据包产品/旧库浏览器可以另立计划，不借验收之名扩成通用归档平台。原始日志和截图写临时目录，计划目录仅新增 Markdown EXECUTION/验收说明，遵守仓库约定。

## 6. 工作项与收口

| 工作项 | 交付 |
|---|---|
| V01 盘点已有检查并定义最小新增原语 | 复用关系、检查/evidence 类型、结构与复杂度限制 |
| V02 共用 lint/validate/accept 检查链 | domain/core/工具/UI 结果一致；实际工具事实仍走 ports |
| V03 默认 Spec/Delivery 配置改进 | 少量代表性规范先校准，再覆盖需要机器校验的默认对象，不固定数量 |
| V04 整理语义夹具与出厂配置测试 | 分清原语测试、配置自洽、产品流程与真实供应商证据 |
| V05 执行 A01–A12 | 按层报告通过/失败/未运行；失败修复后只补跑必要范围 |
| V06 文档与最终核对 | 当前架构/协议/源配置/运行时/编排/经理使用说明、EXECUTION |

正式收口时跑适当的 workspace Rust、HTTP、Web 构建及 debug/release 浏览器回归，再进行真实工程与独立包验证。任何尚未运行的平台/Harness 明确标记，不将 fixture 成功写成真实通过。

完成标准：A01–A12 的必要环境结果有可核对来源，用户四项要求均有实现落点和证据；若某项因外部条件未验收，保留明确未完成状态和后续工作，不以“其余测试全绿”宣告整条路线完成。
