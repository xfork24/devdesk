# S4：Rust 与 Agent 双调度，共用控制内核

状态：待实施。依赖：S1、S2；真实 Harness/资源接入使用 S3。[总体路线图](../PLAN.md)

## 1. 目标

Feature/Task 工作流明确选择 Rust 自动驱动或已配置 Harness 上的经理 Agent 驱动，两者调用同一套 dispatch/accept/complete/change/stop/reconcile 用例。现有手工控制继续作为明确授权的控制方式；已有 segment 是可复用的有界委托，不再承担完整自动模式的替代角色。

业务终态仍由 core 控制内核判断。驱动负责提出下一动作，不拥有独立的终态判定、证据规则或隐式权限。

## 2. 三个职责

| 职责 | 输入/输出 | 限制 |
|---|---|---|
| 执行与接纳内核（core） | 命令、冻结计划、事实 → 验证/状态变化/意图 | 唯一业务规则与终态权威 |
| Rust 驱动（core） | 一致性快照、就绪集合、策略 → 有界命令建议 | 不调用模型决定派发；不能跳过人工门禁、豁免或未知结果核对 |
| Agent 驱动（core 会话编排 + adapter Harness） | 项目/流程查询、唤醒 → 真实控制工具调用 | 受同一租约、策略、预算、冻结工具与身份约束 |

Host 只调度生命周期和调用 tick；外部 I/O 由 adapters 执行持久化意图，内核接纳结果。将“收到执行回执”和“驱动决定接纳步骤”分开。

## 3. 模式、策略和所有权

- 独立 `OrchestrationSelection` 选择 `rust | agent`，包含策略精确引用、Agent 修订/会话要求。放在项目默认/工作选择中，冻结至根实例；不要把模式耦合到某个默认 Workflow ID 或业务步骤名。
- 驱动策略表达并发上限、每轮动作上限、重试规则、等待/唤醒条件和必要授权，均为数据。平台只规定资源和算法的合理边界，不把默认并发固定到 Rust。
- 根实例有唯一控制租约，带持有者、epoch、有效期和控制版本；子流程继承或显式委托，不能被父子两个驱动重复派发。
- 模式切换：先撤销旧控制授权和待派发控制意图，阻止旧 epoch 接纳新调用；对在途控制调用持久化核对结果。保留正常运行的业务 worker，除非本次变更要求停止它。取得新租约后从已持久化事实恢复。不能将“切换驱动”默认实现成杀掉所有任务。
- 人工接管/暂停也受相同 CAS 与作用域约束；Agent 迟到回包、已撤销 segment 与旧 Rust tick 无法再改变当前计划。

## 4. Rust 自动驱动算法

1. 从当前计划和精确事实构建 ready/waiting/blocked 集合；依赖、输入、条件、执行槽位和权限由共同内核计算。
2. 对 queued 且就绪节点生成显式 dispatch 命令；并发按全局/项目/流程/资源约束求可用集合，顺序稳定，设置每轮动作上限。
3. 观察真实输出；按共同 completion/确认/来源规则决定是否提交 accept。人工确认未到、检查未通过或外部结果未知时保持等待/阻塞，留下原因。
4. 技术失败仅按配置的有界策略执行 retry；业务返工是否可自动执行由策略和所需原语决定。需人补充判断时进入明确 waiting 状态，不无限循环、不伪造成功。
5. 正确处理条件跳过、foreach 子实例展开、子流程接纳与 complete，再处理父调用和根 complete。Task 创建、代码候选/发布等仍由配置中的 Tool Step/原语完成；驱动不注入默认工程业务步骤。
6. 每条命令固定计划、epoch、预期控制版本、逻辑动作 ID 和参数指纹，先持久化后执行。进程重启时核对原意图，未知结果不盲目重发。

Rust 和 Agent 不必选择同样的执行顺序，也不要求模型输出逐字一致；它们必须遵守相同约束，产生可追溯的动作和有效终态。

## 5. 经理会话与事件

将现有 Controller 的唤醒、epoch、工具往返和快照逻辑迁入共同驱动框架。工具目录使用 S1 的命令注册及 S3 的实际能力，不另维护一套无关 whitelist。

有事件游标变化、到期计时器、待决输入或预算/租约动作才唤醒；摘要防抖是补充。不能只靠事件跳过到期预算/租约，不能把“需要续租”自动等价为“必须再问模型”。持久化事件/意图是事实源，进程通知只是减少轮询；重启及丢通知可按游标恢复。

经理即使不持有驱动租约仍可在其权限范围查询项目和创作配置；是否改变当前实例需获得对应控制授权。这样 Rust 自动模式下，人仍能和经理沟通，经理不会与 Rust 同时调度。

## 6. 工作项与验收

| 工作项 | 交付 | 必须验证 |
|---|---|---|
| O01 抽取共同控制用例和 ReadySet | core orchestration/configured_runtime | dispatch/accept/complete 对所有 Actor 用相同判据 |
| O02 模式、Driver 主体与租约 | domain orchestration、配置选择 | 全部身份来自可信入口；根/子流程控制唯一 |
| O03 Rust 自动驱动 | core 新驱动模块 | 无经理模型调用也能完成包含 Agent/Tool/Control/Workflow 的 Feature/Task |
| O04 Agent 驱动适配 | controllers、conversation runtime、ports | 原编排能力保留，实际能力不足的 Harness 拒绝 |
| O05 切换、接管和恢复 | 共同命令/意图/事件 | 各切换中断点、重复 tick、过期调用不重复外部效果 |
| O06 查询/UI 与诊断 | 选择表单、流程视图 | 可看模式、持有者、等待原因、动作来源、失败和核对状态 |
| O07 回归与文档 | workflow-orchestration.md、EXECUTION | 以下配对场景和实际流程证据完整 |

同一组自建流程分别验证 Rust/Agent：依赖分支、条件跳过、并发 foreach/子流程、人工确认、技术重试、业务失败、暂停/取消、未知结果核对、重启恢复。再跑当前默认工程流程，防止只支持简化测试图。

重点交错场景：Rust→Agent、Agent→Rust、人类接管；旧 Controller 原生工具回包、新驱动 tick、用户变更计划同时发生。保证单个有效业务动作、旧 epoch 被拒、已有成功回执不失效。空闲 tick 不产生无因模型轮次或无限状态写入。

本阶段不需要实现新的业务智能规划器；Rust 根据已配置图调度，Agent 可用 S5 工具创作新图，两者职责明确。
