## 2. 不可退让的工程约束

1. 按职责划分 `domain / core / adapters / host`。编译依赖允许外层引用内层：`host → adapters → core → domain`，也允许 host 直接引用 core/domain、adapters 直接引用 domain；禁止反向边。运行时 core 调用外部行为，只通过 core 定义的 port。调用方向不等于源码依赖方向。
2. domain 定义对象、不变量、状态规则和纯算法；core 组织用例、授权、编译与接纳；adapters 处理数据库、文件、进程、供应商协议和环境能力；host 负责协议接入、生命周期和装配。文件数和 crate 数不能作为职责正确的替代指标。
3. 已有原语能够表达的数据变化不要求修改或重编译 Rust。配置修订在运行时选择，引用在发布/采用时解析为精确 `identity:revision`，执行时冻结；不会自动跟随最新版本。
4. `schema_version`、渲染器版本、bundle 标签、外部程序版本不决定业务配置合法性。结构、类型、范围、引用、能力与业务规则必须验证。未知执行原语明确拒绝；真正新增原语仍需实现代码。
5. 摘要校验用于证明“所选内容与实际内容相同”，不能变成“只能选择当前二进制知道的唯一内容”。SQL 结构、JSON-RPC 格式和适配器实现身份属于内部/外部协议边界，不能据此限制兼容的源配置修订。
6. UI、Rust 自动驱动和项目经理调用同一用例与控制内核。业务事实来自存储和真实回执；任何驱动都不能自行设置成功、伪造测试、代签人工确认。
7. 配置的“编辑”产生后继修订，“删除”产生停用/移除选择的事实。历史被引用内容保留。对正在运行的实例生效必须显式预演、停止受影响执行、核对并建立新计划/会话。
8. 人工确认由配置的授权策略及真实业务门禁决定。不能把“Agent 不能冒充人类确认”扩大为“所有 Agent 配置修改必须再次找人批准”。已授权动作可直接执行。

顺序：`S1 → S2 → {S3, S4} → S5 → S6`。这里表示工程依赖，不要求由多个 agent 并行执行。每阶段分小批交付、先保持现有流程可用，再切换入口；不把两个新子系统同时合入作为最小交付单位。

阶段完成需要代码、适当回归、对应现行文档和新增 `EXECUTION.md`。不能仅按文件移动数量或接口存在判定。每阶段先验收后进入依赖它的阶段，失败时保持此前已验收能力。

## 5. 改造期间的数据与范围

- 本项目当前按未上线阶段处理，阶段验收使用独立新数据集；不以删除用户工作数据作为修复或验收步骤。
- 本路线不额外建设旧 SQL 基线在线兼容器、尽力投影或无边界迁移框架。若实施涉及已被要求保留的数据，另立明确转换计划：备份、离线转换、核对和回滚，不能以换个名称规避迁移责任。
- 存储 codec 调整不破坏同一受支持基线内已冻结源修订和执行记录；跨程序代际的任意旧库恢复不是本路线的验收承诺。
- S3 不要求 DSH 一定成为编排者。当前已记录的 DSH 工具桥挂起决定继续生效；先做到按真实能力拒绝不支持的组合，并允许兼容 Codex 运行时独立选择。DSH 桥如需实施，单独恢复其跨仓库计划。
- 不引入任意代码插件加载、完整组织/RBAC 系统、无关的前端重写或默认预算/权限大调整。因本路线需要触碰的局部 UI、身份来源、事件和诊断必须一并完成。

## 6. 总体验收与交付记录

最终至少证明以下情景，细项见 S6：

1. 同一 Host 运行包，不改 Rust，发布并选择旧/新 Workflow、Skill、Spec、Agent 修订；使用原语相同但结构不同的两组流程；新旧执行按各自冻结引用运行。
2. 从 UI 导入/选择另一套兼容运行时资源，基于内容和实测能力通过；改版本标签不影响选择，实际内容不符或关键能力缺失则拒绝。
3. 相同 Feature/Task 流程分别由 Rust 自动驱动和经理 Agent 推进，经历人工门禁、失败、取消、恢复和模式切换；判定规则一致。
4. 人类对经理提出：改流程、加项目 Agent instance、改交付物 Spec、改某 Agent Skill、删除一个不用的配置；每项都有真实查询、预演、应用回执和历史可追溯结果。
5. UI 与 Agent 对相同非法配置得到同类、同位置错误；两个入口并发修改不会覆盖彼此；跨全局/项目库失败可恢复，无部分可见配置。
