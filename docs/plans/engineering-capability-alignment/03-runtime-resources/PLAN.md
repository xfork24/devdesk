# S3：运行时资源、外部依赖与真实能力

状态：待实施。依赖：S1 的 ports/应用边界、S2 的资源引用与验证管线。[总体路线图](../PLAN.md)

## 1. 核心目标

在不改 Rust 的情况下，为已实现的协议驱动配置、安装、验证并选择另一份兼容 Harness/Sandbox 运行资源；运行版本由 UI/配置指定，不由程序常量决定。取消 `provider == codex` 对业务能力的替代判断，但继续按真实能力拒绝没有工具桥的 DSH 组合。

不删除内容校验，不信任配置自述的执行能力，不承诺任意新 SDK 协议无需代码实现。

## 2. 拆分当前混合的身份

| 概念 | 事实来源 | 作用 |
|---|---|---|
| 协议驱动 | 已装配 adapter 实现 | JSONL/SDK 映射、请求应答、取消和恢复语义；新增协议需要代码 |
| 运行资源描述 | 可发布的精确配置修订 | 镜像/下载件/构建配方、平台、版本标签、内容摘要、启动声明 |
| 运行安装 | adapter 实际获取/构建后的事实 | image/executable digest、实际平台、可运行性、安装 ID |
| 权限执行资源 | 明确引用的后端资产与实现 | 配置编译和执行所需的 mount/策略/runner；不能被无证明声明替换 |
| 能力验证事实 | 驱动探测与受控验证所得 | 实际安装、权限资产、驱动实现共同支持的能力；带验证来源和摘要 |
| 执行绑定 | core 冻结选择 | 所选源、安装/资产/驱动身份、能力事实、权限及模型连接 |

`RuntimeKey.version` 只作展示/定位元数据，不再编码 `+recipe.<digest>` 来携带权威配方身份。recipe/image/asset digest 使用专用字段和类型。默认资源可以 pin 一个版本，但目录数据是 pin 的唯一来源。

## 3. 资源与能力设计

### 3.1 配置化资源目录

按 S2 约定增加运行资源/配方对象，或以明确类型扩展现有 Harness/Sandbox，实施前选定唯一表示，避免两套同义目录。应能表达不可变 OCI digest、受校验下载件和有界构建配方/资产清单；默认版本、平台下载摘要和 Dockerfile 内容从 `runtime_preparation.rs`/native_release 表移至外层资源包。

Adapter 负责获取、构建、安装与平台核验，core 只组织 Prepare/Observe/Select 用例。准备在事务外执行且有持久化意图/回执；长任务可取消、恢复、查看进度。新配方可以导入并被当前 Host 使用，不要求重新打包程序。资源中的执行资产按实际导入/使用授权处理，禁止在配置校验或预演时隐式执行。

UI 提供导入/修订资源、版本标签和精确镜像/配方选择、准备/验证/采用状态。资源不是“登记成功就视为可执行”。同一标签不同内容不合并；不同标签相同内容可以共享存储，但各自源引用仍保留。

### 3.2 能力判定

定义已有原语所需的能力，例如会话输入输出、结构化输出、原生工具、动态工具注册/调用/回执、外部工具、可确认停止、恢复以及权限执行能力；标识语义明确，不用一个 `tool-calling` 覆盖所有工具桥。

有效能力为：**配置需求被已实现驱动、实际资源验证事实与当前权限共同满足**。配置声明代表要求或预期，不能赋予驱动原本没有的能力。静态实现事实与运行探测结合；不能安全探测的能力以明确范围的受控协议验证记录证明，不把模型口头声称当作事实。

将四处 core Codex 门禁改为能力需求；具体 Codex/DSH wire 分支留在 adapters。有限驱动注册表可以是代码，这是已实现原语清单，不是兼容版本白名单。权限 profile 的选择仍由 core 验证，具体 backend 编译与执行探测在 adapter。

### 3.3 内容一致性与兼容性

核验所选资源描述摘要与实际安装内容；兼容性根据协议操作、真实工具桥、权限约束和行为验证判定。允许同一驱动管理两份均通过验证但摘要不同的兼容运行时；不再要求两者等于 `default_*_recipe_digest()`。

实际内容改变、能力缺失、权限 runner 不支持当前要求必须拒绝。验证事实绑定 driver/资产/安装摘要，任何相关内容变化后重新验证；新安装不能替换正在运行的冻结安装。换版是否需要新会话由冻结 binding 决定，不靠版本标签比较。

## 4. 工作项

| 工作项 | 涉及 | 验收 |
|---|---|---|
| R01 定义资源/安装/能力事实 | domain/runtime、governance、permission | 标签与内容/能力分离；精确引用可进 S2 图 |
| R02 外置默认配方、下载目录与资产 | runtime_preparation、containers、permissions、resources | Rust 无指定外部发行版的唯一常量；构建仍可验证默认包 |
| R03 实现资源准备与观测 port | core services、adapters/runtime_*、host/runtime_setup | 准备过程不占业务事务；重复/取消/恢复可核对 |
| R04 驱动能力报告与控制工具目录 | adapters/harness、core ports/tool catalog | core 无业务厂商门禁；DSH 缺桥准确报能力缺失 |
| R05 解除唯一配方及 Sandbox 版本门禁 | permissions、permission_profiles、core/governance | 两套兼容资源可并存；不取消权限执行验证 |
| R06 UI 资源选择与状态 | 运行时/集成/Agent 配置界面 | 选择精确资源，能看到要求、实测能力和拒绝原因 |
| R07 回归与文档 | model-providers/permissions/contracts、EXECUTION | 独立包无源码目录也能导入、准备并采用新资源 |

## 5. 验收门槛

同一未重编译 Host 选择两份内容不同、同协议兼容的 Codex 运行资源，分别建立真实 Linux 容器 Session，验证工具往返、停止证明和当前权限边界；只修改版本标签不改变接受性。更改镜像/runner 内容后，原验证事实不可复用。

测试替身证明新驱动满足同一 port/capability 即可编译合法组合，不需要改 core 厂商列表；这不代替真实 Codex 验收。DSH 保持 native-only 可用、动态工具/编排组合拒绝的现状，未经其独立桥接计划恢复不声称通过真实 DSH 编排。

如果发现某候选运行时引入新的协议或权限语义，应明确列出缺失原语和需要修改的 adapter；不得通过标签改写、伪造能力或移除权限检查使其通过。
