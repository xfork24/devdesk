# 后续性能与流程修复计划

状态：待执行。2026-11-18按用户要求仅保存计划，当前测试已暂停；不自动恢复付费模型、全流程或矩阵。依据为 [验收报告](ACCEPTANCE.md)、[性能基准](PERFORMANCE.md) 和 [问题清单](OPEN-ISSUES.md)。本计划不修改三个历史方案的目标，也不把尚未验证的策略写成已实现能力。

## 目标和交付边界

优先解决已定位的观察器合同错误、剩余读取/传输开销与经理调度成本，再单独设计预算和物理存储。每项交付根因、改动、定向正确性证据、同条件前后基准或明确无收益的结论。已实现但缺真实异常链验证的R4/R11等，以局部链和原现场隔离副本优先补证。

本轮不再重复全流程。下一阶段也不为每个修复新开Feature：先集中修复、固定候选，用专项门禁覆盖受影响边界，只有稳定候选确需端到端证明时集中安排一次必要的真实链路；不能将各构建的局部成绩拼成完整通过。出现新的局部问题，保留原失败并局部复验。

所有工作保留用户main并行改动。单Host、项目分库、资源级OCC、幂等、未知先核对及真实writer撤权不变；不增加全局/项目业务锁或单写队列，不降低测试/独立评审/人类门禁，不以外部输入或操作者调度补推经理。Human只审批，任何新远端合入另取具体候选授权。

## 1 短周期优先修复：R13审批观察器合同

**问题和输入。** r32的Feature10已提交PRD和独立审核，经理产生真实待批请求，materials含当前评审执行及session/turn，evidence为空。生产`validate_controller_interaction`允许两类引用联合覆盖当前执行；观察器仍要求两个数组同时非空，在保存human-request前断言退出。仅测试的旧`controller_interactions::validate`还有不同规则，存在合同漂移。

**实施。**

1. 保存原请求、冻结计划、确切执行、inputs/output引用和脚本身份，不恢复旧经理或修改业务事实。
2. 核对生产命令、页面和核验器对材料、当前执行、上游、输出、上下文及版本的实际合同，消除仅测试旧实现与生产实现的分歧。分类为空不应自动等于无证据；缺少必须的原件和当前绑定仍应拒绝。
3. 观察器先耐久保存完整有界请求和核验问题，再输出可诊断失败或保持只读等待；禁止裸assert抹掉现场。观察器不替经理补材料或请求、不代调度。
4. 扩展现有`tests/live/workflow_observer.py`及对应工具测试，复用既有核验方法，避免建立第二套业务权威。

**专项验收。** 当前执行位于materials且上下文齐全；位于evidence；缺当前执行；漏必需输出/上游；错项目/根；过期execution/input_digest/output；缺上下文；合法等待中途变化。正向请求可显示并被人类核对，负向保留且不得签署。四项既有活动检测回归继续通过。保存失败Feature10原退出1；专项不调用模型、不发送业务命令，不需要完整Feature复跑。

## 2 剩余读取与原生尾部：R14

**问题和输入。** 同一真实Feature9备份的完整control API响应3363134bytes；r27→r32每次表解码330→229，但30样本P95为418.81→587.76ms。r32/100短原生23项P95=248.52ms，慢项包括artifact.read和execution.inspect；样本少，不能先假定是同一根因。

**实施。**

1. 从现有逐方法原生记录、HTTP账本和调用者定位完整control的实际使用入口，区分普通展示、经理原生工具、确切输入/合同读取和兼容接口。
2. 在相同只读备份、固定单方法参数下，测源恢复、资源/表读取、JSON解析/编码、响应bytes、传输及发生器排队；保留冷/热、缓存开/绕过和共享机器负载上下文。
3. 普通控制/展示只取有限头、状态、版本及摘要，输入正文/产物/合同按确切执行或ref分开懒读；契约要求完整原件时保留完整可读入口，不截断后冒充完整。
4. 消除同一请求重复恢复/解析/编码；缓存只服务显示或不可变内容，带确切项目/资源/版本，业务授权及提交仍核对权威事实。
5. 若完整兼容API确属显式重操作，明确调用边界并让热调用者迁出；不能仅改标签逃避已出现的热路径成本。

**专项验收。** 首先用同一固定数据/方法至少200项形成定位样本；需要声称原方案逐方法SLA时再满足原合同样本和轮次。响应内容或明确分页语义一致、普通读零完整工程恢复/零隐式写、跨项目拒绝、旧输出仍可读、缓存失效/迟到响应/草稿冲突正确。首轮目标为不再出现同方法P95超过`max(基线+10ms,基线×1.1)`的回归，追踪轻量原生P95≤200ms目标；未达标继续报告实际值。先做0/100协议短专项，不新开完整Feature。

## 3 经理调度策略与整体效率：R8，连带验证R4

**问题和输入。** r8没有技术段，经理41Turn累计1831.53s；r9已经自主授权技术段，但策略和收益没有同条件对照。仅RPC变快不能解决经理反复读取、逐节点模型决策和人工/发布等待。

**实施。**

1. 复用现有轨迹按实际Actor、step、operation和等待原因分解：经理Turn、模型服务、执行者、平台I/O、待接纳、Human和发布等待。使用关键路径和不重叠区间，禁止简单相减/累加重叠时长。
2. 找出连续且已授权、无需新业务判断的技术节点，形成可委托边界；中途异常、输入/计划变化、未知效果立即回到经理。独立测试、评审、人类门禁和业务取舍保留。
3. 只有确认需要策略变化时发布新的配置/Capability/Skill不可变修订，旧冻结任务仍按原版本；不按业务key在内核硬编码下一步。
4. 联动R4：用已有PR创建观察在局部发布等待现场验证经理只读可见确切候选/PR/来源并自主通知人类。历史观察不能充当当前远端状态或合入权限。Human签署与仓库合入仍分别授权。

**专项验收。** 先用可控端口及真实Host/SQLite验证段授权、异常回流、根/子作用域、Human门禁阻断、未知不重发。稳定配置才进行有限真实经理局部链，同模型/预算比较Turn数、重复读取、技术衔接和关键路径。必须0外部调度指导、0Human代接纳；不承诺尚未测得的整体加速倍数。完整Feature仅在必要时集中安排。

## 4 预算和超时语义设计：R2

**设计决策。** 区分活动时间、模型/平台等待、人工审核、发布外部事实等待、平台自身deadline、总墙钟及无进展watchdog；明确每种时间由谁持久化、何时开始/暂停/恢复、如何跨Host重启及避免重复扣费。

**实施边界。** 发布明确的新配置/结构合同；旧冻结执行不读取新默认替代旧预算。截止触发时先执行实际停止/撤权并核对未知效果，不以超时自动认定未生效。不能仅提高1800s、原600s观察窗口或无限停表。

**验收。** 可控时钟覆盖平台慢/断连、人工久等、没有进展、总墙钟、重复通知、Host重启、旧版本恢复和到期竞争。真实Docker只验证必要的停止/撤权边界；不靠耗时全流程等待制造样本。R11已实现的“确切已合入结果复用”必须与新预算独立工作，保持原取消和物理operation不变。

## 5 物理步骤存储设计：R3

**先测量。** 同样的活动页和写操作分别扩大实例数十倍、单实例DAG步骤十倍、历史尝试十倍；报告解析/编码、物理写字节、事务占用、WAL/checkpoint、热查询和RSS，不能用冷实例工厂替代单DAG成本。

**再设计。** 对比保持JSON的有界索引/投影与拆分当前步骤、历史、头的单一权威方案。写明资源版本、原子读写集合、幂等、事件、迟到回执、取消、历史计划和恢复规则，不维护两份可独立修改的权威事实。

**兼容门禁。** 明确SQL新基线及旧数据拒绝/显式迁移方案。当前仍global24/project59，不在测量或实现中私自转换用户数据。若收益不足以支撑结构变化，保留结果和当前缺口，不为满足计划而强拆表。

**验收。** SQLite真实交错的兄弟步骤独立提交、同资源冲突、上游变化、取消/重试、未知/迟到回执、重启恢复、外键/quick_check及原件完整性；同条件性能/写放大对照。完全使用隔离数据，无需真实模型全流程。
