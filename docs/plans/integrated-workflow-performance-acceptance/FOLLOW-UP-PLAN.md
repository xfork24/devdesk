## 验收口径与目标

以下沿用 [运行性能合同](../workflow-runtime-performance/ACCEPTANCE.md) 和 [单Host并发合同](../single-host-concurrency/ACCEPTANCE.md)，不是已经取得的新成绩。原生方法/调用大小/场景必须分别统计；正式分位数每类至少1000样本。当前r32的100前端混合原生P95=248.52ms仅有23项，既不能按0前端200ms门槛判为正式失败，也不能按100前端500ms门槛宣布正式通过。

| 关注点 | 拟验收目标 | 验证和解释边界 |
|---|---|---|
| 轻量原生往返 | 0前端P95≤200ms/P99≤500ms；100前端P95≤500ms/P99≤1s | 按方法及大小统计，保留失败、排队和未发送；更严格的优化愿望另列，不替换原合同 |
| 调度及平台衔接 | 就绪到本机派发P95≤1s；外部结束到接纳P95≤250ms/P99≤500ms；接纳到回复P95≤100ms/P99≤250ms | 记录实际可用的阶段边界，暂缺精确COMMIT的项目标注观测限制；不把平台排队划给外部服务，不相减不同分布的分位数 |
| 多前端普通读/写 | 摘要/状态/分页P95≤200ms/P99≤500ms；持久化确认P95≤300ms/P99≤1s | 保留已取得的低延迟基准，变慢需要说明；普通读零完整工程恢复、零隐式业务写，写入有版本/幂等及耐久回读 |
| 实际页面 | 导航到主要状态和可用操作P95≤1s/P99≤2s；正常事件收敛P99≤1s，无故超过3s失败 | 真实浏览器动作和对应项目/版本绑定；请求耗时不替代页面可用，已知只读导航取消单列，修改失败不豁免 |
| 有限读取及历史增长 | 正常执行摘要≤64KiB、普通列表≤128KiB；历史十倍时轻量/摘要P95≤1.5倍且满足绝对门禁 | 大正文/原始JSON/Artifact按需读取并单列，不能截断原件冒充摘要达标；单实例DAG增长与冷实例增长分别测 |
| 后台推进与等待 | 同预算100前端后台吞吐≥0前端的80%，无饥饿；纯稳定等待60s Host平均CPU≤单核2% | 测量窗口必须持续有实际可推进工作，缺货窗口不能算通过；Host/worker/发生器资源分开 |
| 正确性及自主性 | 0丢失更新、0串项目/越权、0重复副作用；0外部调度指导、0Human代接纳 | 人类签署绑定当前材料和执行；经理自己派发/接纳/恢复。旧失败、停止和未知结果事实保留 |

这些门槛用于定义成功，不代表每项修复都要重跑完整合同。先做受影响的短专项：R14单方法定位每项至少200样本；0/100协议对照使用同参数的120s短轮；真实浏览器先1/10/25页面各120s，资源和队列允许时才继续50/100。短轮不足原合同样本/轮次时只作定位和局部复验，不声明正式容量或逐方法SLA完成。

对经理调度先记录“重复读取、无效唤醒、没有新增业务判断的控制回合、就绪后的技术空档”及关键路径，不预设模型一定能减少多少Turn或整体加速几倍。按同业务图/同输入对照证明收益；不同业务需求的全流程墙钟不计算因果加速比。

## 目标和交付边界

先完成观察器合同的小范围前置修复，主要处理剩余读取/传输、实际多前端页面和经理调度成本；预算设计作为P1可靠性工作，物理存储先测量再设计。每项交付根因、改动、定向正确性证据、同条件前后基准或明确无收益的结论。已实现但缺真实异常链验证的R4/R11等，以局部链和原现场隔离副本优先补证。

本轮不再重复全流程。下一阶段也不为每个修复新开Feature：先集中修复、固定候选，用专项门禁覆盖受影响边界，只有稳定候选确需端到端证明时集中安排一次必要的真实链路；不能将各构建的局部成绩拼成完整通过。出现新的局部问题，保留原失败并局部复验。

所有工作保留用户main并行改动。单Host、项目分库、资源级OCC、幂等、未知先核对及真实writer撤权不变；不增加全局/项目业务锁或单写队列，不降低测试/独立评审/人类门禁，不以外部输入或操作者调度补推经理。Human只审批，任何新远端合入另取具体候选授权。

## 1 短周期优先修复：R13审批观察器合同

**问题和输入。** r32的Feature10已提交PRD和独立审核，经理产生真实待批请求，materials含当前评审执行及session/turn，evidence为空。生产`validate_controller_interaction`允许两类引用联合覆盖当前执行；观察器仍要求两个数组同时非空，在保存human-request前断言退出。仅测试的旧`controller_interactions::validate`还有不同规则，存在合同漂移。

**实施。**

1. 保存原请求、冻结计划、确切执行、inputs/output引用和脚本身份，不恢复旧经理或修改业务事实。
2. 核对生产命令、页面和核验器对材料、当前执行、上游、输出、上下文及版本的实际合同，消除仅测试旧实现与生产实现的分歧。分类为空不应自动等于无证据；缺少必须的原件和当前绑定仍应拒绝。
3. 观察器先耐久保存完整有界请求和核验问题，再输出可诊断失败或保持只读等待；禁止裸assert抹掉现场。观察器不替经理补材料或请求、不代调度。
4. 扩展现有`tests/live/workflow_observer.py`及对应工具测试，复用既有核验方法，避免建立第二套业务权威。

**专项验收。** 当前执行位于materials且上下文齐全；位于evidence；缺当前执行；漏必需输出/上游；错项目/根；过期execution/input_digest/output；缺上下文；合法等待中途变化。正向请求可显示并被人类核对，负向保留且不得签署。四项既有活动检测回归继续通过。保存失败Feature10原退出1；专项不调用模型、不发送业务命令，不需要完整Feature复跑。

## 2 剩余读取与原生尾部：R14

**问题和输入。** 同一真实Feature9备份的完整control API响应3363134bytes；r27→r32每次表解码330→229，但30样本P95为418.81→587.76ms。r32/100短原生23项P95=248.52ms，慢项包括artifact.read和execution.inspect；样本少，不能先假定是同一根因。

**实施。**

1. 从现有逐方法原生记录、HTTP账本和调用者定位完整control的实际使用入口，区分普通展示、经理原生工具、确切输入/合同读取和兼容接口。
2. 在相同只读备份、固定单方法参数下，测源恢复、资源/表读取、JSON解析/编码、响应bytes、传输及发生器排队；保留冷/热、缓存开/绕过和共享机器负载上下文。
3. 普通控制/展示只取有限头、状态、版本及摘要，输入正文/产物/合同按确切执行或ref分开懒读；契约要求完整原件时保留完整可读入口，不截断后冒充完整。
4. 消除同一请求重复恢复/解析/编码；缓存只服务显示或不可变内容，带确切项目/资源/版本，业务授权及提交仍核对权威事实。
5. 若完整兼容API确属显式重操作，明确调用边界并让热调用者迁出；不能仅改标签逃避已出现的热路径成本。

**专项验收。** 首先用同一固定数据/方法至少200项形成定位样本；需要声称原方案逐方法SLA时再满足原合同样本和轮次。响应内容或明确分页语义一致、普通读零完整工程恢复/零隐式写、跨项目拒绝、旧输出仍可读、缓存失效/迟到响应/草稿冲突正确。首轮增加内部回归线：同方法P95不超过`max(基线+10ms,基线×1.1)`，同时按上表核对绝对门槛；0前端原生P95≤200ms、100前端≤500ms，不能混用。未达标继续报告实际值。先做0/100协议短专项，不新开完整Feature。

### 2.1 调度和原生衔接的定位范围

在读取和序列化之外，核对“请求登记→技术派发→实际完成→接纳→原生写回→经理事件投递”的可观测间隔。重点找结果已经可用却等待补扫、同次结果重复读取/恢复、慢Git/Docker操作挤占短接纳和回复、同批不相关技术工作被串行等待等情况。先以现有日志和span定位，必要时补最小有界观测；未知时间段明确标注，不凭相邻日志推断精确提交时刻。

只并发或批量处理已经合法授权且资源独立的技术工作。优化完成通知、技术阶段去重和公平轮转，不在Host中决定下一业务步骤；业务资源版本变化、取消、计划替换和worker代次仍会使旧结果失效。验收同时覆盖慢项目下另一项目的就绪工作、取消/停止响应及实际后台吞吐，不能仅以请求返回变快结案。

### 2.2 多前端专项：R5本机定位部分

本项属于P1，和R14共用固定候选；正式容量部分仍保留在第6节。没有独立负载机时继续做本机定位，不能把整项多前端工作推迟到换机器以后。

1. **固定当前界面。** 记录当前main、Web产物、配置、种子及资源预算；保留其他session的布局和交互，以实际待发布界面为对象，历史r29数据只作相应旧版本的依据。
2. **查请求放大。** 分别测执行页、经理页、材料/上下文、跨页/跨项目导航；记录每次动作/SSE事件触发的RPC数、响应bytes、同键并发、历史/正文读取次数，以及标签页不可见时的请求。修复重复请求、过宽失效和无变化轮询，不能取消有界补读或丢最终状态。
3. **查真实页面成本。** 同时记录点击到主要内容、操作可用、对应版本显示、主线程长任务和渲染；列表、阶段及子流程按需加载，减少无关区域重绘。只在有测量依据时调整组件，不借性能任务重做外观或回退并行UI。
4. **查慢订阅者和发生器。** 分开记录Host、Docker、Python发生器、Chromium资源及发送队列，进程RSS总和不能当作唯一物理内存。覆盖项目切换、隐藏/恢复、慢订阅与重连；不能把发生器未发出的请求删出统计，也不能直接把浏览器超时归咎于Host或OOM。
5. **局部联合复验。** 0/100协议对照配合持续合法后台工作；实际浏览器按1/10/25短阶梯开始，50/100只在资源条件允许时继续。核验不同对象写入和回读、同对象预期冲突、项目/订阅隔离，以及后台派发/接纳没有被前端读流量挤占。

**完成判据。** 每个已定位产品问题都有实际页面或协议复现、修复及同条件前后样本；普通读不拉全历史，同键请求有界，事件/隐藏页恢复不丢最终版本，写入/冲突语义正确。页面和后台推进按上表给出实际结果；发生器达到瓶颈时保留失败及其资源证据，清楚列出“已验证到多少真实页面”和“哪些更高并发未证实”。不能仅用100SSE连接或低HTTP P95关闭本项。

## 3 经理调度策略与整体效率：R8，连带验证R4

**问题和输入。** r8没有技术段，经理41Turn累计1831.53s；r9已经自主授权技术段，但策略和收益没有同条件对照。仅RPC变快不能解决经理反复读取、逐节点模型决策和人工/发布等待。

**实施。**

1. 复用现有轨迹按实际Actor、step、operation和等待原因分解：经理Turn、模型服务、执行者、平台I/O、待接纳、Human和发布等待。使用关键路径和不重叠区间，禁止简单相减/累加重叠时长。
2. 找出连续且已授权、无需新业务判断的技术节点，形成可委托边界；中途异常、输入/计划变化、未知效果立即回到经理。独立测试、评审、人类门禁和业务取舍保留。
3. 只有确认需要策略变化时发布新的配置/Capability/Skill不可变修订，旧冻结任务仍按原版本；不按业务key在内核硬编码下一步。
4. 联动R4：用已有PR创建观察在局部发布等待现场验证经理只读可见确切候选/PR/来源并自主通知人类。历史观察不能充当当前远端状态或合入权限。Human签署与仓库合入仍分别授权。
5. 对依赖图中同时就绪且资源独立的工作，核对串行等待是否必要；由经理或其既有合法授权段自主选择派发，保留额度、公平和写入隔离。无新事实时不反复读取完整状态、发相同通知或重做相同评审；等待必须绑定实际事件、对象或期限。

**专项验收。** 先用可控端口及真实Host/SQLite验证段授权、异常回流、根/子作用域、Human门禁阻断、未知不重发。稳定配置才进行有限真实经理局部链，同模型/预算比较Turn数、重复读取、技术衔接和关键路径。必须0外部调度指导、0Human代接纳；不承诺尚未测得的整体加速倍数。完整Feature仅在必要时集中安排。

评审拒绝后的业务研判、返工额度和人工例外批准已有 [独立计划](../review-rejection-and-approval/PLAN.md)。本项记录重复评审/补证循环造成的成本，并与其衔接，不重复定义另一套返工或审批规则。R2时间预算与该计划的业务返工额度分别设计；减少控制回合不能跳过失败报告、独立评审或真实Human决定。

## 4 预算和超时语义设计：R2

**设计决策。** 区分活动时间、模型/平台等待、人工审核、发布外部事实等待、平台自身deadline、总墙钟及无进展watchdog；明确每种时间由谁持久化、何时开始/暂停/恢复、如何跨Host重启及避免重复扣费。

**实施边界。** 发布明确的新配置/结构合同；旧冻结执行不读取新默认替代旧预算。截止触发时先执行实际停止/撤权并核对未知效果，不以超时自动认定未生效。不能仅提高1800s、原600s观察窗口或无限停表。

**验收。** 可控时钟覆盖平台慢/断连、人工久等、没有进展、总墙钟、重复通知、Host重启、旧版本恢复和到期竞争。真实Docker只验证必要的停止/撤权边界；不靠耗时全流程等待制造样本。R11已实现的“确切已合入结果复用”必须与新预算独立工作，保持原取消和物理operation不变。

## 5 物理步骤存储设计：R3

**先测量。** 同样的活动页和写操作分别扩大实例数十倍、单实例DAG步骤十倍、历史尝试十倍；报告解析/编码、物理写字节、事务占用、WAL/checkpoint、热查询和RSS，不能用冷实例工厂替代单DAG成本。

**再设计。** 对比保持JSON的有界索引/投影与拆分当前步骤、历史、头的单一权威方案。写明资源版本、原子读写集合、幂等、事件、迟到回执、取消、历史计划和恢复规则，不维护两份可独立修改的权威事实。

**兼容门禁。** 明确SQL新基线及旧数据拒绝/显式迁移方案。当前仍global24/project59，不在测量或实现中私自转换用户数据。若收益不足以支撑结构变化，保留结果和当前缺口，不为满足计划而强拆表。

**验收。** SQLite真实交错的兄弟步骤独立提交、同资源冲突、上游变化、取消/重试、未知/迟到回执、重启恢复、外键/quick_check及原件完整性；同条件性能/写放大对照。完全使用隔离数据，无需真实模型全流程。

## 执行顺序和交付

审核后的建议顺序为：R13短前置→R14与R5本机多前端定位→R8/R4经理调度→R2预算设计及R11局部补证。R3先测存储成本再决定改造，R6按归因需要补最小观测，R5正式容量在修复稳定和条件具备后另排；R10的其他UI问题保持独立范围。前置小修不能扩成长期阻塞两个性能主项的工具工程。
