# 工作流故障恢复与升级

状态（2026-11-23）恢复机制已部署，Task3 后续验收进行中。本文补录并修订对话中已批准的恢复计划。提交 `87965271` 和 Task1、Task2 的实际回执证明了对应路径可以恢复。此前没有证明每次尝试都读取了历史，也没有证明经理无法提前将可解决的故障升级给人类。

## 审查范围

- 内置 Feature v9 有 19 步，Task v4 有 14 步。两个定义的每步 `budget.retry_limit` 都是 3。本地项目登记了 13 个工作流定义，其中 11 个是派生的冻结版本，各步的重试额度同为 3。当前绑定使用 Agent 经理。两份内置定义的 Rust 故障代码自动重试列表为空。
- 运行时统一提供恢复协议，新派发的执行使用结构化自修。已派发的旧会话仍能读取原始任务并按原协议续跑，新的经理技术续跑计入同一逻辑步骤额度。
- Agent 经理负责需要诊断和选择修复的流程。显式选择 Rust 驱动时，Rust 按冻结列表处理可安全重跑的故障，经理权限仍由原有驱动选择控制。Rust 调度使用独立的 `scheduling.max_retries`，对运行前反复准备失败也能停止，实际修复额度继续以开始证明计数。

## 范围与规则

- Agent 在原步骤、原工作区和原权限内诊断可解决的问题。每个逻辑步骤的 `budget.retry_limit` 默认 3，可配置。首次执行不扣重试额度。Agent 自修重跑和经理安排的修复重跑共用该步骤的额度，只有运行时证明实际开始才扣减。排队、Host 重启、换 Agent 和更换执行 ID 沿用同一个逻辑步骤的额度。
- 下一轮先读取以前的诊断、动作、结果和依据。已试过的同一修复只有在相关输入或外部条件有真实变化时才能再次执行。无法自行解决时，Agent 将诊断和证据交给项目经理。
- 经理核对真实回执和已尝试的动作，在冻结范围内补充技术方案、继续原会话或重新派发合适的执行者。平台测试失败按原报告和依赖图回到正确的作者或实施者。未知副作用先核对。
- 可解决的故障只有在相关步骤的额度用完后才生成一次人工处理事项。需求、范围、验收条件、权限和明示人工门禁走确切的人类决定。发布、核对和测试回执仍以实际平台证据为准。
- 同一模型轮次内的阅读、分析和普通工具调用属于诊断。重跑由工作流内核准入并以实际 Turn 或平台操作计数。内核校验确定的动作和实际运行身份。模型对技术结论的判断仍须由经理及平台证据复核。

## 关闭条件

| 用例 | 必须观察到的事实 |
|---|---|
| Agent 自修成功 | 首次失败后按实际额度启动不同的修复，至少一次真实执行有开始证明。人类没有收到技术升级事项 |
| Agent 无法自修，经理恢复成功 | 经理读取原诊断和全部前序尝试，安排有实质区别的方案。原会话继续或换执行后产生真实结果 |
| 自修、经理修复逐次失败 | 配置为 N 时最多发生 N 次实际重跑。重复动作被拒绝。N 次用完且仍失败后只有一项人工处理事项 |
| 中途重启、更换 Agent、取消排队 | 原历史和已用额度仍可见，未开始的重试不扣额，已开始的重试保持同一身份 |
| 既有门禁 | 实际业务决定、拒绝评审、未知副作用仍走原签核或核对。输入与材料绑定确切版本 |
| Task3 | 原 4/4 通过回执仍可读。基线验证在当前确切候选上实际通过。Green、正式回归和真实 Mac 验收分别报告 |

验收记录逐项区分内核测试、浏览器显示与实际工作流。恢复入口可用或某一条线上路径跑通，只关闭它对应的用例。
