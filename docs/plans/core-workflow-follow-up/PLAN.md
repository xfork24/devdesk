# 核心工作流调度与验收补强计划

日期：2026-11-14。状态：待实施。基线：`1669f86c1fc142f46853122c4b439ec5267553b4`。本次仅编制计划，不执行实现。

## 目标与范围

对 `review/plans` 全部 14 个提案重新核对后的结论是：**不整包执行旧提案，只做三项仍直接影响核心功能的工作：修复任务调度阻塞，补全可配置技术重试，落地默认交付的确定性验收与自检。**逐项处置、代码依据和已复现缺陷见 [ASSESSMENT](ASSESSMENT.md)。

本计划聚焦基本执行能力、工作流调度、任务分配及交付验收。已有配置图、经理创作工具、双调度、精确修订选择和真实证据链继续复用。账号、审计界面、导出产品、监控指标、通用前端重构、新模型服务商及 DSH 工具桥不在范围内。

## 必须遵守的实现边界

沿用[工程能力对齐第二节](../engineering-capability-alignment/PLAN.md)全部八项工程约束，并落实到本次工作：

1. domain 放纯判定与领域事实；core 负责授权、动作选择和接纳；adapters 处理真实执行/存储；host 只装配和接入。业务判定不得搬到 UI、Host 或适配器。
2. UI、Rust、经理 Agent 使用同一动作资格及控制用例。查询可表达当前阻塞原因，最终执行仍在事务内核对计划、控制版本、身份、租约和真实资源状态。
3. 原语相同的 Workflow、Skill、Spec、预算和并发策略通过配置后继演进；不新增 schema_version/bundle/renderer 版本门禁，不恢复 Contract Registry。
4. 已授权配置修改不额外强制人审；人工业务门禁由真实人类入口完成。任何驱动都不能自签人工确认、把业务失败重试成成功或伪造测试/Git 回执。
5. 修改配置产生后继，执行冻结精确引用。运行中改计划或改派必须走预演、停止受影响执行、核对和后继计划/会话，不能热改正在执行的绑定。
6. 本项目仍按未上线和新数据集策略实施，不新增历史 SQL 兼容/尽力投影，也不删用户数据来通过验收。若变更存储表达，须保留同一受支持基线内冻结记录的自洽性。

## C1 统一动作资格并消除调度阻塞

### 问题

当前 foreach 槽位已满的 queued 子流程仍会被 workflow.inspect 标为 dispatchable。Rust 驱动按 ID 先选中它，命令拒绝后结束本轮，其他子流程可接纳的结果得不到推进。该路径已经用生产命令和 SQLite 在临时目录复现，细节见评估。

### 工作项

- C1.1 将 dispatch/accept/retry/complete 的核心资格收敛到可复用的判定入口，至少统一本次触及的 foreach 槽位、祖先暂停、待应用计划、依赖、输入、真实执行者停止和人工/完成门禁。区分“当前可做”“等待条件”“已失效/需核对”，返回结构化原因；不声称一次查询保证之后提交必成功。
- C1.2 workflow.inspect、Rust 选择器和实际命令复用相同规则，实际命令保留事务内复核。经理 Agent 与 UI 获得同一事实，不在各入口复制一份简化状态机。
- C1.3 Rust 驱动跳过当前不可执行的候选，继续寻找本根其他合法动作。对并发造成的陈旧候选只在单 tick 的动作/扫描预算内重读；无进展时等待，不能无限重试，也不能跳过 needs_reconciliation 或权限撤销。
- C1.4 派发资格只反映真实能力与冻结授权。集合并发限制、根 worker 限制、项目/全局执行额度及 worktree 写者约束各守其职责，不通过提高限额或绕过接纳门禁掩盖问题。
- C1.5 等待原因复用现有 driver 查询和执行面板显示；只补需要的字段和局部展示，不改导航、路由、前端状态架构。

### 验收

| 场景 | 必须证明 |
|---|---|
| 已复现的两子流程案例 | foreach=1，先人工派发 ID 靠后的子流程再切 Rust；其结果能被正常接纳并完成，之后另一个获得槽位；不能依赖 ID/插入顺序 |
| 槽位不足与释放 | 查询显示等待集合槽位；旧查询在槽位变化后提交仍被事务正确接纳/拒绝；无超额派发 |
| 多任务依赖 | A、C 可独立执行，B 依赖 A；B 不提前派发，受阻 B 不妨碍合法 A/C；使用明确配置的集合及根额度 |
| 等待真实停止或人工确认 | 某步骤不能接纳时，其他独立合法工作仍推进；不得代签确认或提前接纳活动 writer |
| 暂停、取消、切换、变更 | 祖先暂停有效，取消等待停止证明，旧 epoch/旧计划的迟到动作被拒；合法后继恢复后继续推进 |
| 无可做工作 | 不增加重复 dispatch/accept 意图，不忙循环；已有“无变化零模型调用”行为保持 |

停止条件：若“修复”需要放松 foreach、输入冻结、停止证明或人工门禁，退回判定设计，不进入 C2。

## C2 补全技术失败与有界重试原语

### 问题

Rust 驱动目前仅从 tool_call_id 读取结构化错误；Agent 会话创建/轮次派发失败主要变成 reason 文本。sequence 同时用于补充输入轮次和重试次数比较，两个预算口径发生耦合。配置了非零重试策略也不能因此获得完整、可信的自动恢复能力。

### 工作项

- C2.1 先增加故障回归，覆盖 Agent 建会话、发 Turn、平台/外部 Tool 的已知技术失败，明确哪些已有真实错误码，哪些是结果未知。根据这些实际来源建立最小的失败事实，保留 code、类别、来源 operation/intent/receipt、结果是否已知和停止状态；不从模型文本或中文 reason 推断可重试。
- C2.2 分开补充输入/模型轮次、技术重试次数和业务返工轮次的含义。优先从现有执行历史推导；确需新增字段时同步领域、codec 和 Schema。步骤 retry_limit 与策略 max_retries 共同限制技术尝试，不因补充输入消耗重试配额，也不因重启清零。
- C2.3 C1 的共同资格入口消费失败事实。只有权限策略允许、可信错误码在所选策略内、两层重试预算都允许、旧执行者已停止且副作用结论已知时，才创建新执行。保留冻结输入和旧失败/拒绝记录，不复用旧执行身份。
- C2.4 业务拒绝、规范不合格、人工等待、取消请求及结果未知不自动转为技术重试。未知操作先核对，不能重发可能已执行的 Git/测试/外部请求。
- C2.5 继续保持默认策略 max_retries=0；不提高默认 max_turns/timeout，不加固定三档预算，不以更长预算掩盖卡住的驱动。

### 验收

- 明确可重试的 Agent 和 Tool 故障分别按同一规则恢复，创建新的 execution/operation，旧回执保持原样。
- 同一个策略下，补充输入后首次技术失败仍有正确的重试额度；用尽后停止；重启和驱动切换不能获得额外额度。
- 规范拒绝和真实测试断言失败不被技术恢复机制刷成通过；Red 的合法预期失败仍按现有配置判定。
- 在意图落盘、外部执行已开始、回执未接纳的不同中断点恢复，未知结果不重复派发；晚到的旧回执不污染新执行。
- 当前默认策略不产生新增自动重试，人工 retry/rework 仍受原授权、停止和冻结约束。

停止条件：无法证明错误来源或副作用结论时保持等待/核对；不使用字符串解析或默认 retryable=true 补齐覆盖率。

## C3 将现有 Spec 检查用于实际产出和验收

### 工作项

- C3.1 补齐普通 Workflow Tool/业务 Agent 调用 spec.lint 的 core 通路，和经理、UI、接纳继续调用同一检查器。业务 Agent 只可检查当前冻结步骤声明的输出 Delivery/Spec 与其草稿，不借此获得全项目配置查询或经理配置写权限。
- C3.2 对确实需要产出文档/评审的角色，通过 Capability、步骤 Tool 授权和 Permission Context 后继显式提供自检；缺实际工具桥的 Harness 组合继续拒绝。调用只读、受大小和工作量上限约束，不生成成功产物或接纳事实。
- C3.3 根据默认 Workflow 的真实输入输出逐项建立规则清单：哪些结构由现有 content_schema 覆盖，哪些 Markdown 必需章节可由 RequiredSections 检查，哪些评审需要对冻结输入提供精确位置。只配置具有实际判定价值的项目，不为凑覆盖率给全部 Delivery 添加空洞长度规则。
- C3.4 优先落到 PRD、Design 和默认关键评审：结构漏项由系统拒绝；评审证据绑定 source_ref、value_digest 与真实位置。结构成立不代表语义质量成立，原独立评审、测试、候选及完成门禁保留。
- C3.5 使用现有 MachineAssertion、JSON Schema、EvidenceLocation；不新增 Delivery.structure_checks、正则 DSL、RequiredNodes 或另一套验收引擎。AC 编号唯一性、需求到实现的语义映射等不能由现有原语准确表达的规则，继续由明确的内容评审承担。
- C3.6 发布关联 Spec/Delivery/Workflow/Skill/授权的必要后继并精确采用。出厂目录按现有清单机制更新；已创建工作和历史执行不自动升级。新规则导致合法产物被拒时，修正规则或交付内容后发布后继，不改写历史证据或放松内核。
- C3.7 仅补相关自检入口、失败位置/检查结果展示及当前工作流文档。现有编辑能力能表达的字段直接复用。

### 验收

| 场景 | 必须证明 |
|---|---|
| 生产步骤自检 | 合法授权下普通 Agent/Tool 步骤实际调用成功；未授权、跨步骤或越项目引用被拒；不调用模型替代检查器 |
| 同一产物同一结论 | 相同精确 Delivery/Spec 和相同内容的 lint、导入、输出接纳得到一致结构结论；失败不封存为已接纳结果 |
| 缺必需章节/字段 | 默认新修订的 PRD/Design/报告按各自声明拒绝，指出具体检查；补齐后可重新交付 |
| 证据错误 | 悬空位置、错误摘要、超范围引用及 quote 与范围不一致均拒绝；不能引用未授权或另一轮输入 |
| 业务拒绝 | 结构合法但评审拒绝时保持失败/返工语义，Rust 和经理均不能自动批准 |
| 配置独立演进 | 同一个 Host 二进制采用不同 Spec/Workflow 后继，旧执行继续按冻结选择运行；无需修改 Rust 版本常量 |

## C4 核心闭环验收

先用小型自建流程和明确测试端口验证状态/故障组合，再用现有真实 Codex 和 Docker 跑受影响的工程闭环。测试端口结果不能冒充真实 Harness、测试或 Git 回执。

1. **基本原语**：Agent、Tool、Control、子 Workflow 在同一父子图中执行；能力、Skill、输入、输出和步骤授权缺失均在正确边界拒绝，不按厂商名或版本标签决定源配置合法性。
2. **任务分配**：构造至少三个 Task，包含独立项和依赖项，使用明确选择的并发策略；验证不同工作空间、共享写者互斥、额度释放、取消传播和子流程完成后父流程继续。保留默认 foreach=1，并另测配置允许的并发值。
3. **双驱动**：同类图分别由 Rust 与经理 Agent 派发/接纳；经历真实人工门禁、规范拒绝和重试边界。驱动可选择动作，成功规则保持一致。
4. **变更与恢复**：在执行中发布后继、预演并改变流程/角色分配，停止受影响 writer 后建立新计划/会话；未受影响兄弟任务保留。重启、人工接管及两方向驱动切换后，旧调用失权、既有真实结果可继续接纳。
5. **实际交付**：在实施时明确指定的专用测试仓库，跑带新 Spec 的真实 Feature/Task 与 Red/Green/候选/独立评审链；核对确切输入、运行镜像、测试代码/结果和 Git 回执，保留拒绝、恢复和未执行项。复用现有本地证据导出工具，不建设新归档产品。

变更范围内先运行 domain/core、orchestration、configured_workflows、configuration_changes、manager_workspace、schema_contracts 及相关 Spec 回归；UI 改动跑对应浏览器用例。阶段合并后运行既有 check.sh；真实工程通过 check-live 通道单独记录。新增必要的引擎用例使用最小自建图，专门的出厂业务合同测试保留。

验收环境不足时如实记录未验和原因，不能靠模拟回执、豁免、删数据或放宽门禁替代。已有历史双驱动工程成功只能作为基线，不能替本次改动签收。
