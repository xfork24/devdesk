# S5 物理步骤存储定位

状态：2026-11-18，完成首轮三维增长的组件测量，R3 仍开放。没有修改 SQL、数据集标记或物理权威结构，没有运行正式容量矩阵。

## 可复现输入与测量边界

入口为 `crates/adapters/tests/workflow_storage_scaling.rs` 的显式 ignored 测试。只能创建全新证据目录；在目录中建立四个隔离数据集，不接受已有用户数据。生产配置发布、启动、取消、停止及重试均走实际 Engine/SQLite；没有模型、容器、GitHub、真实工作执行者或完整 Feature。

固定页大小 25、一个目标实例、相同单步骤输入/输出与读取、编码、解码及提交动作。每项一次预热另存，随后 30 项定位样本。控制步骤输入/输出为空，目标执行约 698 bytes；不代表丰富正文和 Artifact 场景。三种增长分别为：

| 组 | 冷实例 | 当前 DAG 步骤 | 目标节点历史尝试 |
|---|---|---|---|
| base | 1 | 32 | 1 |
| cold10 | 10 | 32 | 1 |
| dag10 | 1 | 320 | 1 |
| attempts10 | 1 | 32 | 10 |

冷实例是经实际取消后终止的根；DAG 是实际发布的串行图，不以十倍冷实例冒充大图。历史由合法静止 Control 的停止/技术重试产生，真实归档前驱执行，校验确切历史数，未复制治理行。四组实际 writer 均为 0，因此是存储归因，不能证明工作持续推进、并发正确性或容量。

提交采样使用可信存储接口的单个 `workflow_step` OCC patch，只交替修改同长度 reason；不经过业务授权，不宣称是完整业务命令延迟。每次确认版本增加、值耐久回读；无其他线程竞争。`resource.sql_transaction` 每样本恰为 1 次，保存实际单事务聚合 span；没有借此补齐独立 BEGIN 等待、COMMIT 返回时刻或页面事件关联。

原始证据位于 `/tmp/devdesk-remediation-20261118-t9uov0ry/s5-storage/`：`samples.jsonl` 共 628 行，包含预热、全部采样、输入及存储观察；`summary.json`、数据库及其摘要。私有 release 测试入口 SHA-256 为 `a246528a3d981882369f017793bda96a5fbe51ccf9cf66fc84a7128ea0f92e9c`，源码 SHA-256 为 `b1ff5a2b94f6a0f77199a7398b96b9041594bb15afb6b1e4d46898ae7f02227f`，保存在同根 `s5-candidate/`。641 项产品输入与 S2 冻结清单逐项一致，新增的是测试入口。

## 结果

同机单进程依次执行，没有本任务的构建与采样重叠；共享宿主没有独占 CPU 条件。下表为 P50/P95/P99，单位 ms，30 样本仅用于定位。

| 组 | 单步骤资源读取 | status 页读取及编码 | 单步骤存储提交 |
|---|---|---|---|
| base | 0.0255/0.0284/0.0352 | 0.939/0.992/1.016 | 3.081/3.446/4.757 |
| cold10 | 0.0262/0.0299/0.0355 | 0.960/1.069/1.079 | 3.116/3.486/9.107 |
| dag10 | 0.1185/0.1307/0.1326 | 1.709/1.764/1.766 | 17.688/17.967/17.976 |
| attempts10 | 0.0264/0.0290/0.0398 | 0.948/1.027/1.090 | 3.058/3.180/3.214 |

单独编码目标步骤 P50 约 0.0005 ms、解码约 0.0020 ms，四组目标大小相同；详见原始分布。完整实例实际存储 JSON 从 base 的 22041 bytes 增至 dag10 的 209969 bytes。十倍 DAG 的目标读取 P95 约 4.60 倍、提交约 5.21 倍；不能由这些温热小规模数据外推百前端吞吐或全部长历史门禁。

每组提交批次含预热共 31 次。只对该组新建数据集在批次前 TRUNCATE checkpoint，计时期间不插入 checkpoint，采样后做 PASSIVE checkpoint；没有读快照钉住 WAL。下列帧数均小于默认自动 checkpoint 阈值，保存原始 busy/log/checkpointed 结果。这里不测繁忙时 checkpoint。

| 组 | 批次 WAL frames | WAL 文件 bytes | 进程 rchar 增量 | 进程 write_bytes 增量 |
|---|---|---|---|---|
| base | 714 | 2941712 | 2056294 | 3072000 |
| cold10 | 885 | 3646232 | 2269291 | 3776512 |
| dag10 | 815 | 3357832 | 8650860 | 3485696 |
| attempts10 | 751 | 3094152 | 2068588 | 3223552 |

`/proc/self/io` 计入提交及耐久回读，排除造数和批次报告文件写入；`rchar` 是逻辑读取系统调用字节，`write_bytes` 是 Linux 进程 I/O 记账，不等于唯一物理设备流量。批次 WAL 只增约 14%，没有证明写字节随 DAG 十倍增长；更明显的是事务内工作和逻辑读取。进程 RSS 随组依次约 45/64/91/91 MB，受前组分配器驻留影响，不能当作各组独立峰值。四库 quick_check/外键均通过。

## 归因与结构选择

代码核对：`resource_commits::value` 的单步骤读取在实例 steps JSON 上 `json_each`；提交在原记录上 patch 后重新读取、解码整个实例，计算 `content_digest`。这与大 DAG 的扫描及事务内成本增长一致。具体解析、哈希、触发器及各索引写入尚未逐段分开，不把全部 17.97 ms 归给单一函数。

| 选择 | 收益边界 | 仍需证明 |
|---|---|---|
| 保留 JSON，继续缩小读取及重复解码 | 保持现有基线，可能改善查询及同事务重复工作 | 单步骤 patch 和完整记录摘要仍随当前 DAG 增长，不能据此关闭物理问题。 |
| 分离头、当前步骤与历史，以独立步骤为单一权威 | 有机会让选中步骤的读取、摘要及更新与兄弟数无关 | 明确头/步骤资源键、当前执行选择、历史封存、多对象原子性、取消/重试/迟到回执、事件、幂等与重启；避免长期双权威。需要新 SQL 基线及不兼容旧库的明确拒绝。 |

本轮先保留现有结构。当前微基准绝对延迟较低，但已确认 DAG 维度存在放大，不能宣告结构健康或 R3 关闭。进入结构实施前，需补更大合法正文/输出组、原合同规模下真实命令与并发提交的成本及门禁，并细分事务内 CPU；没有充分证据时，不把测量升级为数据兼容变更。
