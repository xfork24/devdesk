## 等待态回归及修复

首个实际 HTTP/60 s 诊断虽然验证了截止及拒绝签署，但 Host 达单核 11.18%，未满足 2% 等待参考线。原始轮次 `time-http-idle/` 保留，不能因脚本打印 HTTP 合同 PASS 而判 CPU 通过。

修复两处：

1. 下一期限只读提示使用应用注入的 UTC/进程身份/单调计数。相同进程按单调差值筛选，不同进程按 UTC/倒退条件筛选；当前页与调度提示使用相同规则。新增有界等待索引。到点后仍重新读取权威状态及版本，不以显示行授权停止。
2. Workflows 阶段沿用项目事件游标和一秒空闲退避；新提交立即打破退避。已封存的 needs_reconciliation 不因旧 stop 标记永久变成就绪；直接父执行 stop 会唤醒子根，确保未选择新政策的 Human 等待也能停止。

中间候选 `c18de3424a7cae7a39e92a6834455819d375bb39a6f433f20f5c2e386461a242`，同样两项目、一个已超时根加一个 Human 等待根，60 s CPU 为单核 0.85%，窗口采样 RSS 最大 90592 KiB。最终候选为单核 0.40%、窗口采样 RSS 最大 92672 KiB，预算及步骤版本不变、0 签名/未撤权 writer，三库完整性通过；原始记录为 `time-http-idle-v3/`。完整结果见[性能结果](PERFORMANCE.md)。这些都是本机单场景诊断，不代表参考机/长历史/多前端容量。
