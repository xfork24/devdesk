# DevDesk 工作台与存储性能优化计划

P0、P1A–P1C 和 P2B 已通过阶段验收。P2A 已完成开发与本机诊断，正式容量验收待独立负载环境。P3 当前决定保留 SQLite 项目库及同库读投影。各阶段的基准、结果与回退见实施记录。 [工作台延迟评估](../../design/performance/workbench-latency-2026-11-23.md) · [实施与验收记录](VALIDATION.md)

## 一、目标与范围

沿用单 Host、按项目分库的 SQLite 架构。先缩小页面读取范围和重置准备成本，再用持续工作流负载验证写事务、连接池与 WAL 是否仍有瓶颈。独立读库和 PostgreSQL 各设验证条件，按实测结果决定是否进入选型阶段。

以本轮修复后的 Release 构建作为实施前基线。报告中同一项目样本的上下文、材料、执行记录 RPC P95 分别为约 91、123、95 ms。经理协作浏览器 P50 为 391 ms，重置单次成功样本为 5.04 秒。这些是前次测量结果，P0 将按以下验收口径重测并冻结基线。

继续使用现有工作流派发、审批、版本校验与证据规则。工作流读取以确切实例、执行轮次、冻结计划及原产物为依据。运行中或已完成的实例继续使用自身的冻结定义。展示读层可重建，审批、接纳、重试、权限和发布仍在权威库验证当前版本和证据。

## 二、实施顺序

| 阶段 | 工作 | 阶段交付 |
| --- | --- | --- |
| P0 | 固定数据集、自动化基准和分段计时 | 可重复运行的基准，版本与数据身份，含错误的分布报告 |
| P1A | 上下文、材料和执行记录的项目内读投影 | 索引、增量维护、历史回填与并行对照结果 |
| P1B | 项目经理首屏与历史详情按需读取 | 轻量首屏、当前待操作证据、历史分页及单项读取 |
| P1C | 模板重置源依赖索引及可恢复发布 | 按确切修订筛选受影响历史、进度查询及恢复验证 |
| P2A | 调整读预算、连接池与 WAL 运维，完成容量验收 | 并发矩阵、故障回归、实测瓶颈归因 |
| P2B | 按页面拆分 Web 入口，复用配置目录索引 | 分包、冷导航与精确选择回归 |
| P3 | 按门槛评估独立读库或 PostgreSQL | 保留现状或进入原型的决策记录。满足条件时再制定迁移方案 |

P0 完成后，P1A、P1B 和 P1C 可分别实施和验收。P2B 可沿用 P0 的浏览器基准。正式容量验收使用已完成 P1 与前端拆分的同一构建。每阶段记录基线、结果、遗留问题与回退办法。

### P0 · 性能基准与分段归因

- 冻结源码及工作区改动、Release Host 和 Web 资源哈希、SQLite 版本与参数、主机预算和数据规模。使用已有匿名化测试数据或真实数据的隔离备份。用正常写入入口生成满足约束的 1×、10×、100× 历史数据，分别扩大同一 Feature 历史和同库其他 Feature 历史，观察不同查询的增长来源。
- 将上一份报告的页面与 RPC 矩阵纳入基准。增加材料原文、经理历史展开、待审批证据、Feature 切换与清空、模板重置和重新连接事件流。冷 Host 启动、冷浏览器首访、热查询命中与未命中缓存分别记录。每组延迟分布至少 30 次，保留原始样本、P50/P95/P99、最大值和失败数。重置测量前从同一备份恢复初始状态，并分别测量保留自定义、完整重置、相同命令重放和实际无变化的请求。
- 在现有性能跟踪中补齐浏览器导航和可操作时刻、RPC 排队、连接池等待、SQL、外部正文 IO、Rust 解码、序列化与写事务。在重置上另外记录各库的准备与提交时间、已同步库数和最终完成时间。嵌套区间按包含关系展示，日志只记录时序、计数及必要身份。

### P1A · 工作流读投影

- 复用现有 `workflow_display_headers` 和 `workflow_display_steps`，在项目库补齐可索引的工作归属和读路径。投影按 Project、Feature 或 Task、根与子流程、计划版本、执行 ID 与轮次关联。上下文投影保存执行到会话及轮次的关联，材料投影保存执行到产物、交付修订与端口的关联，执行记录投影保存状态、时间和历史轮次。行内仅保存目录所需的短字段和确切引用。
- 在现有资源提交事务维护变更行，覆盖创建、执行推进、重试、计划调整、配置重置和删除。优先用现有索引按作用域定位再分页。正文、Spec、快照和公开回执在用户打开时按精确 ID 读取，目录搜索和深链接保留现有筛选、排序和作用域语义。
- 新装数据集按新逻辑生成投影。既有数据集如需新增表、列或索引，纳入仓库已有显式迁移流程，明确支持的 project 60/61 路径及新版本号。回填分批并记录游标，补齐回填期间的变化后校验行数、持久化引用和事件位置，再启用新投影。对已支持但未完成投影的库继续提供已有的有界读取路径。支持从权威事实重建，并在损坏、缺页或游标落后时给出可识别状态。
- 在同一快照上对照旧读路径的行及排序，覆盖子流程、重新运行、已归档 Delivery 和 Spec、手工材料、跨项目拒绝、重置后的历史及分页边界。验证库内无关历史从 1× 增长到 100× 时，首屏仍以当前作用域定位。另测增量维护的写入耗时、数据库与 WAL 增量。

### P1B · 项目经理首屏和历史按需读取

- 复用现有经理、编排及驱动摘要，首屏显示当前状态、阻塞、进度和待处理事项。对当前待处理审批或接纳，按需取得确切决策、当前资格和必要材料后启用操作。原有 RPC 的完整查询契约继续服务已有调用者。
- 已处理决策按稳定游标读简表，只显示识别一次决定必要的状态、时间、步骤与结果。用一批有界查询取得该页签署记录和材料摘要。展开某项才读取原正文、材料出处及精确决策。优先复用现有确切读取入口并补足作用域验证。切换项目、Feature 或收起时取消可撤销的请求，迟到响应只更新原作用域。当前待处理决定始终独立于历史页的游标。
- 验证首屏、进行中的审批、过期审批、接纳、已签意见、子流程操作和材料深链接。记录可操作首屏、当页必需内容及展开历史的延迟。核对请求日志，确认首屏读取的历史正文条数为零，展开单项只读该项所需数据。

### P1C · 模板重置索引与恢复

- 写入源依赖时记录确切修订、消费者、相关内容摘要和编解码版本。区分已索引且无依赖、已索引且存在依赖、索引覆盖未知。验证嵌套源引用、外部正文、字面值和需要恢复的传递依赖。重置按实际移除或改变的确切来源挑选候选。未知范围走现有保守扫描，由回填和对照逐步缩小。
- 利用现有全局重置回执和项目同步，在全局库持久化重置代次与各库的待应用工作项。各库对同一代次幂等准备与提交，准备在前台读取连接池之外，提交前校验原基础版本和必要资源。进度区分全局已提交、项目应用中、全部完成及可重试故障。项目在本库结果完整提交前继续读其上一代已提交目录。重启后按同一重置命令与代次继续，避免重复生成证据或覆盖并发修改。
- 保持保留自定义与完整重置的原语义。测试准备期间的读写、全局提交后退出、首个项目提交后退出、重放、库暂时不可用、目录版本冲突和正文校验失败。以全部目标库完成为重置延迟终点，另报命令受理和首次进度可见耗时。核对冻结计划、历史 Agent、产物和项目绑定的结果及摘要。

### P2A · 并发、连接和 WAL

- 在 1、4、16 个活跃页面下阶梯加压，同时测普通读取、事件流、重置和持续 Run 写入。采集连接借用、实际 SQLite 锁等待、事务占用、checkpoint 进度、WAL 大小、调度饥饿和错误。先用指标确认饱和点，再调整项目与查询预算、维护连接及 checkpoint 策略。常用读预算按作用域和页大小约束，避免单个历史查询耗尽读池。
- 最终按现有 [100 前端验收合同](../single-host-concurrency/ACCEPTANCE.md) 的数据规模、资源、持续时间和 W1/W2 场景验证同项目热点、多项目、突发、重连与长跑。确定性端口用来复现竞态，真实本机工作流用专用数据集、实际 Docker、Git 与回执接纳。分别记录本机性能、外部运行耗时和缺失场景。

### P2B · 页面分包与目录复用

- 先分析生产构建的依赖和请求时序，按项目管理、基础组件、流程规范等页面边界拆分代码。共用导航、当前项目和执行页首屏入口保持轻量。用项目、目录版本与筛选条件复用已有索引请求，选中定义后再读确切正文。切换项目或采纳新模板代次时按作用域失效。
- 使用 Release 单二进制验证资源路径、冷导航、浏览器前进后退、直接深链接、确切版本选择、清空 Feature 和目录更新。比较主入口 gzip 大小，首访实际下载总量、脚本解析和页面可操作时间。阶段目标是主入口由约 191 kB gzip 降至约 135 kB 以下，同时保持关键页面的冷导航 P95。

## 三、验收口径

| 验收项 | 目标 |
| --- | --- |
| 上下文、材料和执行记录 | 1×、10×、100× 样本的普通首屏热读，各 RPC P95 ≤ 150 ms。深页与全文筛选单列，并通过查询计划核对无关历史的影响 |
| 项目经理 | 1× 浏览器热导航的当前状态、阻塞及当页必要操作可用 P95 ≤ 300 ms。历史单项展开单列 |
| 模板重置 | 同两项目样本完整重置 P95 ≤ 3 s。重置期间前台关键读 P95 ≤ 150 ms。首次有旧历史回填与已建立索引后的结果分别报告 |
| 100 活跃前端 | 沿用既有合同。普通读 HTTP P95 ≤ 200 ms，执行与交付首屏 P95 ≤ 1 s，读连接等待 P95 ≤ 10 ms，标准负载 `storage_busy` 为零 |
| 数据正确性 | 原文与事实可按原身份核对。跨项目泄露、丢失更新、重复副作用、旧版本误审批为零。历史回填和重启恢复通过 |

每阶段记录性能与正确性两组结果。延迟未达标时保留实际分布、归因和受影响场景。隔离副本上的局部通过与正式容量通过分别标注。

## 四、存储选型与发布回退

| 决策 | 何时进入 | 原型或发布验收 |
| --- | --- | --- |
| 保留 SQLite 项目库及同库读投影 | 作为首选实施方式。按 P1、P2 测量，并量化读与写的成本 | 支持正常维护和显式迁移，符合延迟、写入与恢复验收 |
| 试验独立本地读库 | 完成同库投影后，读投影占用、历史重建或读快照对主库的写入、WAL 或恢复仍产生可复现的干扰 | 以主库已提交事件推进游标，验证断点、重放、重建和可见滞后。只把展示读取导向读库，动作资格仍向主库核对。与同库投影比较延迟、磁盘、重建时间和运维复杂度 |
| 试验 PostgreSQL | 有明确的多 Host 或远程共享状态需求。另一触发条件是优化后仍能在相同负载的多轮测试中将超标归因到同库写竞争 | 用相同数据、负载与持久化要求比较部署成本和尾延迟。验证事务隔离、项目范围、版本见证、命令回放、作业递交、备份恢复与产物引用 |

按项目启用新读路径，验证一个历史库和一个持续执行库后扩大范围。保留旧有界读路径作为观察期回退，并区分读路径回退与数据库版本回退。发布前在副本验证备份恢复和迁移失败恢复。已有新写入的库按实际兼容性决定修复或导出恢复，恢复点与后续写入逐项核对。
