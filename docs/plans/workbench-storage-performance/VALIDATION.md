# 工作台与存储性能实施验收

## P0 基准

基准使用生产 Release Host 和构建时嵌入的 Web。运行器逐个比对 Host 实际提供的资源及磁盘构建哈希，记录 Git HEAD、工作区文件摘要、二进制、数据集文件、SQLite 表计数和机器身份。数据集由含外部正文与产物的隔离备份提供。运行时在独立副本上启动生产调度器，从本机环回访问。

每个常规组默认采样 30 次。保存原始时延、请求身份、响应字节、结果哈希、错误和最近秩 P50、P95、P99 及最大值。浏览器区分全新 BrowserContext、已有 BrowserContext 的文档导航和应用内热导航。冷 Host 采样重新启动进程，保留操作系统文件缓存。RPC 找到 Host 的实际显示缓存标记再汇总命中和未命中。已有浏览器文档与热导航还验证历史展开、原材料正文、Feature 切换及清空。

Reset 样本从同一带自定义定义的检查点备份克隆。每轮核对保留自定义、完整重置、同命令原回执及新命令无变化四种结果。完整重置在返回后核对各库目录代次，另外可与 1、4 或 16 个前台读并行采样。单独的待审批夹具使用真实控制步骤和人工确认前置条件，验证当前决定、确切证据和可操作按钮。

Host 使用 `DEVDESK_PERF_LOG=1` 记录 RPC 排队、派发和序列化，以及 SQLite 连接预算、借用、锁等待、列表 SQL、正文 I/O、摘要校验和 JSON 解码。嵌套区间以路径保留包含关系。重置准备按数据库路径摘要记录，提交和回滚边界保存在各库事务记录中。事件流共享尾读也记录阶段和事件数。

### 复现入口

先构建生产 Web 与 Release Host。在仓库根目录使用已检查点的独立备份和一个尚未存在的输出目录。通过实际备份填写项目、Feature、根流程和可切换 Feature 的身份。

```bash
npm --prefix web run build
cargo build --release --locked -p devdesk-host
python3 tests/performance/workbench.py \
  --host target/release/devdesk-host --web web/dist \
  --dataset "$workbench_backup" --output "$workbench_evidence" \
  --project "$workbench_project" --feature "$workbench_feature" \
  --root "$workbench_root" --switch-feature "$workbench_switch_feature" \
  --samples 30 --freeze-source
```

在同样的备份上准备历史分组。1×、10×、100× 缩放的是经正式命令创建并取消的控制工作流根及其步骤历史。分别扩大选中 Feature 和同库另一 Feature。真实材料、Agent 上下文与归档证据使用代表性备份，倍率结果仅覆盖控制工作流的根与步骤历史。

```bash
python3 tests/performance/seed_workbench.py \
  --host target/release/devdesk-host --web web/dist \
  --dataset "$workbench_backup" --output "$workbench_growth" \
  --project "$workbench_project" --scale 100
```

每组的同名 JSON 提供所选 Feature、根流程及实际生成的历史列表。将对应备份和身份交给 `workbench.py --run growth --samples 30`。使用 `approval` 备份、对应身份和 `--approval-root` 运行 `--run approval`。前台读取与重置混合采样使用 `--run reset --reset-readers 4`。

当前缺少独立负载机。本机协议测试验证了 100 个客户端的真实 HTTP/SSE 调用、十项目重连和工作流持续推进，并提供浏览器阶梯诊断。正式结果仍需按[100 前端验收合同](../single-host-concurrency/ACCEPTANCE.md)取得独立环境的 W1/W2 协议与 100 BrowserContext 双层矩阵。矩阵还包含限速与断网、重复场景、多项目切换、60 分钟运行、分窗口资源门槛和合同规定的全量正确性用例。单机短窗口和实际 Docker/Git 证据均作为本机诊断归档，正式容量状态仍待验收。

## P3 存储选型决定

保留单 Host、按项目分库的 SQLite、同库读投影及既有 WAL 自动检查点。审批、接纳及其它版本敏感修改继续以权威库里的确切修订和证据为准。技术选型使用目前已完成的本机实测，正式 100 前端容量仍按独立验收合同判断。

独立读库的进入条件是同库投影或长读快照对提交、检查点或恢复持续产生可复现的干扰。当前观察到的十项目重连饱和已在同库布局、连接上限和 SQLite 超时原值下修复。重连复测写事务 P95 为 1.58 ms，负载停止后各库检查点均追平。历史正确性和两次重置崩溃恢复在同库方案通过，当前先保留同库投影。若正式负载复现长快照阻塞检查点或投影恢复拖慢权威写入，用相同数据和负载再比较独立读库的滞后、恢复和磁盘成本。

本计划的范围仍是本机单 Host 和项目独立权威库。当前没有多 Host 共享权威状态需求，也没有修复后多轮验证仍稳定归因于同库写竞争的证据，因此本轮不启动 PostgreSQL 原型。若确认远程共享权威状态需求，或正式验收多轮测得同库写锁主导超标，再按计划的事务、接纳、备份与回执条件启动对照验证。

回退按兼容范围使用冻结的 Host/Web 构建。旧布局可打开并通过保守扫描重置。已显式迁移的项目如需回到旧布局，使用已验证的迁移备份或导出，并核对迁移后的写入。展示投影可单库重建，临时失效时使用已有的有限作用域读路径。本轮验证均在隔离副本上执行。
