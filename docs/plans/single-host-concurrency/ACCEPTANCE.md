# 工作流运行时 100 前端并发验收合同

状态：验收设计，基础合同测试已有部分实现，完整负载矩阵与正式验收待实施。适用于 [单 Host SQLite 底层并发重构方案](PLAN.md) 的 P0–P6。本文规定必须执行的测试和通过条件，不是测试结果。

## 一 验收对象与参考环境

一个受测 Host 管理同一份专用数据集，使用本机 SQLite 全局/项目/讨论库、实际 HTTP/RPC、鉴权、SSE 和已构建 Web。不能通过多个 Host、内存权威存储、关闭调度器或增加请求超时满足标准。

正式性能基准使用 release Host 与 production Web；冻结源码及未提交改动的内容身份、Host/Web SHA、SQL 基线、SQLite 版本和编译选项。debug 用于定位，不作为正式容量通过依据。

参考宿主资源为至少 8 个逻辑 CPU、16 GiB 内存和本地 SSD。Host 与 SQLite 的预算固定为最多 4 个逻辑 CPU、8 GiB；本机 Docker/Git 工作流使用另外最多 4 个逻辑 CPU、6 GiB，余量留给系统。资源预算可在 P0 按实际参考机冻结，但同一轮前后对比不得改变；更强硬件的结果须另列，不能代替参考预算。macOS/Linux 宿主与其虚拟化开销分别登记，Linux 容器成绩不代表 Linux 宿主验收。

负载发生器和 100 页面浏览器队列放在独立机器，避免把浏览器内存和 CPU 计入或干扰受测 Host。网络使用稳定局域网，记录往返延迟、带宽、丢包与传输协议；本地回环的服务器计时另外保存。若只能同机运行发生器，必须分离并固定资源预算，结果标为辅助诊断，不代替正式参考成绩。

SQLite 开启 WAL 与外键检查，记录实际同步、busy、checkpoint、连接池与缓存参数。不得使用 `synchronous=OFF`、禁用完整性规则、清空历史、停用版本检查或省略证据封存。

## 二 数据规模与构造

所有数据必须满足真实 Schema、外键、不可变源、冻结引用和执行状态机约束。历史数据通过测试工厂与正式用例生成或从允许使用的 SQLite 备份取得，不能把无法恢复的随机 JSON 填入表中。

| 数据集 | 必须包含的规模 | 用途 |
|---|---|---|
| D1 单项目 | 至少 100 个 Feature、2000 个 Turn、10000 条讨论事件、1000 条步骤执行事实及其源、材料、产物和历史；另有持续运行的工作流。 | 同项目热点与全体前端读取同一运行实例。 |
| D2 多项目 | 至少 10 个项目，每项目达到 D1 的历史规模；至少 2 个项目同时推进工作流，全局讨论库有独立历史。 | 每项目 10 个前端、跨项目切换、全局配置和讨论。 |
| D3 历史增长 | 一个热项目至少达到 D1 各历史计数的 10 倍；分页大小与活动工作负载保持相同。 | 判断普通读取是否随完整历史线性退化。 |

数据库、Artifact 和冻结任务关联必须可校验。归档统计各表行数、各类治理记录、数据库/WAL/Artifact 大小、平均/最大正文长度及源修订数量。每次重复测试从相同已校验种子恢复，并记录测试期间新增行数，不能用不同历史量比较优化收益。

现有 `configuration_loading.py` 只能在线备份后关闭调度器测量查询。它可以提供 P0 对照，不能证明工作流运行时容量。

## 三 活跃前端与施压方式

### 两层测试

必须完成两层测试，各自保留结果：

1. 协议层：100 个独立虚拟客户端，分别维护鉴权、项目选择、读版本、命令身份和 SSE 游标。使用开放到达速率发出请求，记录排队和错过的计划发送时间，不能等待前一个慢请求完成后才发下一个来掩盖饱和。
2. 浏览器层：100 个独立 BrowserContext，各运行一个真实 Web 页面、独立 URL 和页面选择。使用实际 UI 读取、保存、导航及事件刷新，RPC/SQLite 不模拟；用语义化页面状态确认可操作，不以 `networkidle` 判定持续运行页面完成。

100 个空闲连接、复制一次响应给多个客户端、一个浏览器页面代表 100 用户、关闭 SSE/轮询，均不满足“100 活跃前端”。浏览器运行器可分布在多个发生器上，但目标只允许一个 Host。

协议负载的稳态目标为合计每秒 100 个业务读取和 10 个业务修改；额外记录 SSE 补读、页面自动请求及后台提交。浏览器负载为每页每秒一次读取/局部刷新动作、每 10 秒一次修改、每 20 秒一次页面导航，按固定种子错峰。若动作被合并，记录实际动作和 RPC 数，必须仍达到 100 次读取动作/s、10 次修改动作/s 和 5 次导航/s，不能靠停用用户动作减少负载。

读取使用当前执行摘要、驱动/阻塞状态、实例步骤页、讨论增量、历史/材料分页、配置详情等真实组合。修改覆盖独立 Feature 材料、工作配置、全局设置、讨论追加、权限/接入绑定与允许的运行控制；不得全部选择无状态 no-op。权限或前置状态不允许的动作在构造阶段替换成合法动作，不能把大量业务拒绝当作写入吞吐。

普通稳态为各客户端分配不重叠的修改目标；全局设置等单一共享目标由指定客户端操作。对同一对象的有意竞争放入 L5，不能让负载生成器制造大量版本冲突后仍声称完成了 10 次成功修改/s。

建议固定读取权重为执行摘要 30%、步骤/驱动 20%、讨论增量 15%、材料/历史 15%、配置/项目目录 20%。写入权重在 P0 清单冻结后覆盖全部资源族，热点冲突另作专项，不混进普通成功率来隐藏失败。

### 必选负载矩阵

| 场景 | 客户端分布与动作 | 必须验证 |
|---|---|---|
| L1 同一运行实例 | D1，100 前端观察同一热项目/工作流，按稳态频率读取，修改不同的合法目标。 | 高命中视图、并发读、事件分发及同项目写竞争；不能依靠分库分散热点。 |
| L2 多项目独立上下文 | D2，每项目 10 个前端；其中至少 10 个前端每 5 秒轮换一次项目，其他前端保持原项目。 | 切换不影响其他页面；原项目写入、订阅、历史与产物继续正确路由。 |
| L3 同步读取突发 | 稳态负载中，每 10 秒使 100 个客户端在 100 ms 内请求同一执行摘要，共 30 轮。 | 并发许可、请求合并、首个和最后一个请求耗时；不能出现按客户端数阶梯增长的业务锁等待。 |
| L4 独立目标写突发 | 同一项目内，100 个客户端在 100 ms 内分别修改 100 个已读取版本的不同对象，共 30 轮。 | 全部最终提交成功，没有由项目全局版本产生的错误冲突，无丢失更新。 |
| L5 同目标竞争 | 100 个客户端用同一基版本、不同 command ID 修改同一对象；另测同 ID 重放和跨对象批次。 | 恰好一个提交，其余明确版本冲突；重放与批次原子性正确。 |
| L6 历史增长 | D3，重复 L1、L3 和稳态混合负载。 | 相同页大小下的读取、响应大小和内存不随整库恢复成本增长。 |
| L7 重连与慢订阅者 | 100 前端中 10 个断网/限速/重连，其他前端保持稳态；循环 10 次。 | 恢复游标、无跨项目事件、慢客户端不拖慢提交与其他订阅者。 |
| L8 长时间运行 | D2，100 活跃前端和持续工作流运行 60 分钟，周期性切页/切项目。 | 有界内存、连接、WAL、队列和历史增长；无资源泄漏和调度饥饿。 |

L4 是有限突发，不以强行维持 100 写/s 作为本轮稳态要求；所有 100 次写入仍必须在突发完成时限内成功，不能被限流丢弃。L5 的预期冲突不计入存储故障，但必须统计冲突响应时延与最终状态。

## 四 工作流持续推进的证明

负载开始前工作流必须已进入可推进状态。测量期间至少保持一个根实例活跃，并持续产生实际派发、运行、产物封存和回执接纳；不能只保留 `running` 标签、等待人类审批或暂停在同一步骤。

必须分别完成以下两种运行：

| 运行 | 执行边界与用途 |
|---|---|
| W1 可重复推进 | 同一源码的 release 测试入口运行真实 Host/core/调度器/SQLite，使用只编译进测试的确定性 Harness/工具端口控制事件时序和失败；用于稳定复现并发与故障。不得在产品中增加模拟模式。 |
| W2 真实本机执行 | 同一源码的正式 release Host 和 100 前端负载下，专用仓库、实际 Docker worker、Git、工具动作、Artifact 与回执接纳持续运行。可使用不调用付费模型的合法 Tool Workflow；不能只用直接写终态的夹具代替执行。 |

W1 与 W2 均为容量必选，各自冻结二进制身份并完成协议层和浏览器层的必选场景；不能只做 W1 就标注“真实工作流运行通过”。付费模型/GitHub 另行显式验证，外部服务耗时不作为本机 RPC 延迟，但其观察与接纳开销必须保留。W2 使用专用测试仓库和数据集，不操作当前用户运行中的工作流。

固定执行并发预算，保持至少 4 个可执行工作项在测量期内持续流转，可由多个有界工作流顺序接续。W1 平均每秒至少 2 次工作流状态提交；W2 平均每 5 秒至少完成 1 次真实工具/worker 执行，并持续出现派发与接纳。测试期间若可推进工作断供，受影响测量窗口无效，不能计入通过时间。

使用相同工作流、历史规模和资源预算先测 0 前端运行基线，再测 100 前端。记录每个执行 ID 的就绪、派发、外部开始/结束、回执观察和接纳时间，不以 Agent 自述或 UI 状态代替真实回执。

## 五 延迟 吞吐与资源门禁

下列指标用于 100 前端稳态的 L1、L2、L6，以及 L8 每个连续 5 分钟窗口。按方法/页面与场景分别计算，不能只公布所有请求混合后的平均值或百分位。

| 指标 | 必须达到 |
|---|---|
| 核心摘要、驱动状态、普通分页读取 | HTTP 端到端 P95 ≤ 200 ms，P99 ≤ 500 ms。 |
| 普通修改的持久化确认 | P95 ≤ 300 ms，P99 ≤ 1 s；长操作测意图提交，不把外部执行时间计入该确认。 |
| 执行与交付首屏 | 从点击导航到当前工作主要状态和可用操作显示，P95 ≤ 1 s，P99 ≤ 2 s；冷启动单列。 |
| 常规冲突响应 | P95 ≤ 300 ms，P99 ≤ 1 s；不得在冲突前等待整个其他命令处理链。 |
| 正常事件收敛 | 提交到所有在线可见订阅页面显示相应版本，P99 ≤ 1 s；无故超过 3 s 直接失败。 |
| 重连收敛 | 网络恢复并重新鉴权成功后，P99 ≤ 3 s，游标补读或视图恢复后不丢最终状态。 |
| 持续输入完成率 | 计划读取/修改/导航动作完成率 ≥ 99.9%；未发送、排队超期、超时、连接失败也计入失败。 |
| 业务与存储正确性 | 丢失更新、串项目、重复外部派发、未提交状态可见、意外版本冲突均为 0；标准负载暴露的 `storage_busy` 为 0。 |
| 后台推进 | 相同预算下，工作流完成吞吐 ≥ 0 前端基线的 80%；就绪到本机派发 P95 ≤ 1 s，无可推进工作因前端持续饥饿。 |
| SQL 与连接等待 | 读连接等待 P95 ≤ 10 ms；写事务占用 P95 ≤ 10 ms、P99 ≤ 25 ms，技术竞争单独记账。 |
| CPU | Host P95 使用量 ≤ 其固定 CPU 预算的 70%，不能持续占满预算；worker 使用量独立统计。 |
| 内存 | Host RSS 峰值 ≤ 2 GiB；缓存预热后 L8 后 30 分钟增长 ≤ max(128 MiB, 预热后 RSS 的 10%)。 |
| 连接与队列 | 不超过冻结配置的全局/每库上限；活动客户端数量不线性放大数据库连接和历史扫描任务。 |
| WAL | 单热库 WAL ≤ 256 MiB；停止写入后 30 s 内可回收到 ≤ 16 MiB，持续订阅不得永久阻碍 checkpoint。 |

SQL 占用与 RPC 耗时中嵌套 span 不能直接相加。pool/busy 等等待、SQL 执行、解码、历史恢复、业务计算、序列化和网络分别记录；缺少阶段证据的成绩不用于判定瓶颈已解决。

L3 的每轮 100 个读取全部在 1 s 内完成；L4 的每轮 100 个独立对象写入全部在 2 s 内成功；L5 的全部提交/冲突响应在 2 s 内完成。突发窗口另计，不能删去最慢样本，也不能拿突发专用时限放宽稳态 P95/P99。

正常执行摘要响应 ≤ 64 KiB，普通列表页 ≤ 128 KiB，不携带整套计划、全配置目录或全部正文。大正文/原始 JSON/Artifact 按需请求并单列，不混进摘要大小指标；其并发读取也不得持有全局业务锁。

所有普通首屏/状态/列表查询必须满足完整工程快照次数为 0、Workflow 编译次数为 0、业务写事务次数为 0。事件订阅的数据库扫描按作用域复用；从 1 到 100 个订阅者不能增加为 100 份相同历史扫描。

冷进程与冷浏览器首访分别至少采样 30 次，执行页主要状态 P95 ≤ 2 s。固定进程已完成合法启动/恢复；启动本身的耗时单独报告，不能把正常页面查询重新触发的恢复归入启动以绕过首屏门禁。清缓存方式与操作系统文件缓存状态如实登记，不混称完全冷启动。

## 六 正确性必选用例

| 编号 | 用例与通过条件 |
|---|---|
| C1 独立选择 | A/B 前端分别选项目 P/Q；A 连续切换后，B 的 URL、显示、草稿、后续 RPC/SSE/Artifact 仍属于 Q。覆盖 100 前端及新标签页。 |
| C2 显式范围 | 每个项目入口缺少/错误项目 ID 必须拒绝，不回退到别的项目；全局配置与全局讨论不可混用。 |
| C3 所有修改入口 | 从入口清单逐项测试缺失前置条件、错误版本、正确版本、重复命令和不同参数重用；任何未覆盖修改入口阻塞验收。 |
| C4 同版本竞争 | 用屏障同步 100 个不同命令修改同一版本，恰好一次提交、99 次 `revision_conflict`，资源版本仅增加一次；使用单对象单事件测试命令时，只产生一个业务变化事件。 |
| C5 独立对象 | 同项目 100 个不同对象用各自正确版本并发修改，全部成功；全局对象变化不使无关项目/对象冲突。 |
| C6 创建与唯一性 | 同身份同时创建仅有一份对象；不同身份并发创建不发生错误覆盖。版本 0/absent 条件与唯一索引在提交时生效。 |
| C7 幂等 | 100 个相同 command ID/指纹并发请求得到同一结果或同一 operation；业务、版本、事件和外部副作用只产生一次；检查早于旧版本拒绝。 |
| C8 多对象与写偏差 | 两个请求竞争活动轮次、当前 head、配额、依赖或授权；成功提交始终满足整体业务约束，失败无部分写入。 |
| C9 回滚与可见性 | 在 SQL 更新、事件写入、幂等登记及 commit 边界注入故障；读者只看到完整旧版或完整新版，失败不发布成功事件。 |
| C10 长操作与回调 | 准备/取消/后继安装或凭据意图并发，迟到 OAuth/worker 回执不能覆盖后继；重启核对未知效果，重复回调只消费一次。 |
| C11 快照与视图 | 单次响应的内容与版本对应；跨库标注独立版本；旧快照完成后释放，不把过期视图作为执行授权。 |
| C12 前端编辑 | 自动刷新、迟到响应、路由切换与重连不覆盖草稿；保存使用原编辑版本，冲突保留输入，不自动换新版本重提。 |
| C13 SQLite 竞争 | 注入 `BUSY` / `BUSY_SNAPSHOT` 与 checkpoint 压力，重试有界、事务正确结束，不能跳过原前置条件或使用长业务锁。 |
| C14 恢复 | 测试 Host 提交后、通知前崩溃并重启；事件可补读，已提交回执可重放，已发生外部作用不重复派发，客户端重新握手不采用旧 Host 生命周期令牌。 |
| C15 冻结与权限 | 源/计划/授权并发更新后，历史仍按原确切引用恢复；新动作验证权威权限与控制代次，缓存命中不放宽准入。 |

C4–C8 使用至少 30 组独立目标/种子重复执行，不能仅靠顺序调用制造“并发”。故障恢复与终态用专用数据集，不中断用户正在执行的 Host。

在测试中延迟某个长命令的事务外编译或外部轮询，期间其他读必须继续完成；在短写事务竞争期间，独立 WAL 读快照仍可读取旧的已提交版本。单纯检查“删除了某个 Mutex 字段”不构成并发证明。

## 七 测量流程与统计

每个必选性能场景按以下顺序运行，构建、数据生成和正式采样不并行：

1. 校验构建身份、参考机资源、数据集清单、SQLite 配置、空闲外部任务和工作流实际准备状态。
2. 从固定种子建立专用数据集，运行 0 前端工作流基线，至少 10 分钟；记录完整推进与资源数据。
3. 以 1、2、10、25、50、100 客户端逐级增加，每级 2 分钟定位拐点，不用逐级结果代替稳态验收。
4. 在 100 客户端下预热 5 分钟，正式稳态至少 20 分钟；在此窗口中安排规定的读取/写入突发。每个场景独立运行至少 3 轮，从相同种子开始，全部通过才算通过。
5. 浏览器队列为每个核心导航累计至少 1000 个有效点击样本，分别报告点击到内容、点击到操作可用、请求瀑布与主线程长任务；完成 L2、L7 的切换/重连证明。
6. 独立执行 L8 的 60 分钟测试，保留所有 5 分钟窗口指标；结束后验证 checkpoint、数据库完整性、Artifact 摘要、孤立操作/租约及实际 worker 停止/清理。

开放到达采样必须记录预定发送、实际发送、首字节和完成时间。没有发出的计划动作、排队过期和失败响应都进分母；服务端分位数与客户端端到端分位数分开，不能只统计成功响应，也不能用合并所有方法的总体分位数掩盖慢方法。

正常流程中的长操作只计算意图持久化确认延迟，并另列执行完成时长、事件观察和接纳延迟。预期冲突、业务拒绝、技术竞争、传输失败和超时分别分类，不能互相抵扣。

## 九 通过与失败判定

P6 只有在 L1–L8、W1/W2、C1–C15、延迟/资源门禁和对应全量回归全部通过后才能完成。各场景的 3 轮均须通过，不能选择最好一轮。出现数据正确性、执行授权、重复副作用或持久化问题时直接失败，不由较快的平均延迟抵消。

失败报告必须保留具体资源、请求阶段、SQLite 占用和工作流证据。改变参考硬件、负载、历史规模、缓存、工作流预算或重试参数后是新一轮测试，须重新冻结身份并报告，不回写原失败记录。当前文档交付不包含实际 100 前端测试结果。
