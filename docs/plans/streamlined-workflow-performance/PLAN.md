## 后续性能提升顺序

### 1. 先控制审核响应与建立可重复对照

最终样本 Human 共 71.108 秒，其中最终人审 60.910 秒来自本轮响应等待，仍计入成绩。后续使用事件通知、确切材料提前审阅和及时签署，避免读取结果不及时；实际签名仍绑定当时的候选与原件，不预先批准未知版本。

只将最后一道等待改为约 3 秒，按本轮区间估算墙钟约 664.080 秒；这是诊断估算，未经新完整样本验证。即使人工总等待控制到约 10 秒，自动路径仍需从 650.882 秒减少到约 590 秒，即还需约 61 秒（9.4%）的自动关键路径收益。

后续同条件先做少量重复样本，报告中位数、范围、失败和全部原始记录；少量样本不计算正式 P95/P99，也不以一次较快结果保证稳定达标。

### 2. 优先处理业务 SDK 的重复生成

最终互斥业务 SDK 为 382.335 秒，占墙钟 53.0%；独立测试49.412秒、实现62.220秒、五份独立评审合计188.045秒。先测实际工具调用前后、lint 到最终提交的生成区间，区分上下文、工具、生成与未知区间。

优先用现有引用和紧凑格式减少同一报告重复输出。若测量证明 lint 后重写是重要成本，再设计已校验草稿的引用式交付；当前未实现。设计须绑定原 Turn/Session、端口、Delivery/Spec、输入摘要及计划，保留正文、来源和历史可读，提交时重验并拒绝过期或跨执行引用。不能以摘要替代必需内容或减少独立评审。

退出条件为相同模型、需求及预算下的单步骤成对记录与全部负向回归，再验证完整链路；字节变少不等于延迟已改善。

### 3. 继续测量剩余经理接力

经理已从历史38轮降到11轮；最终 SDK 累计250.239秒，互斥部分172.815秒（23.9%）。剩余包括4次人审请求、子流程与根完成判断，不能把11轮全部视为冗余。先量化真实决策与仅搬运冻结参数的区间。

只在有收益依据时考虑进一步的条件委托或请求准备复用；必须由经理显式授权确切范围，保留实质判断、独立评审和实际 Human 签名。当前仅已实现人审节点的执行及签署后接纳委托，没有自动创建人审请求或自动签署。现有失败、输入、控制/计划变化、新实例和撤权通知继续保留。

### 4. 可选模型对照独立报告

`gpt-6.2-sol/low` 仅准备过本地配置草案并做目录检查，未构建、未运行或取得性能结论，草案已撤回。后续如继续，先核实实际能力和单步骤质量，再用相同需求、图、权限、预算及全部门禁做独立完整对照，核对实际原生请求中的模型身份。模型收益与软件收益分列，未经验证不更换当前默认模型。

### 5. 平台尾部、恢复与容量分别推进

平台互斥区间59.959秒（8.3%），普通树读取 P95 12.726ms、26次混合原生往返 P95 139.485ms。先做 Git/网络/轮询归因，再决定尾部优化；保留 lease、未知效果 reconcile、保护分支、精确候选、人审和同步。

第五候选的 ENOENT 故障未做完整故障注入恢复重跑：最终轮次证明正常路径避免该错误；schema 提示、计划激活和撤权有定向回归。后续补测试配方错误、参数拒绝、未知副作用、计划冲突、签署后撤权等自主恢复验证，不由外层代改运行数据。

P5 根预算和正式容量作为独立专项。按原合同补稳定等待60秒CPU、丰富长历史/大Artifact、原生T0–T6、COMMIT/SSE/页面版本链及100活跃前端矩阵。当前不排定无归因的 SQL/存储重构。
