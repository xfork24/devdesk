# 精简版工作流性能改进计划

状态：待实施。制定日期：2026-11-19。本轮先退役详细版出厂配置，再执行精简版完整业务基准；本文件安排后续优化，不在此次基准期间修改调度、模型、预算或业务门禁。源码起点为 `ab7bc628389fd57ff0c7e29e6f4f1759fc1938df` 加本轮出厂清理；确切构建、原始计时与限制见 [BASELINE.md](BASELINE.md)，清理和回归见 [EXECUTION.md](EXECUTION.md)。

本计划已随本轮 rebase 衔接远端 `6e33514` 的 Feature 代码投影交付和 Standard 4 / Feature 4 / Task 3。BASELINE 的历史样本仍为原冻结版本，不能据此宣称投影交付已取得相同性能成绩。

## 1. 目标与边界

继续以小型单 Task Feature 完整交付不超过五分钟为业务目标。保留 PRD、设计、Task DAG 的独立评审与 Human 确认、独立 Red/Green、独立代码评审、源版本与合并结果两类真实项目回归、确切版本 Human 合入审核、远端核对和本地同步。降低成本的方式是减少内容与协议重复、经理模型往返及平台空档，不修改通过标准。

完整墙钟从根实例创建到权威 complete 决定，不能以最后步骤 finished、PR 创建或用户点击批准作终点。另报 Human 请求创建到决定提交、外层材料审计、返工、维护和实际外部执行区间；原始总时间始终保留。五分钟业务目标与排除外部人类等待的自动执行诊断值分别判定，不能事后从总耗时任意扣除等待达到目标。没有同条件直接 Codex 对照时，不声称相对执行倍率。

技术指标继续采用 [运行性能合同](../workflow-runtime-performance/ACCEPTANCE.md) 和 [单 Host 并发合同](../single-host-concurrency/ACCEPTANCE.md)：0 前端轻量原生往返 P95 ≤ 200 ms / P99 ≤ 500 ms、就绪到本机派发 P95 ≤ 1 s、外部结束到接纳 P95 ≤ 250 ms、接纳到原生写回 P95 ≤ 100 ms、普通摘要 P95 ≤ 200 ms、稳定等待 60 s Host CPU ≤ 单核 2%。正式每类分位数至少千样本。一次真实 Feature 与观察器 HTTP 抽样不能替代这些门禁。

此次范围为后续性能与可靠性改进，不恢复详细版、不升级旧实例、不删历史源、不更换 SQLite 或增加 Host；不移除人审，不让模型代替 Human，不使用外层脚本替经理派发业务节点，不为凑指标减少测试或跳过失败。

## 4. 分阶段实施

### P0：冻结口径和关键路径

以整合后的当前配置和实际模型为实施起点，保留本次业务需求及单 Task 规模，先完善 profile 的关键路径计算。代码投影改变流程验证材料的路径和最终候选内容，须按当前合同冻结验证材料分布、保留正式项目测试，先建立该交付策略的新基准；本次旧策略成绩继续单列，不把两种策略混为同条件对照。保持本轮已修复的诊断隔离、原请求持久化与显式审核边界，补齐关键路径的观测。聚合并行 SDK/Harness 时间必须使用区间并集；每次交接区分产出结束、结果登记、接纳、经理决策、Human 等待、后继就绪及实际派发；子实例结束到父汇总和根 complete 单列，不能遗漏最后收尾。

保存请求/响应字节、动态工具数、上下文/审计引用大小、SDK Turn 时间与累计 token usage 的实际口径。SDK 包含模型、网络、上下文及工具等待，不是纯推理。观测缺失、时钟边界、工具调用嵌套和失败均入报告。稳定候选完成后再安排必要完整 Feature，不为每个改动反复运行全流程。

退出条件：同一记录可重算完整墙钟和关键路径，互斥分段覆盖全部时间且有解释；没有未计入的历史尝试、尾部或人审。保留原始记录及 SHA，不复制凭据。

### P1：减少生成和评审的重复内容

分析 PRD、设计、计划、实现和各独立评审的冻结输入、实际生成字节、lint 调用及重复输出。为简单任务提供满足相同 Spec 的紧凑内容要求；平台合同、权限、测试执行和 PR 回执由确切引用展示，业务文档只描述本次需求与设计决定。避免先在正文或 lint 参数输出全文、最后再输出同一全文。保持本轮已发布的评审报告 lint 和实际位置指导，测量其正确性与额外模型/工具成本，不放宽来源、摘要或越界检查。

优先复用已存在的输出/Artifact 引用、分块读取与结构检查；若增加引用式交付，必须保持完整内容可读、摘要/Spec/来源验证、过期输入拒绝、评审独立和历史重放，不以只交摘要替代必需正文。冻结后继 Skill/Spec/Delivery/Capability 修订，不覆盖既有源。

验证：固定相同需求/图/模型/预算，先做单步骤成对对照，记录所有样本、失败及总 token/字节；评审能发现原有位置和语义缺陷，结构和来源伪造仍拒绝。内容缩短但模型墙钟没有下降时如实报告，不宣布收益。新旧样本保持独立，最终完整链才判五分钟。若同模型内容/调度优化后串行 SDK 下界仍超过目标，再单列经过能力和质量门禁验证的模型/推理预算策略；不自动降低质量，不把换模型收益混入同模型算法收益。

### P2：减少经理的串行模型往返

对本次每个经理 Turn 按事件和实际动作归类，识别结果/完成/停止相邻通知、已委托的运行态重复 inspect/wait、Human 请求准备、签署后接纳及子流程完成后的父收尾。当前 `metadata_only` 合并和按实例 segment 已存在，先验证实际采用与打断原因。

按耐久事件批次和权威状态提供紧凑的行动材料，减少同一合法进展拆成多次模型请求。审批材料应直接带齐当前评审及其全部必需上游原件，避免本轮设计审批缺少 PRD 直接链接而要求外层另行定位。只能合并同一已授权推进范围内的通知/操作；不得丢失业务失败、输入、停止撤权、Human、计划变化、授权撤销或新版本。模型仍负责业务判断；segment 保持既有边界，异常回流经理，Human 明确排除。不能通过内核按业务 key 自动接纳或给模型加代签权限换取速度。

验证：同一固定图、事件序列和模型预算记录经理 Turn、inspect/wait/accept/dispatch 数、输入字节及关键路径空档；覆盖重启、游标分页、事件重复乱序、已完成子实例、授权撤销和跨根拒绝。保存 R4 的确切 PR 创建事实到经理自主通知链；一次工具返回成功不能当作用户已经收到通知。

### P3：裁剪冻结上下文与原生工具成本

按真实请求测量 developerInstructions、dynamicTools、当前输入、源闭包、恢复消息和工具结果大小；只发送当前角色/步骤实际需要且被授权的工具和有界上下文。恢复同一线程时保留已实施的历史省略规则；新线程、跨会话继承、当前输入、完整审计和原始材料继续可追溯。

优先复用确切摘要和按需读取，避免把全目录、全部冻结源、完整 control 或所有上游文档塞进每次经理请求。引用式上下文仍在提交前核对权威版本、输入摘要和权限；缓存只存不可变源或建议性视图，受条目/字节预算限制。

验证：请求字段逐项字节和工具数对照；工具可达性与权限负向、同线程/新线程/跨会话恢复、历史采用和迟到回执回归。不能只用 developerInstructions 缩小就推断模型延迟下降。

### P4：平台交付和读取尾部

沿 PR 准备、试合并读取、源/目标核对、GitHub 状态报告、合入及本地同步，拆分本机 Git、网络、轮询、持久化与调度。复用确切操作回执和已验证不可变候选，减少重复网络查询；目标/源变化必须重验，未知效果先 reconcile，不重发副作用。保留当前无保护目标的 beforeOid/force=false 与已有保护目标的正常 PR 合入合同；Task 使用开发分支双父试合并，Feature 使用冻结代码投影的单父候选与专用 candidates 分支。投影只剔除流程验证材料，正式项目测试保留，审核与回归绑定实际投影 SHA/tree；不改远端保护、不使用 bypass。

联动 R14：在本次真实完成历史的只读备份及丰富长历史/不同 Artifact 大小上，测有界摘要、execution.inspect、artifact.read 和兼容完整 control。0/1 前端和复杂历史分开；每方法报告大小、样本、失败、P50/P95/P99 与 SQL/编码成本。必要时才进一步处理 R3 的 JSON 扫描/重编码；不得用全量历史恢复、全局写锁或无限缓存换成绩。

验证：合入响应丢失、目标竞争、并发 Task、脏 worktree、重启后仅恢复同步、过期测试/批准、跨项目及幂等回执；技术尾部达到原合同并保存完整输出摘要。网络实际执行与平台残余按逐样本区间计算，不能相减不同分布的 P95。

### P5：补齐预算可靠性

接续 R2/R11 的独立设计：区分模型活动、平台可重复等待、外部事实等待、Human 等待、整根总墙钟和无进展期限，明确各预算起点/消耗/重启/返工与继承。补平台 deadline、watchdog、提交临界点、跨重启时钟异常及停止/回执/合入竞争，再决定默认出厂采用的不可变修订。

验证：可控时钟、真实 SQLite 强制交错、实际 worker 停止/撤权证明。超时不能被视为远端未应用，不能盲重发；技术 retry、返工、计划替换和等待通知不重置总额度。稳定等待 CPU 回归必须独立连续 60 s 采样；不能把经理调用 wait 的次数当作 watchdog 或执行预算正确性证据。

### P6：固定候选整体验收与条件容量

P1–P4 集中完成并通过定向回归后冻结候选，按相同 slugify 需求、单 Task 规模及正式项目测试基线完成一次真正交付，固定当前验证材料分布和代码投影策略；只有同策略、同条件样本才能计算改进幅度。另以小型 DAG 局部链保护并发与依赖解锁；只有局部证据不足才追加完整 DAG。记录全部返工和失败，禁止外层替经理业务推进。比较同条件绝对耗时、关键路径与成本，五分钟未达标继续开放，不把单轮较快当成统计保证。

R6 补实际 COMMIT 返回→SSE→目标页面版本关联和日志开销。R5 正式容量在独立发生器/参考配额、十项目、十倍历史、真实后台及全写资源具备后单独执行原 100 活跃前端矩阵；此次基准与后续单 Feature 验收均不关闭 P6/F6 容量认证。

## 5. 优先级与交付

先 P0 冻结证据，再并行设计 P1/P2/P3，按实际关键路径收益集中实施；P4 基于原生和外部区间排序。P5 属于可靠性主线，不能因性能达标而跳过；R3 结构改造与正式容量以测量和条件为前置。

每阶段交付实现、与风险对应的正负回归、同条件测量及未解边界。最终运行必要的 Rust/Schema/配置/Host/浏览器及风格门禁；配置加载零完整快照/零业务事务与 P95 回归线继续有效。所有源修订、Host/Web/脚本、镜像、数据、输入和模型身份冻结，原始日志/JSON/截图放临时证据目录，计划目录仅保存 Markdown。未经后续明确执行，本计划保持待实施。
