# 架构独立性改造计划：领域无关内核、第二个领域与 SDK

日期 2026-11-26。状态：**待实施**。本计划中的契约、领域和工具都尚未实现，不能当作已有的接口或已通过的验收。范围：把内核改为领域无关，用第二个领域验证抽象，消除三者之间的源码级耦合，并建立版本协商、脚手架和构建独立。不含新增 Harness，不含不可信领域的隔离。

## 0. 结论与范围

### 0.1 什么算完成

| 目标 | 完成的标志 |
|---|---|
| 内核领域无关 | 通用概念留在内核；工程能力是内置扩展模块，领域包声明依赖时才启用；Feature、Task 成为软件开发包的对象类型。内核 crate 的非测试代码里没有工程词汇和任何领域包标识 |
| 第二个领域 | `ecommerce-outbound` 的三个流程可端到端运行，只使用协议核心与内核资源，在未安装软件开发包的 Host 上通过 |
| 消除源码级耦合 | 内核不引用领域目录；领域不引用 `web/src` 和内核内部文件；Web Core 不包含领域代码 |
| 版本协商 | 领域包声明依赖，Host 暴露能力目录，安装期逐项核对，失败时指明缺什么 |
| 脚手架 | 一条命令生成领域骨架；检查、构建、对运行中的 Host 核对依赖都由同一个工具完成 |
| 构建独立 | 领域包只凭 SDK 制品、自身目录、Node 和 Python 就能构建出 ZIP，并由 CI 的独立作业证明 |

### 0.2 已定决策

| 决策 | 结论 |
|---|---|
| 内核定位 | 领域无关。`model`、`harness`、`sandbox`、`skill`、`tool`、`permission`、`workflow`、`delivery`、`spec`、`standard`、`role`、`capability`、`agent` 等通用概念由内核定义，领域相关的必须迁移 |
| 工程能力去向 | 内置扩展模块。Rust 实现移出通用 crate，经通用扩展点注册；Feature、Task 改为软件开发包的对象类型 |
| 兼容范围 | 不兼容。软件开发包随内核重发，旧数据集归档后重建，不写兼容层 |
| 单体测试模式 | 移除并改造测试 |
| 第二个领域 | 电商出库，下单、库房操作、物流配送三个完整流程，纯文档与纯函数 |

决策的来由见[报告](REPORT.md)第 5 节。

### 0.3 非目标

- 不做不可信领域的隔离。领域包被视为可信代码，与内核同源同权限。
- 不放开处理器能力。处理器保持只读、短时、断网。
- 不为电商领域接入真实的电商平台或物流商。
- 不在首版做阶段之间的自动串联。
- 不解决处理器每次调用启动一个新容器的延迟。

## 1. 现状

三者的独立性只在运行期与制品层成立。内核生产代码有两处字面引用软件开发包；领域包协议、内核端口和 Host 的领域 RPC 按首个领域的形状编写；领域 UI 约 96% 的源码在 `web/src`，48 个核心模块被重复编译进领域包；边界没有机器守卫。完整情况见[报告](REPORT.md)。

有两处现状对计划有直接影响：

- 单体模式嵌得很深。`fixture-catalog` 和 `build:fixture` 不只服务于浏览器用例，[check.sh](../../../scripts/check/check.sh) 第 16–37 行里的 6 个 entrypoint 测试也都跑在带工程目录的 Host 上。
- 仓库已有 ZIP 模式的测试基础。[tests/entrypoints/domain_packages.mjs](../../../tests/entrypoints/domain_packages.mjs) 对正式 Host 与正式 Web 运行，[tests/fixtures/domain-packages](../../../tests/fixtures/domain-packages/build.py) 能构建确定性的最小领域包。测试改造以它为基础，而不是从零开始。

## 2. 目标架构

| 归属 | 内容 | 位置 |
|---|---|---|
| 内核 | 配置模型、会话、工作流引擎、权限、存储、对象、证据门禁、处理器运行时、客户端协议，以及这些处理器的工具定义 | `crates/*`、`kernel/core/` |
| 工程扩展模块 | Git、GitHub、测试、代码工作区，以及它们的工具定义 | 工程 crate、`kernel/engineering/` |
| Web Core | 工作台外壳 | `web/src/core/` |
| Web SDK 与组件套件 | 外壳契约；内核概念的通用界面 | `web/src/sdk/`、`web/src/kit/` |
| SDK 制品 | Schema、处理器引导模块、命令行工具、Web 的类型与构建配置 | `@devdesk/domain-sdk` |
| 领域包 | 配置、对象类型、处理器、页面、领域工具 | `plugins/<id>/` |

三个形态决定了计划的形状：

1. **扩展通过同一套接入点。** 工程模块注册自己的处理器、钩子和内核输入；领域包在清单的 `extensions` 里声明依赖。内核按组查找，不认识具体的钩子名。
2. **Web 分两个入口。** 外壳契约很少变化，是领域稳定的目标；配置编辑器和工作流视图随内核演进，与 Web Core 同版本。
3. **领域作者只面对一个包。** `@devdesk/domain-sdk` 同时提供 Schema、命令行工具、处理器类型、Web 类型和构建配置。

## 4. 分阶段交付

每个阶段以门禁结束。门禁不过不进入下一阶段。

### P0 守卫与基线

不改行为。工作项：G-1、G-2、G-4、G-5。基线文档与审计清单已随本计划入库。

**门禁 0**

- 两条守卫进入 `check.sh` 与 CI。架构检查的已知例外清单恰好覆盖审计项 A1、A2。

### P1 协议核心

工作项：G-3，WS2 全部，WS3 的 N-1 到 N-8，WS4 的 S-1 到 S-5，W-5，D-1。内核侧的泛化、协商、SDK 制品和命令行工具都在这一阶段落地，软件开发包第一个迁到新格式上。

**门禁 1**

- 软件开发包以格式 2 构建，清单来自 `domain.json`，构建只调用 `devdesk-domain build`。
- 格式 1 的包被拒绝，错误指明包与 Host 各自支持的协议版本。
- 缺处理器、缺扩展组的包分别被拒，错误指明缺失项。
- 软件开发的交付证据经通用证据门禁生效，既有的领域证据用例通过。
- 内核 crate 中领域包标识为零，已知例外清单清空。
- 出厂 Host 上发布的平台工具定义覆盖全部内核处理器。
- N-8 的结论已记录：无仓库项目的 Agent 步骤可直接运行，或已补上文档工作区。
- 完整检查通过。

工作项：WS5，WS7，S-6，D-1。软件开发 UI 迁到自己的目录，单体模式在这一阶段移除。

**门禁 2**

- Web Core 制品的 import 图不含领域目录。
- 软件开发 UI 从 `plugins/software-development/web` 构建，只依赖 SDK 制品；独立构建作业通过。

**门禁 3**

- 电商出库 ZIP 在独立作业中只凭 SDK 制品构建成功。
- 在未安装软件开发包的 Host 上安装并激活，三个页面可用，项目可凭标题创建和移除。
- 13 个处理器的正常分支与错误分支都有测试。
- 三个流程在协议夹具驱动下走完，覆盖人工补充、人工确认、门禁拒绝和返工。
- 反向验证通过：全程不出现仓库接入、测试配置、分支和 PR。
- 真实模型验收单独记录：一个订单从下单走到签收。
- 实施中发现的每个抽象缺口都有结论：已回写契约，或登记到第 7 节。
- 完整检查通过。

### P4 工程扩展模块迁移

工作项：WS8 全部，N-9，D-1。M-0 先行，其产出的契约经确认后再开始 M-1 之后的各项。

**门禁 4**

- 未声明工程扩展组的领域不能使用工程处理器，电商出库仍通过门禁 3。
- 软件开发包重发后通过既有的真实交付验收。
- 完整检查通过。

## 5. 总体验收

计划完成的条件是门禁 1 到 5 全部满足，并且以下六条同时成立：

1. 在 `crates/` 的非测试代码中搜索两个领域包的标识和工程词表，结果为空，由检查保证。
2. `plugins/` 下的任何领域都能在只有 SDK 制品的目录里构建，由 CI 的独立作业保证。
3. 两个领域包的清单都声明依赖，安装期核对有正向和反向的测试。
4. 电商出库不声明任何扩展组即可完整运行；软件开发包声明三个工程扩展组。
5. Web Core 的源码与制品都不包含领域代码，领域 UI 只依赖两个入口。
6. 文档与实现一致。

## 6. 风险与待验证点

| 编号 | 风险或待验证点 | 应对 |
|---|---|---|
| V1 | 无仓库项目的 Agent 步骤可能无法运行。现有领域的 Agent 步骤都运行在已接入仓库的项目上，没有仓库的项目尚未验证过 | N-8 在 P1 内尽早验证。不成立则增加通用的文档工作区，这本身就是一个由第二个领域暴露出来的内核假设 |
| R1 | P4 规模大，且涉及冻结执行的恢复语义 | 排在第二个领域验证之后；M-0 先出契约；用模块注册做切面，不一次性重写 |
| R2 | 测试改造比预想的大：34 个浏览器用例和 6 个 entrypoint 测试依赖单体模式 | T-1 先做公共引导；内核用例改用自建的最小领域包，不再依赖软件开发的配置内容 |
| R3 | 工具定义归属的调整会改动软件开发包里大量引用 | 不写兼容层，一次切换；`devdesk-domain check` 负责找出断开的引用 |
| R4 | 与 Harness 计划并行时的路径和 Schema 冲突 | 按 0.5 节的约定 |
| R5 | 电商领域的真实模型验收依赖模型凭据和 Docker | 与自动化测试分开记录，不阻塞门禁 3 的其余各项 |
| R6 | 组件套件的配置编辑器可能仍带有工程假设，例如要求仓库就绪 | P3 中逐页核对，发现的假设登记为抽象缺口 |

## 8. 实施约束

- 沿用[仓库指南](../../../AGENT.md)的全部约定：保留已有改动、先核对引用再删除、专用测试数据目录、报告写明命令与未验证范围。
- 不写兼容层。遇到“要不要保留旧路径”的选择，一律不保留，把行为变化写进当时的执行报告。
- 改变业务路径时核对冻结历史的读取与恢复。新数据集上的在途执行仍须能恢复。
- 调整 crate 文件后运行文档索引的更新命令。修改行为时同步更新设计与当前文档。
- 每个阶段的执行报告放在本目录，只保留 Markdown。
