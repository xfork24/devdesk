## 1. 摘要

仓库自述为“Rust Host、Web Core、领域 ZIP”三者独立交付。审阅的结论是：**互操作方式的骨架合理，但三者只在运行期和制品层独立，在源码、构建、契约三层都不独立。** 它们目前更像一个仓库里的三个目录，还不是三个组件。

说骨架合理，是因为以数据为主的领域包、受限的只读处理器、声明式的界面贡献、内核保留全部写权限与外部副作用，这套模型让领域可以在不改内核、不重启 Host 的情况下安装和切换，同时不扩大信任边界。缺的主要不是运行时重构，而是契约与守卫。

| 层 | 审阅时的情况 |
|---|---|
| 运行期与制品 | 独立。Host 可从空领域启动，领域 ZIP 在运行时安装和切换，领域处理器在沙箱中执行 |
| 源码与构建 | 不独立。领域 UI 约 96% 的源码在核心包，构建配置在核心包，领域 ZIP 的构建读取内核内部文件 |
| 契约 | 不独立。没有单一入口、版本和兼容声明；内核与 Web Core 都含有按首个领域形状编写的通用逻辑 |

三个问题直接回答如下。

**内核 SDK 是否清晰、隔离良好。** 运行时隔离是好的：领域处理器在断网、只读、限时、限额的容器里执行，只能读不能写，输入输出双向校验。SDK 本身是隐式的，分散在七个切面里。内核生产代码有两处字面引用软件开发包；更多的是概念层泄漏。它当时实际是软件开发领域的参数化接口：换一个领域做思想实验，14 件事里 8 件做不到。

**Web Core 对领域 UI 的约束。** 约束等于“能加载”。名义 SDK 只有 4 个模块，其余靠领域直接 import 核心源码。嵌入规则没有一条写成了文档，共整理出 18 条隐式契约。核心与领域之间靠 DOM 探测互相挂载。

**整体架构哪里不合理。** 内核的身份没有定下来；领域包协议是照着第一个领域搭的；边界没有任何机器守卫。

## 3. 发现

### 3.1 内核到领域包的反向依赖

两处字面引用都在生产代码中，都硬编码了软件开发的六个角色标识：[configuration_catalog.rs](../../../crates/core/src/configuration_catalog.rs) 第 49–61 行与 [experience_index.rs](../../../crates/adapters/src/experience_index.rs) 第 214–223 行。它们是单体迁到领域包时留下的兼容逻辑，但写成了内核对具体标识的永久知识。

### 3.2 内核被首个领域塑形

这是数量最多的一类，审计中归为 C、D 两类，共 12 条。

- **领域包协议带着工程钩子。** 分支命名、测试识别、项目接入、PR 文案是清单的顶层字段，core 的 `DomainReader` 端口有同名方法。
- **通用引擎按工程工具名分支。** 内核在十余处以字面量判断 `tests.run`、`git.delivery.open` 等名字，并据此改变权限、恢复和重试行为。
- **证据门禁只有一个具名槽位。** `operation_evidence` 在 Schema 上是任意键，内核只读 `git.delivery`，还会去读领域的输入端口名 `test_configuration`。
- **Host 的通用领域 RPC 按 GitHub 校验。**
- **Feature、Task 是内核一等类型。** 它们出现在 domain crate、状态、项目库的表和 RPC 中。

### 3.3 归属错位

- 领域 UI 源码住在 `web/src`。软件开发的前端只有 14 行入口在领域目录。
- `plugins/core` 不是 plugin，它是编译进内核的出厂资源。
- 40 个内核处理器的工具定义只发布在软件开发包里。空领域的 Host 上只发布了 9 个平台工具定义。
- 核心样式表 3117 行中有 186 行的选择器属于领域界面。

### 3.4 领域包到内核的非 SDK 依赖

领域 ZIP 的构建读取内核仓库的两个文件（`schemas/rpc.schema.json` 与一个检查脚本），构建脚本里还改写了内核 Schema 的一段。领域前端构建的 Vite 配置、TypeScript 范围和 npm script 全在 `web/`。检查脚本写死了两个目录，新领域无法使用。

### 3.5 守卫与文档

Rust 四个 crate 之间的依赖方向有完整守卫，crate 与 `plugins/` 之间没有任何规则。Web 侧的守卫是三个文件的黑名单。文档里的处理器数量与源码已经不一致，同一份配置包清单在内核构建时和领域安装时的校验深度也不同。

## 4. 应当保留的设计

| 设计 | 为什么好 | 位置 |
|---|---|---|
| 领域处理器断网、只读、限时、限额，且在合同中登记为只读 | 领域代码可以执行，但无法产生副作用 | [worker.rs](../../../crates/adapters/src/domain_packages/worker.rs) 第 20–51 行 |
| 输入输出按包内 Schema 双向校验，具名钩子再做语义校验 | 内核不采信领域返回值 | [domain_packages.rs](../../../crates/adapters/src/domain_packages.rs) 第 230–241、944–967 行 |
| 命名空间、逐文件摘要、引用闭合在安装前校验 | 坏包进不了数据集 | 同文件第 256–552 行 |
| 对象类型、带基数的关系、对象工作流绑定 | 真正通用的扩展点，不含工程词汇 | [domain-entity-types.schema.json](../../../schemas/domain-entity-types.schema.json) |
| 不可变的 `identity:revision` 与执行冻结 | 领域包升级不影响在途执行 | 全局 |
| Web 同文档共享 React 树，资源按代次与摘要校验 | 避开了 iframe 与微前端的复杂度 | [DomainWorkbench.tsx](../../../web/src/DomainWorkbench.tsx) 第 172–327 行 |
| 客户端中立的贡献声明 | 非浏览器客户端可以通用呈现 | [domain-contributions.schema.json](../../../schemas/domain-contributions.schema.json) |

改造是在这些设计之上补齐契约，不是另起一套模型。

## 5. 决策记录

审阅给出了若干待决策事项，以下是 2026-11-26 确定的结论。

| 决策 | 结论 | 影响 |
|---|---|---|
| 内核定位 | **领域无关**。通用概念由内核定义，领域相关的必须迁移 | 工程能力与 Feature、Task 离开内核 |
| 工程能力的去向 | **内置扩展模块**。经通用扩展点注册，领域包声明依赖时才启用；Feature、Task 改为软件开发包的对象类型 | 这是改动面最大的一项，排在第二个领域验证之后 |
| 兼容范围 | **不兼容**。软件开发包随内核重发，旧数据集归档后重建，不写兼容层 | 不需要新旧字段并存，也没有数据迁移 |
| 单体测试模式 | **移除并改造测试** | 端到端用例改为安装真实 ZIP 后运行 |
| 第二个领域的深度 | **三个完整流程，纯文档与纯函数** | 不接真实电商或物流 API |

审阅时曾建议把内核定位为“工程内核加领域包”，理由是代码事实如此、迁移成本最低。最终决定选择领域无关。它的代价是迁移面覆盖 domain、core、adapters、SQL、RPC、Schema 和 Web，由分阶段交付来控制：先让第二个领域验证协议核心，再迁移工程能力。

## 6. 未验证范围

审阅是静态的。以下各项在审阅时没有验证，报告与基线中涉及它们的陈述应按此理解：

- 没有运行 Host、Web 或任何测试。文中“已核实”指读过对应源码。
- import 闭包统计基于对 `import`、`export … from`、动态 `import()` 的正则匹配。没有解析 CSS 的 `@import`，没有统计 JSON。
- 重复编译的模块各持一份状态，是否已经造成实际缺陷没有运行验证。
- ModelProvider 的哪些 `protocol` 取值可以工作没有核实。
- `defaults.json` 中 `capability_ref`、`orchestration.mode`、`authoring` 的读取点没有逐一追踪。
- 没有做安全评估。文中提到的处理器沙箱边界只描述配置值，没有验证其逃逸难度。
- 没有评估性能。处理器每次调用启动一个新容器的延迟特征未测量。
