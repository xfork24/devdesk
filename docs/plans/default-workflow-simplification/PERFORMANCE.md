# 精简版实际执行计时

状态：真实验收进行中，以下为已落盘区间的实测值，不是完整 Feature 验收结论。日期：2026-11-18。

## 口径与场景

本次使用真实 Codex app-server、Docker、Git 和 GitHub；模型冻结为 `builtin-model-gpt-6-1-sol-high:1`。专用测试仓库为 `xfork24/devdesk-default-workflow-test-20261118`，有效场景证据在 `/tmp/devdesk-default-workflow-simplification-20261118/live-dag4`。此前失败尝试保留，不能与当前成功执行混算。

用户提出简单 Feature 总耗时应接近直接 Codex 的约三分钟，流程开销后以五分钟为目标。本场景包含 A/B/C 三个 Task、独立评审、两类回归、竞争和恢复故障注入，B 的测试刻意等待 90 秒，不能作为无负载单 Task 的速度基线。详细版真实运行及性能对照已按用户要求取消。

B 的 Red、Green、Task 源回归、Task 合并回归、Feature 源回归和 Feature 合并回归至少六次完整执行该等待，沿 B 到 Feature 的前后依赖路径至少需要九分钟；目标竞争后的重新回归还会增加等待。该人为负载与正常调度开销分别记录，不能通过缩短测试来达到五分钟。

SDK duration 是一次原生 Turn 的墙钟时间，包含模型、网络、上下文处理和动态工具等待；现有日志不能进一步精确区分纯推理与网络。Harness 基础开销这里只计已测的进程/容器/协议启动与停止。工具往返位于 SDK 区间内部，不能再次加到总时间。并行 Task 的时长也不能简单相加。

需求生成的启动为 2.070 秒，其中 Docker create 0.196 秒、协议初始化 1.843 秒；停止 0.225 秒。评审启动 1.831 秒，停止 0.232 秒。冷启动镜像安装不在这两个区间内。

需求生成累计输入 73,775 token，其中缓存 51,840；输出 6,192，其中 reasoning 195。评审累计输入 133,883，其中缓存 98,432；输出 2,150，其中 reasoning 200。这些是多次模型调用的累计量，不能解释为单次 prompt 大小。需求生成先向 lint 工具提交 5,009 字符的完整草稿，随后最终返回 4,954 字符文档；两稿并非完全相同，但存在大量重复生成，最终文本流本身占 60.006 秒。评审最终文本流占 20.549 秒。

结论只限于已测区间：主要时间处于 SDK 调用期间；目前没有证据把这两分钟归因于 SQLite、容器启动或 Host 工具执行。文档长度、多轮模型调用与全文重复交付是后续优化的具体调查方向。

同一经理 worker 的 thread/resume 携带 developerInstructions 220,746 UTF-8 字节、41 个动态工具定义合计 44,958 字节；本轮 turn/start 的增量 input 仅 1,881 字节。需求 worker 对应指令 15,127 字节、输入 19,093 字节；评审 worker 对应 18,482 和 40,259 字节，均为 4 个动态工具。字节数来自序列化请求字段，不能换算为精确 token 或延迟。经理工具和冻结上下文的大小值得单独优化，但尚不能据此声称其具体增加了多少秒。thread/tokenUsage.total 是线程累计值，尤其不能把经理此前所有轮次的累计输入当成此次交接输入。

## 额外等待与失败隔离

独立需求评审结束到 source_workspace 开始为 1,147.800 秒。这段不能计为“独立评审耗时”，也不能归咎于用户审批速度。经理把正常确认误用成评审拒绝例外申请，平台正确拒绝；经理随后声称等待已有人工检查点。外部验收脚本只监听新增 decision，漏掉了该原生检查点，导致延迟发现和代签。期间记录了 11 次 controller.wait、10 个经理 worker；其中 SDK 区间累计与空闲等待需按时序分析，不能当作连续工作。

已保留原始拒绝和等待，按用户已有的代批授权核对确切 PRD、独立报告及经理推荐后，通过正常 Human 确认接口签署，再由经理接纳。验收脚本补充监听已有检查点；出厂精简版经理 Skill 补充说明正常确认使用 step.confirm、step.approve 只用于允许的拒绝评审例外，已启动实例仍使用原冻结正文。该外部脚本代签不是产品 Agent 获得 Human 权限。

此前还分别出现冷镜像准备、父工作流默认 300 秒超时、SQLite storage_busy 导致原生观察中断等问题。它们作为失败/恢复证据保留，不用重新计时掩盖。父调度预算和持久化观察的有界重试已修正，完整端到端结果另行审计。

## 明确的后续优化依据

1. 优先调查六次文档生成/独立评审的长文本及重复完整输出；保持独立审查门禁，以减少生成及反复传递的内容为方向。
2. 减少经理在接纳、检查、派发之间的串行模型轮次，裁剪庞大的冻结上下文和动态工具定义，扩大适合连续自动节点的有界委托覆盖；当前约四分钟的前期交接有直接证据。
3. 运行计划的权限锁原来以新 Workflow 地址比较，误把相同权限当作变化，导致局部合同修复扩大到整条流程重做。本轮修复为按实际权限内容比较，并补充有根 Agent、完成子实例和变更输入的正反回归；新加不可变 Delivery 只影响引用它的步骤及下游。
4. 区分平台外部 I/O 与模型时间。单 Task 的 PR 准备及 merge/sync 已分别记录，不把 GitHub 网络时间记为 Harness；普通测试在本场景不到数秒，不能解释整体二十多分钟。

未执行直接 Codex 三分钟对照，因此不声称工作流相对直接执行的倍率；详细版性能对照按用户指示取消。此次交付记录性能缺口，为独立后续优化提供依据，不通过删除独立评审、两类回归或最终人审换取五分钟。

## 采集与证据

`tests/live/probe_streamlined_workflow.py --performance` 记录 Host 原生阶段计时与观察查询延迟；`tests/live/profile_workflow.py <证据目录> --output <外部 JSON 路径>` 以只读 SQLite 快照、已注册协议产物和 Host 计时生成逐步骤、逐 worker、交接区间报告。输出仅保存计时、计数、身份与大小，不复制凭据或协议正文。实例总墙钟使用实际 complete 决定时间；步骤 finished 是产出方工作结束，不代表下游接纳或父流程 complete，不能用两者差值遗漏收尾交接。
